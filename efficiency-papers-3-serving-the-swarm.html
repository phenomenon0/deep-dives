SERVING THE SWARM

ML engineers rediscovered what OS engineers knew in 1960. Pages, tables, copy-on-write — the papers that turned inference into infrastructure._
The Efficiency Papers — Part III

01 // The Hotel Problem

Imagine you run a 100-room hotel. Every guest who walks in might stay for 30 nights — but most leave after two. Your reservation policy: block 30 rooms for every guest, just in case. A backpacker wants one night? Thirty rooms blocked. A couple wants a weekend? Thirty rooms blocked. By the time three guests have checked in, you've "reserved" 90 rooms but only six are occupied. The lobby is full of people you're turning away because the system says you're at capacity.

That was GPU memory management before 2023.

Every time a language model receives a request, it needs space for a KV cache — the running memory of every token the model has seen and generated. Each layer of the Transformer stores a key vector and a value vector for every token in the sequence. As the model generates its response, the cache grows token by token. But here's the problem: the system doesn't know how long that response will be. Could be 10 tokens. Could be 4,096. Could be 32,768. So it reserves for the worst case: one contiguous slab of GPU memory, sized for the maximum possible output length.

A request that generates 50 tokens still holds memory for 2,048. A request that asks "What's 2+2?" and gets "4" holds the same reservation as a request generating a five-page essay. The GPU doesn't distinguish between "might need this" and "actually using this." Reserved is reserved.

To feel the scale: for a Llama-2 13B model with a 4,096-token context window, each request's KV cache reservation is approximately 800 MB. On an A100 with 80 GB total memory, after the model weights consume ~26 GB, you have ~54 GB left for KV caches. That fits 67 concurrent requests if each reserves 800 MB. But if requests only generate 200 tokens on average (using ~5% of their reservation), you could fit 1,300 requests in the same memory. The gap between 67 and 1,300 is the cost of pre-allocation.

The waste is not subtle. Measurements from the PagedAttention paper (Kwon et al., 2023) decomposed the problem into three failure modes:

Internal fragmentation. Each request's allocated slab is sized for the maximum, but the actual generation rarely fills it. The unused tail of each slab is dead space — allocated, mapped, invisible to the free-list, doing nothing.

External fragmentation. When requests finish and release their slabs, they leave gaps of varying sizes. A new request needs a contiguous block. The gap is too small. Another gap exists elsewhere, also too small. Total free memory might be sufficient, but no single contiguous region fits. Same pathology that plagued heap allocators in the 1970s.

Reservation waste. Memory reserved for tokens that haven't been generated yet — and may never be, if the request finishes early or gets preempted. The system is holding a reservation on behalf of a future that may not arrive.

The combined toll: only 20–38% of KV cache memory actually stores token states. The rest — 60 to 80% — is dead weight. On an A100 with 80 GB, that's 48–64 GB doing nothing. On a cluster of 1,000 GPUs, that's 48–64 terabytes of the most expensive memory in the world, holding empty space.

The Cost

An A100 GPU rents for $2–3 per hour. If 70% of its memory is wasted on fragmentation, you're paying $1.40–$2.10 per hour per GPU for nothing. A 1,000-GPU deployment loses $1,400–$2,100 per hour — $12–18 million per year — to empty reservations.

One request is easy. Ten thousand is a different universe.

Serving a single LLM request is trivial. Load the model, run prefill, decode token by token. A 7B model on a single A100 handles one user comfortably. The entire field of "LLM serving" exists because one user isn't the problem.

Scale to 10,000 concurrent users and three crises compound at once.

Crisis 1: Memory is finite, requests are greedy. Each request's KV cache grows with every generated token. A thousand concurrent requests at 2K context on a large model can demand hundreds of gigabytes of KV cache alone — far more than any single GPU holds. You must decide who gets memory, who waits, and who gets evicted mid-generation. Do you preempt the request that's 90% done to make room for a high-priority new one? Do you swap KV caches to CPU RAM and back? This is a policy problem, not an engineering problem. It's the same problem operating systems solved with page replacement algorithms — LRU, LFU, clock — and serving systems reinvented the same solutions, often without knowing they existed.

Crisis 2: Variable lengths make batching a mess. The naive approach: collect a batch of requests, run them together, wait for ALL to finish. If one request needs 500 tokens and the other 31 finish at 20, the GPU runs 480 additional decode steps where 31 out of 32 slots are padding — fake computation that produces no useful output. You're paying for a supercomputer and using it to wait. The GPU utilization curve looks like a sawtooth: briefly high when a batch starts, then declining as requests complete and slots go idle, then high again when the next batch begins.

Crisis 3: Prefill and decode sabotage each other. Prefill processes the entire input prompt in one parallel pass — compute-heavy, the GPU doing what it was born to do. Massive matrix-matrix multiplications that saturate every tensor core. Decode generates one token at a time — a skinny matrix-vector operation that is memory-bandwidth-bound. The GPU has thousands of cores but decode uses maybe 1–5% of available FLOPS. It's mostly waiting for data to arrive from HBM.

When both phases share a GPU, they sabotage each other. One tourist demands a two-hour check-in while the line grows. A single long prefill — someone feeding a 32K-token document to be summarized — monopolizes the GPU for seconds. During that time, every in-flight decode request in the batch is blocked. No tokens generated. Latency spikes. Users stare at frozen cursors. This is head-of-line blocking, the same pathology that plagued single-threaded web servers in the 1990s.

The Reframe

LLM serving is, at its core, a scheduling problem — closer to air traffic control than to machine learning. Finite runway (GPU memory), variable-size aircraft (requests with different lengths), unpredictable arrival times. The model itself is the easy part. The hard part is managing 10,000 overlapping lifecycles on hardware that wasn't designed for sharing.

Four papers fixed this problem. They arrived in sequence between 2022 and 2025, each one reaching deeper into the same bag of tricks — one that operating systems engineers packed in the 1960s and '70s. Together they turned inference from a research hack into production infrastructure.

Each paper made a different bet. One bet that the scheduling was wrong. One bet that the memory management was wrong. One bet that the caching strategy was wrong. And one bet that the abstraction layer itself was wrong — that you should stop reimplementing the OS and start using it. They were all right. Here's how.

02 // The Scheduling Revolution

In 2022, Gyeong-In Yu at Seoul National University looked at how inference servers batched requests and saw a bus that refused to stop. Static batching — the only approach anyone used — collected a fixed batch of requests, ran them all through the model, and waited for every single one to finish before accepting new passengers. If one request needed 500 tokens and the other 31 needed 20, the bus drove the full 500-stop route while 31 passengers sat trapped, their destinations long passed.

Think about what this means concretely. Request #7 finishes generating at iteration 20. Its tokens are complete. Its memory could be freed. But it remains in the batch — padded with dummy tokens — for 480 more iterations, consuming GPU cycles on meaningless computation. Meanwhile, Request #33 arrived at the server at iteration 21. It will wait in the queue until all 500 iterations complete. Then the system clears the batch, collects the next group of requests, and starts over. Request #33 might wait minutes, watching an idle queue, because the batch boundary is sacred.

Yu and his collaborators — including advisor Byung-Gon Chun, who would later co-found FriendliAI — published Orca at OSDI 2022. The paper's subtitle says it all: "A Distributed Serving System for Transformer-Based Generative Models." Not a model optimization paper. A systems paper. Published at the Operating Systems Design and Implementation conference.

The idea was disarmingly simple: don't schedule per request. Schedule per iteration.

Iteration-level scheduling

After every single decode step — one forward pass through the model, one token generated per active sequence — Orca's scheduler runs. It checks three things:

Orca scheduler loopfor each iteration:
    // 1. Who's done?
    finished = [seq for seq in batch if seq.eos or seq.len >= max_len]
    batch.remove(finished)
    release_memory(finished)

    // 2. Who's waiting?
    waiting = queue.dequeue(batch.free_slots)
    batch.insert(waiting)
    allocate_memory(waiting)

    // 3. Run the next forward pass
    forward_pass(batch)

That's it. The batch is fluid. Sequences enter and leave at every iteration, not at batch boundaries. The transportation analogy shifts: static batching is a bus that can't stop. Orca is a subway — passengers enter and exit at every station. The train never waits for the last rider.

Static Batching

Gather N requests. Run all until the longest finishes. Accept new batch. GPU idles on padding for short requests. New arrivals sit in queue until the batch clears.

Throughput: 1x baseline

Continuous Batching (Orca)

After each decode step: eject finished sequences, inject waiting ones. Batch stays full. GPU never wastes cycles on completed requests. No one waits for a batch boundary.

Throughput: up to 36.9x

Selective batching

There's a subtlety the summary misses. Not every operation in a Transformer can be naively batched across sequences of different lengths. The feed-forward layers are position-independent — they process each token identically regardless of where it sits in the sequence. Batch freely. But attention depends on sequence position: each token attends to all previous tokens in its own sequence, not tokens from other sequences in the batch. You can't just concatenate everyone's tokens and run one attention kernel.

Orca introduced selective batching: apply batching to position-independent operations (the feed-forward networks, layer norms, embeddings) while handling position-dependent operations (attention) per-sequence. This sounds like a detail, but it's what makes the whole thing work. It lets the engine process heterogeneous sequences — some still in their prefill phase (processing long input prompts), others mid-generation (producing token #47 of a response) — in a single forward pass.

The result: 36.9x throughput over NVIDIA's FasterTransformer at the same latency, measured on a GPT-3 175B-scale model. That number is extreme. It captures the worst case for static batching: high variance in output length, where short requests wait ages for long ones. Real production gains — conversational workloads where output lengths vary 10–500 tokens — settle around 3–8x. But 3x on a GPU that costs $30,000 means the same workload runs on one-third the hardware. Or three times the users on the same hardware. Either way, millions of dollars.

The Ripple Effect

Every major inference framework adopted iteration-level scheduling within two years. vLLM calls it continuous batching. NVIDIA's TensorRT-LLM calls it in-flight batching. Hugging Face TGI, SGLang, LMDeploy — all of them. An OSDI paper from Seoul became the default scheduling policy for the entire industry. Yu went on to become CTO of FriendliAI. The paper won Best PhD Dissertation from Seoul National University's CS department.

The prefill-decode interference problem

Continuous batching solved scheduling. But it introduced a new conflict: prefill-decode interference. The two phases of inference have opposite computational profiles, and cramming them onto the same GPU creates head-of-line blocking.

Prefill processes the entire input prompt in one parallel pass. Every token in the prompt is processed simultaneously. This is a massive matrix-matrix multiplication — the kind of operation GPUs are designed for. Tensor cores saturate. FLOPS utilization is high. The operation is compute-bound.

Decode generates one token at a time. Each new token requires a full forward pass, but the computation is a single matrix-vector operation (the new token attending to all cached keys/values). GPU utilization drops to 1–5% of available FLOPS. The operation is memory-bandwidth-bound — the bottleneck is reading the model weights and KV cache from HBM, not the computation itself.

When continuous batching mixes prefill and decode requests in the same batch, a long prefill (a 32K-token document being summarized) monopolizes the GPU for seconds. Every in-flight decode request in the batch is blocked. No tokens generated. The user who asked "What's the weather?" watches their cursor freeze because someone else submitted a legal document.

The industry response: prefill-decode disaggregation. Run prefill on one pool of GPUs and decode on another, so they never interfere. DeepSeek deployed this architecture for their V3 model. Together AI's cache-aware variant reported 40% higher throughput for long-context workloads. Every major serving framework — vLLM, SGLang, TensorRT-LLM — now supports disaggregated scheduling. It's the same principle that drove web servers from single-threaded to multi-process architectures: separate the heavy initialization work from the interactive streaming work.

The disaggregation story is worth pausing on because it reveals how deep the OS analogy goes. In web serving, Nginx separates the "accept connection and parse headers" phase (fast, I/O-bound) from the "run the application handler" phase (slow, compute-bound). They run on different processes. The same pattern appears in databases: the query parser and the execution engine are decoupled so that parsing one query doesn't block executing another.

Prefill-decode disaggregation is the LLM equivalent. Prefill GPUs become the "parser pool" — they accept prompts, process them in bulk, and ship the computed KV caches to the decode pool. Decode GPUs become the "execution pool" — they generate tokens one at a time, latency-sensitive, never blocked by a heavy prefill. The architecture looks identical to a web application with separate frontend and backend tiers. The only difference is that the "network" between tiers is NVLink or InfiniBand, and the "requests" are KV cache tensors.

But Orca's deepest contribution wasn't any single optimization. It was a reframing. Before Orca, inference was a machine learning problem: run the model. After Orca, inference was a systems problem: manage the queue. That shift — from compute to scheduling — opened the door for everything that followed.

Think about what Orca didn't change. It didn't change the model. It didn't change the hardware. It didn't even change the attention mechanism. It changed the order in which requests execute and the granularity at which the system makes scheduling decisions. Pure scheduling. Pure systems design. And it delivered more throughput improvement than any model architecture change that year.

The next paper through that door would reach even further back into the operating systems playbook — all the way to the 1960s, and to the single most important memory management abstraction ever invented.

Deep detail: How selective batching handles mixed prefill/decode

In a continuous batching system, the active batch might contain sequences at very different stages. Sequence A is on token 3 of its decode (generating word by word). Sequence B just arrived and needs to prefill a 2,000-token prompt. Sequence C is on token 47 of its decode. How do you run a single forward pass with all three?

Orca's selective batching splits the forward pass into two categories of operations:

Position-independent operations (feed-forward layers, layer norms, embedding lookups): These process each token identically regardless of context. You can concatenate all tokens from all sequences into one big batch, run the FFN, and split the results back. This is maximally efficient — full GPU utilization on the compute-heavy layers.

Position-dependent operations (self-attention): Each token attends only to tokens in its own sequence. You cannot batch across sequence boundaries. Orca processes attention per-sequence (or uses grouped attention with appropriate masking). For prefill sequences, this means a single large matrix-matrix attention. For decode sequences, this means a single-row matrix-vector attention. Both run in the same forward pass, just with different shapes.

Modern implementations (vLLM, SGLang) use FlashAttention with variable-length support: a single kernel call processes multiple sequences of different lengths by passing a cumulative sequence length array. The kernel handles the per-sequence boundaries internally. This eliminates the overhead of separate per-sequence kernel launches.

03 // The Page Table

In the summer of 2022, a team of PhD students in UC Berkeley's newly launched Sky Computing Lab had built a framework for distributing models across GPUs. When they set up a demo, performance was terrible. Not "could be better" terrible. Barely functional terrible. Zhuohan Li and Woosuk Kwon spent months profiling, expecting to find a compute bottleneck — maybe the attention kernels were slow, or the pipeline parallelism had too much bubble time.

Instead they found a memory management disaster.

The KV cache — not compute, not communication — was the binding constraint. Requests were reserving huge contiguous slabs of GPU memory and barely using them. The GPU was reporting "out of memory" while most of its HBM held nothing. The profiling traces told a clear story: memory fragmentation was killing throughput before compute ever got a chance.

Kwon had a specific memory. Not a GPU memory — a human one. He recalled a concept from his undergraduate operating systems course at UC Berkeley: virtual memory with demand paging. The idea that transformed computing in the 1960s. The OS doesn't give each process a contiguous slab of physical RAM. It breaks memory into small fixed-size pages, typically 4 KB each. A process thinks it has a big contiguous address space (the "virtual" part), but the pages are scattered across physical RAM wherever there's room. A page table maps virtual addresses to physical locations. The hardware (the MMU) handles the translation transparently. Pages are allocated on demand — only when the process actually touches them, not when it asks for address space.

This is the idea that let a 64 KB machine run programs that needed 256 KB. It's the idea that lets your laptop run dozens of programs whose combined memory demands exceed your physical RAM. It solved the same three problems the KV cache faces: internal fragmentation (processes that don't use their full allocation), external fragmentation (freed memory leaving unusable gaps), and over-reservation (allocating for worst-case needs that rarely materialize).

The Atlas computer at the University of Manchester implemented the first virtual memory system in 1962. By the 1970s, every major operating system used demand paging. By the 1980s, it was so foundational that engineers stopped thinking about it — it just worked. It's one of the three or four most important abstractions in the history of computing.

Kwon asked the question that created an industry: why aren't we doing this for the KV cache?

PagedAttention

The answer became PagedAttention, the core algorithm behind vLLM. Kwon, Li, and their collaborators — including Ion Stoica and Hao Zhang, both key figures in the Berkeley systems community — published the paper at SOSP 2023. Not a machine learning conference. The Symposium on Operating Systems Principles. The most prestigious venue in systems research.

The paper's core contribution is a one-to-one mapping between OS virtual memory concepts and GPU KV cache management. Every concept has a direct analog:

The mechanism: break the KV cache into small fixed-size blocks, each holding key and value vectors for 16 tokens. Don't allocate them upfront. As the sequence grows token by token, allocate new blocks on demand from a free list. Store them anywhere in GPU memory — they don't need to be contiguous. A block table maps logical positions (block 0, block 1, block 2...) to physical block IDs. The attention kernel gathers scattered blocks using this indirection, the same way a CPU's memory management unit translates virtual addresses to physical ones.

PagedAttention pseudocode// Each sequence gets a block table: logical_idx -> physical_block_id
block_table[seq_id] = []

// As tokens generate, allocate blocks on demand
def append_token(seq_id, token):
    logical_idx = seq_id.num_tokens // BLOCK_SIZE
    if logical_idx >= len(block_table[seq_id]):
        phys_block = free_list.pop()            // grab from pool
        block_table[seq_id].append(phys_block)   // map it
    offset = seq_id.num_tokens % BLOCK_SIZE
    write_kv(block_table[seq_id][-1], offset, token)

// Attention kernel uses block table to gather K,V from scattered blocks
def paged_attention(query, seq_id):
    for block_idx in block_table[seq_id]:
        k, v = load_block(block_idx)           // physical location
        output += attention(query, k, v)        // standard attention
    return output

Result: memory waste dropped from 60–80% to under 4%. The only waste is in the last block of each sequence, which might not be completely filled — and even that waste is at most BLOCK_SIZE - 1 tokens per sequence, amortized across the entire cache.

The practical impact: same GPU, same model, 2–4x more concurrent requests fit in memory. This translates directly to 2–4x throughput, because more requests in the batch means the GPU does more useful work per forward pass. The gains are multiplicative with Orca's continuous batching — Orca packs the schedule, PagedAttention packs the memory, and the combination is the foundation of every modern serving engine.

Against HuggingFace Transformers (the naive baseline many teams started from), vLLM showed 14–24x throughput. Against FasterTransformer (NVIDIA's optimized engine, already using some batching), the gain was 2–4x. Against Orca itself (which had continuous batching but not paged memory), the gain was still meaningful: the same scheduling quality, but fitting 2–3x more requests in the batch.

Copy-on-write for beam search

Beam search generates multiple candidate sequences from the same prompt. In the old world, each beam got its own copy of the prompt's KV cache — identical data, duplicated N times. PagedAttention asks: why copy? All beams start from the same prompt. Their KV caches are identical until they diverge.

The solution: reference counting, borrowed directly from Unix fork(). When the beam search forks, all candidates share the prompt's physical KV blocks. The reference count on each shared block increments. When a beam generates a token that diverges from its siblings — writes new KV data to a block that other beams still need — the system copies that block first, then modifies the copy. Classic copy-on-write.

The savings: 55% memory reduction for beam search workloads. For parallel sampling (generating multiple responses to the same prompt), shared prompt blocks saved 6–10%. In the original paper, beam search with 4 beams went from requiring 4x the memory to requiring roughly 1.8x — the shared prefix dominates.

The kernel tax

There's a catch, and it matters for the next chapter.

PagedAttention's block table adds a layer of indirection to every attention computation. The kernel must look up physical block IDs before accessing KV data. FlashAttention — the fastest attention kernel, the one Part I of this series covered — expects contiguous memory. It was designed to tile through a single contiguous buffer with optimal memory access patterns. Non-contiguous blocks break those patterns.

PagedAttention needed a custom "paged" variant of FlashAttention: flash_attn_with_kv_cache. That variant works, but it's 2.8x slower than native FlashAttention for the kernel itself. The total system throughput still wins because you're serving 2–4x more requests (the memory savings outweigh the kernel overhead). But the per-kernel tax is real.

Worse, it created an ecosystem problem. Every new attention kernel innovation needed a paged version. FlashAttention-2 needed one. FlashAttention-3 shipped without one initially — meaning you couldn't use the fastest attention kernel with dynamic memory management. FlashInfer built its own paged backend. DeepSeek's MLA attention needed yet another. Each kernel, each variant, each integration: hundreds of lines of GPU code to handle block table indirection.

The Kernel Tax

PagedAttention's block table is a software reimplementation of hardware address translation. Every kernel must implement the lookup. Every new attention innovation must be ported to the paged format. The abstraction saves 60% of memory but costs 2.8x in kernel speed and fragments the entire attention kernel ecosystem. One paper, later, would ask: why are we doing this in software?

The eureka, and why it appeared at SOSP

The PagedAttention paper was reviewed and accepted by operating systems researchers, not machine learning researchers. The program committee at SOSP recognized what it was: an OS paper that happened to run on GPUs. The contribution wasn't a new model architecture or a new training trick. It was a memory management system — a page table, a free list, a demand allocator, and a copy-on-write mechanism — applied to a new domain.

The Eureka

"This IS virtual memory." Woosuk Kwon literally recalled his undergrad OS course and transplanted the core abstraction to GPUs. Every CS undergrad learns paging, passes the exam, forgets it. Then, a decade later, the exact same problems appear on different hardware, and someone has to reinvent the same solutions. The deepest insight in the vLLM paper isn't technical. It's sociological: knowledge siloed in one field sat dormant while another field needed it.

Deep detail: Inside vLLM's block management

The current vLLM architecture (v1, post-refactor) implements PagedAttention through four key components:

BlockPool: Manages all physical KV cache blocks. Maintains KVCacheBlock objects indexed by block_id, a free block queue (FreeKVCacheBlockQueue) sorted in LRU order, and a cached block map (BlockHashToBlockMap) for prefix caching lookups.

BlockTable: The page table. Maps each request's logical block positions to physical block IDs. Supports a hybrid mode where one allocation block maps to multiple kernel blocks via blocks_per_kv_block, allowing different granularities for allocation and computation.

KVCacheManager: Orchestrates the allocation flow. On each new request: (1) check the prefix cache for hits via get_computed_blocks(), (2) allocate new blocks from the BlockPool via get_new_blocks(), (3) when blocks fill up with tokens, hash them and register in the prefix cache for future reuse.

LRU Eviction: When the free list is exhausted, evict blocks with ref_cnt == 0 from the head of the LRU queue. Blocks are freed in reverse order (tail first) to prioritize evicting less-reusable blocks — the tail of a sequence is less likely to be a shared prefix than the head.

This is a full OS-style memory management subsystem, running in Python and CUDA, inside a serving framework. It's the functional equivalent of Linux's mm/ subsystem, specialized for KV cache blocks instead of 4 KB pages.

04 // Just Use the OS

PagedAttention was inspired by OS paging. But it reimplemented paging in userspace — inside the serving framework, inside the GPU kernels. It wrote a custom allocator. A custom page table (the block table). Custom attention kernels that understand block-table indirection. Every component of the OS memory management stack, rebuilt from scratch in CUDA.

In 2025, a team at Microsoft Research India asked the question that was hiding in plain sight: the GPU already has a memory management unit. Why aren't we using it?

vAttention (Prabhu et al., ASPLOS 2025) completed the arc. CUDA has had virtual memory management APIs since CUDA 10.2. The function signatures are right there in the documentation. cuMemAddressReserve. cuMemCreate. cuMemMap. They do exactly what their names suggest: reserve virtual address space, create physical memory handles, map physical pages to virtual addresses. The GPU's hardware MMU does the virtual-to-physical translation at wire speed, transparently, without any kernel modifications.

PagedAttention rebuilt this in software. vAttention deleted the rebuild.

Three API calls

The entire memory management system reduces to three CUDA functions:

CUDA VMM// Step 1: Reserve a contiguous virtual address range
// No physical memory allocated yet. Address space is cheap.
// 64-bit GPUs have 128 TB of virtual address space available.
cuMemAddressReserve(&ptr, size, alignment, 0, 0);

// Step 2: Create a physical memory handle (one "page")
// This actually allocates physical GPU memory.
cuMemCreate(&handle, page_size, &prop, 0);

// Step 3: Map the physical page to a virtual address
// After this, the virtual address range is backed by physical memory.
// The GPU MMU handles translation in hardware.
cuMemMap(ptr + offset, page_size, 0, handle, 0);

The strategy: reserve 12 terabytes of contiguous virtual address space per KV cache (64-bit GPUs have 128 TB available — virtual address space costs nothing). Map physical pages only when tokens actually arrive. The model sees a contiguous tensor. The GPU hardware handles the physical scatter underneath.

This is exactly how malloc works on Linux. The kernel overcommits virtual address space freely. Physical pages get mapped (via page faults) only when you actually write to them. The application never knows the difference. The MMU makes non-contiguous physical memory look contiguous. vAttention does the same thing on the GPU.

FlashAttention works UNMODIFIED. Any kernel works unmodified.

That last line is the real payoff. FlashAttention sees a contiguous tensor — because the virtual addresses are contiguous. The GPU hardware handles the physical scatter transparently. No custom kernels. No block tables. No paged variants. When FlashAttention-3 ships, it works immediately. When someone writes a new attention kernel next month, it works immediately. The kernel tax that PagedAttention imposed on the entire ecosystem simply vanishes.

Deferred reclamation

vAttention adds a clever optimization for the hot path. When request R1 finishes, don't immediately free and unmap its physical pages. When R2 arrives, assign it R1's request slot and reuse the already-mapped physical memory. Only allocate new pages if R2's context exceeds R1's length. Batch the actual reclamation (unmapping and freeing pages) only when free memory drops below 10%.

This amortizes the cost of cuMemCreate (1.7 microseconds per 64 KB page) and cuMemMap (8 microseconds per mapping) across many requests. In practice, the allocation bandwidth reaches 7.6 GB/s — far more than the ~600 MB/s that decode-phase allocation actually needs. The overhead is invisible.

The page size problem

One wrinkle: NVIDIA's standard CUDA drivers only support a minimum page size of 2 MB. For a small model like Yi-6B, a single 2 MB page might hold KV data for hundreds of tokens — far more than a request typically needs per allocation step. The internal fragmentation in that last partially-filled page, multiplied across all active sequences and all layers, can reach 128 MB. On a 24 GB consumer GPU, that's 0.5% of total memory. On a production 80 GB A100 with hundreds of active sequences, it adds up.

The vAttention authors solved this by modifying NVIDIA's open-source unified memory driver (nvidia-uvm) to expose custom page sizes: 64 KB, 128 KB, and 256 KB. The kernel module exposes three new functions — vMemReserve, vMemCreate, vMemMap — that mirror the CUDA VMM APIs but with finer granularity. With 256 KB pages, worst-case fragmentation drops from 128 MB to 16 MB. With 64 KB pages, it drops further.

The tradeoff: smaller pages mean more page table entries, which means more TLB pressure on the GPU's memory management unit. The authors measured the overhead and found it negligible for typical serving workloads — the TLB is large enough to absorb the extra entries without measurable performance loss. But the custom driver module is a deployment friction. You can't just pip install vattention. You need to build and install a modified kernel module, which requires matching NVIDIA driver versions, kernel headers, and root access. For a research prototype, this is fine. For production at scale, it's a barrier.

The ecosystem irony

vAttention solved the ecosystem problem PagedAttention created: kernel fragmentation. It should be the obvious next step. Use the hardware for what the hardware was designed to do.

But vLLM's community closed the integration request as "not planned," arguing that the industry has converged on paged kernel layouts and that cuMemMap overhead may negate gains in some configurations. FlashInfer, the kernel library that vLLM uses, has deeply optimized its paged attention kernels — they're fast enough that the software indirection overhead is small for common batch sizes.

The ecosystem lock-in that vAttention diagnosed is, ironically, preventing its adoption. PagedAttention's software reimplementation of paging became so entrenched — the kernels so optimized, the integrations so polished, the production deployments so validated — that using the actual paging hardware is now the harder sell. Sometimes the reimplementation outlives the need for reinvention. Sometimes the workaround becomes the standard. PagedAttention wasn't the theoretically right answer — using the hardware MMU was always the cleaner design. But it was the available answer in 2023, when CUDA's VMM APIs were obscure and poorly documented, and it won by shipping first and iterating fast. In systems engineering, being deployed matters more than being correct.

The Pattern

PagedAttention said: "The OS solved this. Let's copy the idea." vAttention said: "If the OS solved it, let's use the OS." The first was a metaphor. The second was the literal implementation. Both were right. The GPU is speed-running 50 years of operating system evolution, and sometimes the shortcut is remembering the destination already exists. But sometimes the detour builds infrastructure that the shortcut can't replace.

Deep detail: The step() API and allocation flow

Before each decode iteration, the serving framework calls vAttention's step(sequence_lengths[]) API. vAttention checks each active sequence's current length against its mapped physical memory. If any sequence needs a new page (has grown beyond its last mapped page boundary), vAttention calls cuMemCreate + cuMemMap for that page. In the decode phase, this is at most one new page per active request per iteration — a small, predictable cost.

If step() can't allocate (out of physical memory), it returns -1, signaling the framework to preempt a lower-priority request. This is analogous to the OS page fault handler returning an out-of-memory signal to the process scheduler.

The step() API replaces PagedAttention's entire block management layer: the BlockPool, the BlockTable, the KVCacheManager, and the free block queue. All of that software becomes three CUDA API calls and a length check.

05 // The Prefix Tree

PagedAttention solved allocation. But it had a blind spot: it threw away the KV cache the moment a request finished. Every new request started cold — even if it shared 90% of its prompt with the previous one. Think about what that means for a chatbot. Every user starts with the same system prompt: "You are a helpful assistant. You respond concisely..." That's hundreds of tokens, identical across every single request. With PagedAttention, every request recomputes those tokens from scratch. Hundreds of times per second, across thousands of users, the same keys and values get calculated, stored, and discarded.

Imagine a library that burns its card catalog at closing and rebuilds it the next morning. From scratch. Even though the books haven't changed.

vLLM later added "Automatic Prefix Caching" (APC) using hash-based block matching at 16-token granularity. The system hashes each 16-token block of the prompt and checks if an identical block already exists in GPU memory. If yes, reuse it. If two prompts share the first 32 tokens, the two 16-token blocks match and get reused. Solid idea. But the granularity is coarse.

If two prompts diverge at token 17, the first 16-token block matches but the single shared token in the second block is wasted — the block can't be partially reused. And APC only cached prompt tokens, not generated ones. In multi-turn chat, the assistant's previous response is part of the next turn's context — but those tokens weren't cached. Every continuation recomputed them.

The filesystem insight

In late 2023, Lianmin Zheng — who had co-authored the vLLM paper — was working with a team spanning UC Berkeley, xAI, and the LMSYS chatbot arena. They'd been building SGLang, a programming language for structured LLM generation, and needed a backend that could handle complex multi-turn, multi-branch workloads efficiently.

Zheng asked a different question: what if KV cache management isn't a memory problem at all? What if it's a filesystem problem?

Think about it. A filesystem organizes hierarchical data: /usr/local/bin/python. Each component narrows the path. Shared prefixes (/usr/local/) are traversed once, not per file. The data structure that makes this work — the data structure Linux uses for its page cache, its routing tables, its radix tree — is purpose-built for prefix matching.

LLM workloads are tree-shaped. Multi-turn chat: shared system prompt branching into diverging conversations. Few-shot learning: shared examples branching into different queries. Agent workflows: shared tool descriptions branching into different tool calls. Beam search: shared prompt branching into candidate completions.

A radix tree is the natural data structure for tree-shaped data. And unlike a hash table (which vLLM uses for its block-level prefix cache), a radix tree preserves the hierarchical structure of the data. It knows that Turn 2 is a child of Turn 1, not just that they share a hash. This lets the scheduler reason about the cache topologically — which branches are hot, which are cold, which should be evicted first — instead of treating each cached block as an independent entry.

RadixAttention

SGLang, published at NeurIPS 2024, introduced RadixAttention: a radix tree that serves as a filesystem for KV caches. Each node in the tree holds a sequence of token IDs (the "key") and pointers to GPU memory holding their KV cache (the "value"). Children branch at divergence points. Looking up a prefix is O(length) — walk the tree, matching tokens at each node. This is how open("/usr/local/bin/python") works: traverse path components one by one until you reach the file.

Three improvements over vLLM's block-level caching make RadixAttention qualitatively different:

Token-level granularity. Unlike vLLM's 16-token blocks, RadixAttention matches at individual token boundaries. If two requests share 47 tokens, all 47 get reused. The tree splits nodes at the exact divergence point using a _split_node operation. No wasted partial blocks. No lost single tokens at block boundaries. The resolution is perfect.

Caches generated tokens too. This is the big one. When a model generates a response, those KV values stay in the tree. In multi-turn chat, the entire conversation history — system prompt, first user message, first assistant response, second user message — accumulates in the tree as a single path. The second turn doesn't recompute the first turn's KV cache. The third turn reuses both. Each continuation is just an extension of the existing path.

This changes the economics of multi-turn chat fundamentally. Consider a 10-turn conversation where each turn is ~100 tokens (user message + assistant response). With vLLM's prompt-only caching:

  • Turn 1: prefill 100 tokens (system prompt + user message). Cost: 100 tokens.
  • Turn 2: prefill 200 tokens (entire history up to now). Cost: 200 tokens.
  • Turn 3: prefill 300 tokens. Cost: 300 tokens.
  • Turn 10: prefill 1,000 tokens. Cost: 1,000 tokens.
  • Total prefill: 5,500 tokens. O(n^2) in conversation length.

With RadixAttention, every previous turn's KV cache stays in the tree:

  • Turn 1: prefill 100 tokens. Cost: 100 tokens.
  • Turn 2: cache hit for 100 tokens, prefill only the new 100. Cost: 100 tokens.
  • Turn 3: cache hit for 200 tokens, prefill 100. Cost: 100 tokens.
  • Turn 10: cache hit for 900 tokens, prefill 100. Cost: 100 tokens.
  • Total prefill: 1,000 tokens. O(n) in conversation length.

From 5,500 tokens of prefill to 1,000. That's a 5.5x reduction in compute for a 10-turn conversation, and the gap grows quadratically with conversation length. For a 50-turn conversation (common in coding assistants or customer support), the ratio is 25x.

Cache-aware scheduling. The scheduler doesn't process requests FIFO. It uses Longest Prefix Match (LPM): requests sharing longer prefixes with cached data get priority. With depth-first scheduling, the system processes the deepest branch of the radix tree first, keeping those KV caches hot in GPU memory. Related requests run back-to-back. Cache thrash drops. Hit rates climb.

Radix tree scheduling// Group pending requests by their terminal node in the radix tree
for node in radix_tree.leaves():
    node.weight = count(pending_requests_at(node))

// Propagate weights upward (child weights sum into parents)
for node in radix_tree.bottom_up():
    node.weight += sum(child.weight for child in node.children)

// Schedule depth-first: process heaviest branch first
// This keeps hot KV caches in memory, maximizing hits
schedule_order = radix_tree.dfs_by_weight()

The result: requests that share long prefixes run back-to-back, keeping those KV caches hot. If 50 users all start with the same system prompt, the scheduler runs them in sequence, reusing the cached system prompt for all 50. Without this, a FIFO scheduler might interleave them with unrelated requests, evicting the system prompt cache between hits.

The scheduling depth

The interplay between the radix tree and the scheduler deserves attention. In a naive FIFO scheduler, requests execute in arrival order. If User A sends Turn 1, then User B sends Turn 1, then User C sends Turn 1, the KV cache thrashes: each request loads a different conversation context, evicting the previous one. By the time User A sends Turn 2, their Turn 1 cache is long gone.

SGLang's depth-first scheduler reorders the queue. It groups pending requests by their position in the radix tree and processes the deepest (longest-prefix) matches first. If User A's Turn 1 is cached, User A's Turn 2 gets priority — it will reuse the most cached data. User B and User C wait slightly longer, but the total computation drops because the system avoids redundant prefill work.

This is the same insight behind disk elevator algorithms (process I/O requests in spatial order to minimize seek time) and CPU cache-aware scheduling (schedule threads that share data on the same core). The pattern: when your system has a cache, schedule to maximize cache hits, even if it means deviating from FIFO fairness. The throughput gain dwarfs the fairness cost.

In practice, SGLang's scheduler also handles a subtle case: in-batch prefix sharing. When multiple requests in the same batch share a prefix that isn't yet cached, the scheduler detects this by simulating the radix tree over the waiting queue. It runs the prefix-establishing request first, caches the result, then runs the dependent requests. This avoids the thundering-herd problem where 50 requests all try to compute the same system prompt simultaneously.

SGLang v0.4 extended this with a cache-aware load balancer for multi-GPU deployments. When requests arrive at a cluster of N GPUs, the load balancer checks which GPU is most likely to have the request's prefix cached. It routes accordingly. The result: 3.8x higher cache hit rates compared to round-robin routing, and 1.9x higher throughput. The insight is that load balancing itself is a caching problem — you want to route requests to the GPU where their data already lives, even at the cost of slight load imbalance.

This mirrors the NUMA-aware scheduling in modern operating systems, where the kernel schedules threads on the CPU socket closest to their data. Same principle: minimize data movement by scheduling computation near the cache.

The Filesystem Analogy

The radix tree is to KV caches what the filesystem is to disk. Path lookup = prefix matching. ls = cache enumeration. rm = LRU eviction. ln = reference-counted sharing. df = memory utilization. The same data structure, solving the same problem: how do you organize a hierarchy of named, variably-sized objects so that retrieval is fast, space is shared across overlapping paths, and eviction is graceful under pressure?

Deep detail: How the radix tree evolves during a conversation

State 1 (empty): Just the root node. No cached KV data. All computation starts fresh.

State 2 (first request): User A sends a message. The system prompt + user message + assistant response become a single edge from root. The KV cache for all these tokens is stored in GPU memory and linked from the tree node.

State 3 (shared prefix splits): User B sends a message with the same system prompt but a different question. The tree splits: the system prompt becomes a shared parent node (its KV cache is reused), and two children branch off — one for User A's path, one for User B's path.

State 4 (LRU eviction): Memory pressure. The system walks leaves in LRU order. User B hasn't sent a follow-up; their leaf node has the oldest access time. It gets evicted. Its KV cache is freed. The shared system prompt node survives because User A's branch still references it (ref count > 0).

State 5 (continuation extends): User A sends Turn 2. The system walks User A's existing branch (system prompt → turn 1 question → turn 1 answer) — all cached, all free. Only the new tokens need computation. The path extends deeper.

Why it happened

The rediscovery isn't a coincidence. It's structural.

GPUs became shared resources. When one model serves thousands of users, the GPU faces the same multiplexing problems that mainframes faced in the 1960s. Multiple processes competing for finite memory. Variable-length workloads requiring fair scheduling. Shared data structures needing copy-on-write semantics. Same problems. Same solutions. Sixty years apart.

Memory became the bottleneck. Just as 1960s machines were memory-constrained (leading to virtual memory), modern GPUs are VRAM-constrained (leading to PagedAttention). The KV cache is the new working set. It grows with context length, competes with model weights for the same HBM, and determines how many concurrent users you can serve. The constraint is identical; only the speed of the memory changed.

The abstraction gap. CUDA gives you raw memory allocation — cudaMalloc returns a pointer, and you manage everything yourself. There's no GPU "operating system" that handles paging, scheduling, or caching for you. ML engineers had to build one. And when you're building an OS from scratch, you inevitably rediscover the same abstractions the original OS builders discovered, because the problems are isomorphic.

Different tribes, same territory. OS researchers and ML researchers read different papers, attend different conferences, use different terminology. A "page fault" and "KV cache miss" describe the same event. A "context switch" and "request preemption" are the same operation. The rediscovery was almost inevitable because the knowledge was siloed. It took individuals who straddled both worlds — Berkeley PhD students who'd taken OS courses and were now building ML systems — to see the mapping.

The Deeper Lesson

Every generation of hardware eventually needs an operating system. The GPU's OS is being written right now, one systems paper at a time. The irony is that vLLM's page table is simpler than a real OS page table — no TLB, no multi-level hierarchy, no swap space to disk. Yet. Give it time. The GPU is where operating systems were in 1970, and it's speed-running the same evolutionary path that took CPUs fifty years. We already have paging, scheduling, and a filesystem abstraction. Swap space (KV cache offloading to CPU RAM or SSD) is arriving. Multi-level page tables will follow. The endpoint is predictable: a full GPU operating system. The question is only how many papers it takes to get there.

The supply-side story

There's one thread that runs through all four papers: they optimized the supply side. More requests per GPU. Better memory utilization. Higher throughput. Lower cost per token. The provider wins: serve more users, spend less on hardware. Orca packed the schedule. PagedAttention packed the memory. SGLang avoided redundant work. vAttention removed the software overhead.

The numbers are stunning. A serving stack built on continuous batching + PagedAttention + RadixAttention can serve 10–20x more users per GPU than the naive approach from 2022. That's the difference between a $10 million GPU bill and a $500,000 GPU bill for the same workload. Infrastructure papers don't win best paper awards, but they determine who can afford to deploy.

Consider the economics concretely. In early 2023, before these optimizations were widely deployed, serving a 70B model to 1,000 concurrent users required roughly 32 A100 GPUs. At cloud prices of ~$2.50/hour per GPU, that's $80/hour, or $700,000/year just for the inference fleet. Apply continuous batching (3x), PagedAttention (2.5x), and prefix caching (2x for typical workloads), and the same 1,000 users fit on 5–8 GPUs. The annual cost drops below $200,000. The delta — $500,000/year — funded by four systems papers.

This is why infrastructure matters more than architecture for deployment economics. A 2x better model that costs 10x more to serve loses to a 1.5x better model with 20x better serving efficiency. The models grab the headlines. The serving papers pay the bills.

But throughput is not latency

Every optimization in this article made the system more efficient. More users per GPU. More tokens per second per dollar. But for any individual user, the picture is more complicated.

Batching 64 requests together amortizes the cost per token beautifully. GPU utilization climbs. Cost plummets. But each individual user now shares the GPU with 63 others. Time-per-output-token increases. Your request must wait its turn in every forward pass. Queuing delay compounds. The system is more efficient overall, but you wait longer.

The provider is happy. The user is not.

This is the fundamental tension of shared infrastructure. Airlines maximize revenue per seat (throughput). Passengers care about how long they sit on the tarmac (latency). Highways maximize cars per hour (throughput). Drivers care about their commute time (latency). Every shared resource faces this tradeoff, and every optimization that improves one metric by sharing resources more aggressively makes the other metric worse for individuals.

In LLM serving, the tension is sharp. A batch of 64 requests uses the GPU 64x more efficiently than a single request. But each request's time-per-output-token increases because it shares every forward pass with 63 others. At batch size 1, a user gets undivided GPU attention: 50 tokens per second, text streaming fast enough to read in real time. At batch size 64, the same user might see 15–20 tokens per second. Still usable, but the experience changes. At batch size 256, latency crosses the threshold where users notice the lag. The text stutters. The illusion of real-time conversation breaks.

We've optimized memory. We've optimized scheduling. We've built a paging system, a filesystem, and argued about whether to use the hardware MMU or the software one. But latency — the time a single user waits for each token to appear on screen — is the one thing batching cannot fix. Continuous batching makes latency worse for individuals even as it makes throughput better for the fleet.

What if the model could guess its own future?

What if a small, fast draft model could race ahead, proposing five tokens at once, and the big model could verify them all in a single parallel pass? The verification is parallel (one forward pass checks all five). The generation is sequential (each token depends on the last). That asymmetry — parallel verification vs. sequential generation — is the same asymmetry that makes CPU speculative execution work. The same asymmetry that lets a proofreader check five paragraphs faster than a writer can compose one. And it's exploitable.
