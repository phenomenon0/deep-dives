CONTROL DECK

Hardware detection, first-boot installer, and a voice supervisor that refuses to stay dead. A deep dive into the orchestration layer of a desktop AI app that has to figure out what machine you're on before it can talk to you._

01 -- THE FIRST FIVE MINUTES

Most apps install in seconds. Control Deck takes five minutes on a good day — not because the code is slow, but because the code is downloading a 5 GB neural network the user did not ask for and probably did not know was coming. That moment, from the first window appearing to the moment the model says READY, is the entire game. Get it wrong and the app is a corpse on disk. Get it right and the user never opens a terminal in their life.

Every chapter in this dive orbits one question: who owns the decisions during that five minutes? Who picks the model. Who runs the installer. Who decides the smoke test failed. Who notices when the voice sidecar dies an hour later. The answer is not one component — it is a small, opinionated chain of them, each handing off to the next.

The chain, end to end 
// First boot, top to bottom:
layout.tsx    → renders <OnboardingGate /> inside the deck shell
OnboardingGate → GET /api/onboarding/state → redirect if !done
OnboardingFlow → GET /api/onboarding/probe → render hardware card
orchestrator   → detectSystem() + recommendTier() + 6 probes
recipe         → load platform yaml (linux/macos/windows)
orchestrator   → spawn install → pull model → smoke test
supervisor     → (electron, separate process) spawns voice-core
arbiter        → (in-process) reserves VRAM for every model load

Eight components. Three processes (the Next.js server, the Electron main, the Python voice-core sidecar). Two ports (3333 for the deck, 4245 for voice-core, 11434 for Ollama — three actually). One config file (inference-bindings.json) that survives reboots. One done flag (onboarding.done) that the gate consults on every load.

That is the territory. The rest of this article is the map.

THE CENTRAL TENSION

The user wants to open the app and talk to an AI. The reality is that no part of that stack — not the LLM, not the speech-to-text, not the speech synth — ships with the app. Control Deck has to install everything on first launch, on three operating systems, without admin rights it cannot demand, while showing live progress and recovering from failure modes the user does not know exist. This is the problem.

02 -- THE BACKEND DETECTIVE

DETECT → tier → gate → probe → install → pull → supervisor → arbiter

Before Control Deck picks a model, it has to figure out where it is. lib/system/detect.ts is the detective — 352 lines of execSync calls into nvidia-smi, system_profiler, and Get-CimInstance Win32_VideoController, each tuned to one OS and ready to swallow failure silently. The output is a SystemProfile, and every downstream decision feeds off it.

The shape is small enough to fit on a card:

lib/system/detect.tsexport interface SystemProfile {
  mode: DeckMode;            // "lite" | "power"
  gpu: GpuInfo | null;
  ram: number;               // GB
  cpuCores: number;
  cpuModel: string;
  isIntel: boolean;
  platform: NodeJS.Platform;
  backend: InferenceBackend;  // "metal" | "cuda" | "rocm" | "cpu"
  storage: StorageInfo | null; // freeGb / totalGb on $HOME
  recommended: { textModel: string; ... };
}

Three OSes, three shell-outs

The detective uses a different witness on every platform. None of them are perfect.

PlatformToolWhat it returnsFailure mode
Linuxnvidia-sminame, vram (MB)missing on non-NVIDIA boxes → null → CPU tier

The Mac path is the most interesting. Apple Silicon GPUs share memory with the CPU — there is no separate VRAM field. The detective spots this by the absence of sppci_vram in the JSON, then estimates the inference budget as 60% of system RAM:

detect.ts — detectMacGpuconst mbMatch = /(\d+)\s*MB/i.exec(vramStr);
const gbMatch = /(\d+)\s*GB/i.exec(vramStr);
if (mbMatch) vram = parseInt(mbMatch[1], 10);
else if (gbMatch) vram = parseInt(gbMatch[1], 10) * 1024;
else {
  // Apple Silicon path — unified memory. ~60% of RAM
  // leaves 40% for OS + app + context scratch.
  vram = Math.round((os.totalmem() / (1024 * 1024)) * 0.6);
  unifiedMemory = true;
}

That unifiedMemory flag is load-bearing. detectBackend() looks at exactly one thing on darwin: did detectMacGpu() set unifiedMemory: true? If yes, the backend is metal. If no, the backend is cpu — even when there is a discrete Radeon Pro 5500M sitting in the machine.

The Intel-Mac trap

This was a real bug. The original code said:

beforereturn gpu?.unifiedMemory ? "metal" : gpu ? "metal" : "cpu";

Read that nested ternary again. Any GPU on darwin returned metal, including the AMD discrete card in a 2019 MacBook Pro. The tier picker would then route the user to T1_MAC, which assumes the Apple Neural Engine. The ANE does not exist on Intel Macs. The whisper.cpp+CoreML stack would install a 1.6 GB model the user could not accelerate.

The fix is one character of code and an honest comment:

afterreturn gpu?.unifiedMemory ? "metal" : "cpu";
DESIGN RULE

The detective's job is not to find a GPU. It is to find a GPU the rest of the stack can use. A Radeon Pro 5500M is real silicon — but if no engine in the cascade targets it, claiming "metal" is a lie that becomes a 1.6 GB download.

The storage probe is the other quiet one. df -Pk "$HOME" returns POSIX-standard 6 columns on both darwin and linux; -P forces a single line even when the filesystem name is long. Windows gets no storage probe at all (the tier check just sees storage: null and skips the floor check). That is acceptable today, and a TODO tomorrow.

The detective hands a SystemProfile off to the tier picker. Next chapter: how the picker turns hardware into a model.

03 -- THREE TIERS, ONE LADDER

detect → TIER → gate → probe → install → pull → supervisor → arbiter

The tier file does something the rest of the codebase quietly depends on: it collapses the entire "what model should this person run?" problem into three named bundles. No menu. No dropdown of forty GGUFs. Three cards. Pick one. The user does not see what they did not pick.

The bundle shape:

lib/inference/hardware-tiers.tsexport interface TierBundle {
  id: TierId;          // "T1_MAC" | "T2_CUDA" | "T3_CPU"
  label: string;
  hardwareMatch: string; // "Apple Silicon · ≥16 GB unified memory"
  rationale: string;
  cascade: { stt; tts; llm };
  omni?: { engineId; sidecar; modelId; sizeMb };
  defaultPreset: "quick" | "balanced" | "quality";
  fits(input): number;  // 0..100 score, highest wins
}

Each tier ships a complete cascade — a STT → LLM → TTS pipeline chosen to be coherent on that class of hardware. T2_CUDA optionally ships an omni lane too (Qwen2.5-Omni 7B running on a separate sidecar) for speech-to-speech at lower latency. T3_CPU has no omni because end-to-end speech models do not run on CPU at conversational latency. The absence is part of the design.

TierSTTLLMTTSDisk
T1_MAC Whisper-turbo (CoreML) Qwen3 8B Kokoro 82M ~7.1 GB
T2_CUDA Parakeet TDT 0.6B Qwen3.5 9B Q4_K_M Kokoro 82M ~8.2 GB
T3_CPU sherpa Zipformer Llama 3.2 3B Kokoro 82M ~2.7 GB

Notice Kokoro 82M is on every tier. That is a deliberate floor: even the CPU tier gets a natural-sounding voice. The cost is 330 MB and a slightly slower first-chunk time on CPU. The alternative — gating "good voice" behind a GPU — would mean every CPU user gets a robot reading their messages. Not happening.

How fits() scores

Each tier carries its own predicate. recommendTier() runs all three, picks the highest, breaks ties Mac > CUDA > CPU. The predicates are deliberately small:

hardware-tiers.ts — T1_MAC.fitsfits({ backend, ramGb }) {
  if (backend === "metal" && ramGb >= 14) return 100;
  if (backend === "metal") return 60;  // 8 GB Mac — works but tight
  return 0;
}

// T2_CUDA.fits scales by VRAM tier:
fits({ backend, gpu }) {
  if (backend !== "cuda" || !gpu) return 0;
  if (gpu.vram >= 12000) return 100;
  if (gpu.vram >= 8000)  return 70;  // 8 GB still runs cascade fine
  return 30;
}

// T3_CPU.fits is the catch-all:
fits({ backend, gpu, ramGb }) {
  if (ramGb < 8) return 0;
  if (backend === "cpu") return 100;
  if (gpu && gpu.vram < 4000) return 80;
  return 20;
}

The tie-break order matters. A 16 GB Apple Silicon machine scores T1_MAC: 100, T3_CPU: 20 — clear win. A 12 GB RTX 4070 scores T2_CUDA: 100. A 16 GB Intel-based ThinkPad with no GPU scores T3_CPU: 100. A 32 GB Threadripper with a 3 GB Quadro K2200 scores T3_CPU: 80 (the GPU is too small to be useful, RAM saves it).

WHY THIS IS WILD

Three numbers. 0, 60-80, 100. That is the entire ranking system. Most "ML model selector" UIs have benchmark tables, latency budgets, quality scores, sliders. Control Deck has a 100. The bet is that hardware is bimodal — you either have the silicon or you don't — and the middle ground is small enough to live in tiebreaks.

One test guards this whole chapter. After the Intel-Mac fix, a unit test pins the expectation that a discrete-GPU Mac scores zero on T1_MAC and falls to T3_CPU. Without it, a future "let's support Metal Performance Shaders on Intel" pull request would silently re-break onboarding.

hardware-tiers.test.tsit("routes Intel Macs to T3_CPU", () => {
  const r = recommendTier({
    backend: "cpu",
    gpu: { name: "AMD Radeon Pro 5500M", vram: 4096, unifiedMemory: false },
    ramGb: 16,
  });
  expect(r.best).toBe("T3_CPU");
  expect(r.scores.T1_MAC).toBe(0);
});

The detective decides what the hardware is. The tier picker decides what to do about it. The next component decides whether to bother the user about any of it.

04 -- THE GATE

detect → tier → GATE → probe → install → pull → supervisor → arbiter

The gate is sixty-three lines and it is the only thing standing between a user and a broken app. Every render of the deck shell passes through it. If onboarding has never run, you go to onboarding. If it ran but Ollama is dead, you also go to onboarding. The rest of the time, the gate returns null and disappears.

The whole control flow:

components/onboarding/OnboardingGate.tsxconst FLAG_KEY = "control-deck.onboarding.done";

export function OnboardingGate() {
  const router = useRouter();
  const pathname = usePathname();

  useEffect(() => {
    if (pathname?.startsWith("/deck/onboarding")) return;

    const cached = window.localStorage.getItem(FLAG_KEY);
    if (cached === "1") return;  // fast path

    let cancelled = false;
    (async () => {
      const r = await fetch("/api/onboarding/state", { cache: "no-store" });
      const data = await r.json();
      if (cancelled) return;

      // "done but broken" — route back to onboarding
      if (data.done && data.ollamaHealthy === false) {
        window.localStorage.removeItem(FLAG_KEY);
        router.replace("/deck/onboarding");
        return;
      }
      if (data.done) window.localStorage.setItem(FLAG_KEY, "1");
      else { localStorage.removeItem(FLAG_KEY); router.replace("/deck/onboarding"); }
    })();
    return () => { cancelled = true; };
  }, [pathname, router]);
  return null;
}

Two sources of truth, in tension

The gate believes two things. localStorage is a cached client hint: a single string "1" at control-deck.onboarding.done. The server flag is a JSON file on disk at the platform-correct state dir — LOCALAPPDATA on Windows, ~/Library/Application Support on macOS, $XDG_STATE_HOME on Linux.

orchestrator.ts — defaultStateDirfunction defaultStateDir(): string {
  if (process.platform === "win32") {
    const base = process.env.LOCALAPPDATA ?? join(homedir(), "AppData", "Local");
    return join(base, "ControlDeck", "state");
  }
  if (process.platform === "darwin") {
    return join(homedir(), "Library", "Application Support", "ControlDeck", "state");
  }
  const xdg = process.env.XDG_STATE_HOME ?? join(homedir(), ".local", "state");
  return join(xdg, "control-deck");
}

The server flag is the source of truth. localStorage is a 0-RTT optimization for the common case — "user opens app for the 47th time, onboarding done long ago, do not even bother fetching." Hit the cache, return early, never block paint.

But the cache lies the moment Ollama dies. Hence the third state:

"Done but broken"

This is the most interesting branch in the file. The gate's server-side check does not just ask "did onboarding finish?" — it asks "did onboarding finish, AND is the stack still alive right now?". The state endpoint does a live probe:

orchestrator.ts — readDoneStateexport async function readDoneState() {
  if (!existsSync(DONE_FLAG)) return { done: false };
  let stored: { tier?; completedAt? } = {};
  try { stored = JSON.parse(await readFile(DONE_FLAG, "utf8")); }
  catch { /* leave empty; we still know it's done */ }
  const ollamaHealthy = await probeOllamaService();
  return { done: true, ...stored, ollamaHealthy };
}

If done: true but ollamaHealthy: false — the user finished onboarding last week but the Ollama service died, the port was hijacked, the systemd unit was removed — the gate clears the localStorage hint and re-routes to onboarding. The user sees a fresh probe with the missing pieces highlighted. They click "Get me running" again and the orchestrator skips everything that's still installed, fixes only what broke.

THE IDEMPOTENCY DIVIDEND

Because every step in the orchestrator is idempotent — missing.ollama is false if ollama is on PATH, regardless of how it got there — the same flow that runs a fresh install also runs a recovery. The gate doesn't need a "repair mode." It just routes back to the same screen and lets the probe figure out what's broken.

The deck shell helps. When the gate redirects to /deck/onboarding, the DeckShell short-circuits its own chrome:

components/DeckShell.tsx// Onboarding is a first-run takeover — render the flow naked, no chrome.
if (pathname?.startsWith("/deck/onboarding")) {
  return <>{children}</>;
}

No sidebar. No chat threads. No settings drawer. Just the installer card, centered. The user is on rails until the smoke test passes.

05 -- THE PROBE

detect → tier → gate → PROBE → install → pull → supervisor → arbiter

The probe is read-only by design. It is the orchestrator's audit pass: nothing it does mutates the system, every check has a 1.5–2 second timeout, and the whole thing returns in well under a second on a happy box. GET /api/onboarding/probe can be called repeatedly, and the onboarding page does — once on mount, again whenever the user clicks "I've installed it — check again."

The body of the probe is one Promise.all:

orchestrator.ts — probeOnboardingWithconst [ollamaPresent, ollamaService, llmModel, voiceCoreHealth, ollamaVersion] =
  await Promise.all([
    binaryOnPath("ollama"),       // walks $PATH, checks X_OK
    probeOllamaService(),         // GET 127.0.0.1:11434/api/tags
    probeLlmModel(tier.cascade.llm.id), // scans /api/tags result
    probeVoiceCore(),             // GET 127.0.0.1:4245/health
    probeOllamaVersion(),         // GET 127.0.0.1:11434/api/version
  ]);

Five parallel checks. Each one has its own timeout (1.5–2 seconds via AbortSignal.timeout). Failure is the empty case, not an exception — every probe function returns a boolean or empty record on any error. fetch rejection? false. JSON parse failure? false. Timeout? false.

The portable PATH walker

The probe never calls which or where. Both might not be installed (Alpine doesn't ship which in the busybox-default image; Windows containers don't always have where). Instead it walks process.env.PATH by hand:

orchestrator.ts — binaryOnPathasync function binaryOnPath(bin: string): Promise<boolean> {
  const sep = process.platform === "win32" ? ";" : ":";
  const env = augmentedEnv();
  const dirs = (env.PATH ?? "").split(sep).filter(Boolean);
  const exts = process.platform === "win32"
    ? (process.env.PATHEXT ?? ".COM;.EXE;.BAT;.CMD").split(";")
    : [""];
  for (const dir of dirs) {
    for (const ext of exts) {
      try {
        await access(join(dir, bin + ext), fsConstants.X_OK);
        return true;
      } catch { /* keep looking */ }
    }
  }
  return false;
}

The augmentedEnv() call is the secret sauce. Electron on macOS inherits PATH from launchd, which does not include /opt/homebrew/bin. A user can have Homebrew installed and the deck still can't see brew. augmentedEnv() prepends the standard install prefixes for each platform:

orchestrator.ts — augmentedEnvconst extras: string[] = [];
if (process.platform === "darwin") {
  extras.push("/opt/homebrew/bin", "/usr/local/bin");
} else if (process.platform === "linux") {
  extras.push("/usr/local/bin");
}
const sep = process.platform === "win32" ? ";" : ":";
const existing = (process.env.PATH ?? "").split(sep).filter(Boolean);

The shape that comes back

The probe ships a ProbeResult the UI uses to draw three things: the hardware card, the missing checklist, and the consent panel (if relevant).

orchestrator.ts — ProbeResultinterface ProbeResult {
  hardware: { backend, gpu, ramGb };
  tier: TierId;
  tierLabel: string;
  diskMb: number;
  llm, stt, tts: { id; sizeMb; runner? };
  missing: {

Six boolean flags. Each flag binds to one row in the "What's needed" checklist. Each row toggles between ○ and ✓ depending on the flag. The user sees the system's mental model.

THE READ-ONLY GUARANTEE

Nothing in the probe writes a file, spawns a process, or installs anything. It can be called from a stale tab, a background poll, a Playwright test, or a curl from the terminal. Every check is a network round-trip or a filesystem stat. That guarantee is what makes the consent UX possible — the user clicks "Show what will run" and can read the install command before authorizing anything.

One more probe is worth pulling out. firstMissingDependency() checks not just whether the install command is on PATH (brew, winget, pkexec) but also any pipeline tools it shells through — curl on Linux, powershell on Windows. If any of them are missing, the probe sets autoInstallable: false, and the UI flips from a consent checkbox to a "Download Ollama" link card. There is no point showing a checkbox we can't honor.

06 -- THE RECIPE

detect → tier → gate → RECIPE → install → pull → supervisor → arbiter

Three operating systems. Three installers. pkexec + install.sh on Linux. brew install ollama on macOS. winget install --exact --id Ollama.Ollama on Windows. The orchestrator does not branch on platform with a giant if. It loads a YAML file.

The shape:

Why YAML, why declarative

Could this be a TypeScript switch? Yes. Would that be better? No. The YAML lets the consent strings live next to the command they describe, in the same file, in the same language as the install. When a future maintainer wants to change the Windows install to a Chocolatey package, they edit one file. No code change. No test breakage. The orchestrator just reads whatever's in windows.yaml and runs it.

The loader is strict. Every required field is validated at parse time, with the path to the offending file in the error:

recipe.ts — validateCommandfunction validateCommand(value, where) {
  if (!isObject(value)) throw new Error(`${where}: must be an object`);
  const bin = value.bin;
  const args = value.args;
  if (typeof bin !== "string") throw new Error(`${where}.bin: must be a string`);
  if (!Array.isArray(args) || !args.every((a) => typeof a === "string")) {
    throw new Error(`${where}.args: must be a string[]`);
  }
  return { bin, args, detach: value.detach === true, ... };
}

The loader fails loud at boot, not midway through a five-minute install. If you ship a malformed windows.yaml, the deck won't start — you get a clear stack trace pointing at .../windows.yaml: ollama.install.command.args: must be a string[]. That is the right place to fail.

Anchoring to the file, not the cwd

One subtle gotcha. The recipe directory is resolved relative to the module, not process.cwd():

recipe.tsconst RECIPE_DIR = join(dirname(fileURLToPath(import.meta.url)), "recipes");

This matters for packaged Electron. When the app is bundled, process.cwd() is wherever the user launched it from — could be ~/Desktop, could be C:\Users\...\Downloads. import.meta.url always points at the JS file's actual location, which lives inside the app bundle. Recipes ship with the code.

The bundling guarantee was a real bug, caught the day this article was written. Next.js's standalone tracer doesn't follow dynamic readFileSync paths, so the YAMLs would not have been included in .next/standalone/ without explicit help:

next.config.tsoutputFileTracingIncludes: {
  "/api/onboarding/**/*": ["./lib/onboarding/recipes/*.yaml"],
},

Without that one entry, a Windows user installing from a packaged build would have hit "no install recipe for this platform" because windows.yaml wasn't in the bundle.

THE BUNDLER TAX

Any file your code reads at runtime that the bundler can't see through a static import becomes a deployment hazard. readFileSync(import.meta.url + "/foo.yaml") works in dev because dev runs against source. It silently breaks in prod when the tracer skips it. The cure: explicit outputFileTracingIncludes — or, better, embed the YAML at build time. We chose the former because adding a new recipe is a one-file change.

07 -- THE INSTALL

detect → tier → gate → probe → INSTALL → pull → supervisor → arbiter

The install step is the only one that mutates the user's machine. Everything before it is read-only. Everything after it depends on it working. It is one spawn() call surrounded by half a dozen pre-flight checks that exist because every one of them has, at some point, failed silently.

Before we even spawn:

  1. Consent gate. If consents.installOllama !== true, fail with a clear "tick the consent box or run manually" message.
  2. Graphical session check. On Linux, if the command uses pkexec and there's no DISPLAY or WAYLAND_DISPLAY, fail — pkexec needs a polkit agent.
  3. Unsupported-distro check. NixOS (immutable FHS) and Alpine (musl libc) both break Ollama's install.sh; we detect and abort with a useful message.
  4. Dependency PATH walk. firstMissingDependency() checks every binary in the pipeline — pkexec, curl, brew, winget.

Then we spawn, and stream lines into the UI:

orchestrator.ts — streamChildasync function* streamChild(cmd: CommandSpec) {
  const child = spawn(cmd.bin, cmd.args, {
    stdio: ["ignore", "pipe", "pipe"],
    env: augmentedEnv(),
    windowsHide: true,
  });
  const queue: ChildLine[] = [];
  let resolveNext: (() => void) | null = null;
  // ... line-buffered pipe from stdout + stderr ...
  const timer = setTimeout(() => {
    child.kill("SIGTERM");
    setTimeout(() => child.kill("SIGKILL"), 2000).unref();
  }, cmd.timeout_ms ?? 300_000);
  // ... yield each line; final yield is the exit event ...
}

An async generator yielding one line per \n. The route handler upstream takes those lines, wraps each in an SSE event, sends them down to the browser, the UI throttles to 300 ms and updates the step row's detail field. The user sees live curl: (22) The requested URL returned error: 503 instead of a spinner.

    detail: userCancelled
      ? "Installation cancelled — click Retry when you're ready..."
      : `${recipe.ollama.install.command.bin} exited ${line.code}...`,
  });
}

A user clicking "cancel" on the system password prompt is not an error. It is a choice. The orchestrator distinguishes pkexec's "user dismissed me" exit (126) from real failure (anything else) and writes a different message. "Installation cancelled — click Retry when you're ready, or untick the consent box to install manually."

Windows PATH refresh

The most platform-specific moment in the whole orchestrator. When the Ollama Windows installer writes ollama.exe to disk, it adds the install directory to the user's PATH via the registry — specifically HKCU\Environment\Path. But this process, the running Next.js server, started before the install ran and snapshotted process.env.PATH at startup. To the orchestrator, the new ollama.exe doesn't exist.

The fix is a quick powershell call:

orchestrator.ts — refreshWindowsPathasync function refreshWindowsPath() {
  if (process.platform !== "win32") return;
  await new Promise<void>((resolve) => {
    const child = spawn("powershell", [
      "-NoProfile",
      "-Command",
      "[Environment]::GetEnvironmentVariable('Path','User') + ';' +
       [Environment]::GetEnvironmentVariable('Path','Machine')",
    ], { stdio: ["ignore", "pipe", "ignore"], windowsHide: true });
    // ... capture stdout, set process.env.PATH = merged ...
  });
}

This runs immediately after the install succeeds. The verify step (ollama --version) then finds the freshly-installed binary because we have the new PATH in memory.

PLATFORM TAX

Half the code in the orchestrator is platform tax. Refreshing Windows PATH. Adding /opt/homebrew/bin for macOS. Detecting Wayland vs X11. Distinguishing pkexec exit 126 from real failure. None of this is interesting work. All of it is necessary. The interesting work — pulling the model, smoke-testing it — is the part you can write once and have it just work.

One more thing the install step does: emit a warning when it falls back to ollama serve in detached mode. On Linux without a systemd unit, on Windows where the installer ships a tray app instead of a service, "ollama serve" gets spawned with detached: true and stdio: "ignore". It runs until the user reboots. The orchestrator surfaces this explicitly: "spawned ollama serve (detached) — won't survive reboot; install a systemd unit to make it permanent." Honest about its limits.

08 -- THE PULL AND THE SMOKE

detect → tier → gate → probe → install → PULL → supervisor → arbiter

The pull is the slow step. It is also the one most likely to die in the middle. A 5 GB LLM, a coffee-shop wifi, a laptop lid that closes — every one of those breaks the stream. Ollama is forgiving (the partial cache resumes on retry), but the orchestrator still has to detect the failure and tell the user something other than "tab is wedged."

The pull request is one POST and a streaming response:

orchestrator.ts — pullOllamaModelresp = await fetch(`${OLLAMA_URL}/api/pull`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: modelId, stream: true }),
});

The response body is newline-delimited JSON. Each line is a status event:

ollama /api/pull stream{"status":"pulling manifest"}
{"status":"downloading","digest":"sha256:...","total":5247483904,"completed":12582912}
{"status":"downloading","total":5247483904,"completed":25165824}
... // hundreds of these per second
{"status":"verifying sha256 digest"}
{"status":"writing manifest"}
{"status":"success"}

Throttling because Ollama is enthusiastic

Ollama can emit hundreds of progress lines per second. The orchestrator throttles to one UI emit every 300 ms (configurable via the recipe's pull.throttle_ms):

orchestrator.ts — pull loopfor await (const evt of pullOllamaModel(tier.cascade.llm.id)) {
  const now = Date.now();
  if (evt.status === "running" && now - lastEmitted < throttleMs) continue;
  lastEmitted = now;
  yield stamp({ ... progress, detail });
}

The progress field is a 0..1 fraction (completed / total). The UI translates it into a green bar that grows under the step row. Every 300 ms the bar advances. Every 300 ms the user sees the download is alive.

The "clean close, no model" trap

Streams can close cleanly without delivering {"status":"success"}. A TCP drop mid-stream, a flaky CDN, a laptop sleep that drops the socket — all of these end the loop without an error and without a success marker. The orchestrator catches this by re-probing after the loop:

orchestrator.ts// The pull stream can close cleanly without emitting `status:success`
// (e.g. TCP drop on a flaky connection). Don't trust the stream alone —
// re-probe /api/tags before claiming the model is present.
if (!sawSuccess) {
  const verified = await probeLlmModel(tier.cascade.llm.id);
  if (!verified) {
    yield stamp({
      id: "pull-llm",
      status: "failed",
      detail: "Pull stream ended before the model arrived — likely a network drop.
        Click Retry; ollama keeps the partial cache so it'll resume.",
    });
    return;
  }
}

Two sources of truth, again. The stream and the tag list. If they disagree, the tag list wins.

Disk-full is a special case

Ollama emits a plain error string when the pull fails on ENOSPC. The orchestrator pattern-matches and rewrites the message:

orchestrator.tsif (j.error) {
  const friendly = /no space left|enospc/i.test(j.error)
    ? `Your disk is full — free up space and retry (ollama keeps the partial
       cache, so retry resumes). Raw: ${j.error}`
    : j.error;
  yield { status: "failed", detail: friendly };
  return;
}

That's all it takes. One regex. The user sees a sentence instead of llm/server.go:421: error pulling: open /home/.../sha256-abc...: no space left on device.

The smoke test, and why it gets a bigger timeout on CPU

Once the model is on disk, we have to verify it actually works. The smoke test is one /api/generate call:

orchestrator.ts — smokeTestLlmconst r = await fetch(`${OLLAMA_URL}/api/generate`, {
  method: "POST",
  body: JSON.stringify({
    model: modelId,
    prompt: "Say the word READY and nothing else.",
    stream: false,
    think: false,
    options: { num_predict: 64, temperature: 0 },
  }),
  signal: AbortSignal.timeout(cfg.timeout_ms),
});

The first inference on a fresh model is the slow one. Ollama has to mmap the GGUF, page in the weights, warm the GPU kernels. On a Mac M2 with the 5 GB Qwen3 8B, this takes 6–8 seconds. On a CPU-only laptop with a 4 GB GGUF, it takes 90–180 seconds.

The orchestrator knows this. It bumps the timeout on CPU:

orchestrator.tsconst smokeCfg = recipe?.smoke ? { ...recipe.smoke } : undefined;
if (smokeCfg && probe.hardware.backend === "cpu") {
  smokeCfg.timeout_ms = Math.max(smokeCfg.timeout_ms, 180_000);
}

The recipe says 60 seconds. CPU says at least three minutes. The user on a CPU box sees a "Smoke-test the LLM" row that sits in "running" for two minutes — and the 45-second-no-progress stall banner kicks in to reassure them. The text on the banner says "The install may still be running on the server — keep this tab open."

THE 45-SECOND BANNER

The SSE stream sends a heartbeat comment (: heartbeat {ts}) every 15 seconds. The browser client resets a 45-second "stall" timer on any incoming data. If 45 seconds pass with nothing — even a heartbeat — the UI assumes the socket wedged and shows a banner. The user keeps the tab open. The orchestrator keeps cooking. Everybody wins.

And then, finally: markDone(tier). The done flag is written to disk. localStorage is set. The Skip button is no longer offered. The UI shows "Ready in 287.3 s — open Chat to start talking" and 1.2 seconds later replaces the URL with /deck/chat.

The user has never seen a terminal.

09 -- THE SUPERVISOR

detect → tier → gate → probe → install → pull → SUPERVISOR → arbiter

The Ollama service runs itself. The voice-core sidecar does not. It is a Python process that hosts whisper.cpp + CoreML + Kokoro + Parakeet + sherpa-onnx, depending on the tier — and it lives or dies on whether Electron remembers to start it. The voice-core supervisor is 292 lines of "make sure the sidecar is up, and if it dies, restart it three times before giving up."

The supervisor lives in Electron main, not Next.js. It runs once at app.whenReady(), holds a reference to the child process, and tears it down on app.before-quit. The state is module-scoped:

electron/services/voice-core-supervisor.tsconst RESTART_MAX = 3;
const RESTART_WINDOW_MS = 5 * 60 * 1000;
const RESTART_DELAY_MS = 2_000;

let proc: ChildProcess | null = null;
let restarts: number[] = [];   // timestamps within current window
let isShuttingDown = false;
let gaveUp = false;
let lastExit: { code; signal; at } | null = null;

The startup ladder

The supervisor decides how to run voice-core based on what's available, in priority order:

  1. uv run --directory apps/voice-core voice-core serve — if uv is on PATH. This is the preferred path because uv handles the Python environment for us.
  2. Project-local .venv-voice-core/{bin,Scripts}/python -m voice_core — if the user (or onboarding) pre-built the venv.
  3. System python3 (or python.exe on Windows) — only useful if the user pip-installed the package globally. Mostly for debugging.
voice-core-supervisor.ts — planSpawnconst uvBin = which("uv");
if (uvBin) {
  return { command: uvBin, args: ["run", "--directory", voiceCoreDir, "voice-core", ...serveArgs] };
}
const venvPython = process.platform === "win32"
  ? path.join(root, ".venv-voice-core", "Scripts", "python.exe")
  : path.join(root, ".venv-voice-core", "bin", "python");
if (fs.existsSync(venvPython)) {
  return { command: venvPython, args: ["-m", "voice_core", ...serveArgs] };
}

Each plan is platform-aware. Linux/macOS use bin/python; Windows uses Scripts\python.exe. The supervisor never assumes a specific Python version — it shells out to whatever ladder rung found a working interpreter.

The port-listen probe

Before spawning, the supervisor checks if port 4245 is already listening. If the user started voice-core manually in another terminal — or if a previous Electron run crashed without cleaning up its detached child — we don't want two sidecars fighting for the same port:

voice-core-supervisor.ts — isPortListeningfunction isPortListening(port, host): Promise<boolean> {
  return new Promise((resolve) => {
    const socket = new net.Socket();
    socket.setTimeout(400);
    socket.once("connect", () => { socket.destroy(); resolve(true); });
    socket.once("timeout", () => { socket.destroy(); resolve(false); });
    socket.once("error", () => { socket.destroy(); resolve(false); });
    socket.connect(port, host);
  });
}

One TCP connect attempt, 400 ms timeout. If we connect, the port is taken — we assume the existing instance and bail. If we get a "connection refused" error, the port is free.

The restart budget

This is the supervisor's actual job. Voice-core can die for a hundred reasons — CUDA OOM, missing CoreML model, a Python import error in a fresh whisper.cpp build. The supervisor's rule: three restarts in five minutes, then stop.

voice-core-supervisor.ts — launch (exit handler)child.on("exit", (code, signal) => {
  proc = null;
  if (signal === "SIGTERM" || isShuttingDown) return;  // our doing
  console.warn(`[voice-core] exited code=${code} signal=${signal}`);
  lastExit = { code, signal, at: Date.now() };

  const now = Date.now();
  restarts = restarts.filter((t) => now - t < RESTART_WINDOW_MS);
  if (restarts.length >= RESTART_MAX) {
    gaveUp = true;
    console.error(`[voice-core] giving up after ${RESTART_MAX} restarts...`);
    return;
  }
  restarts.push(now);
  setTimeout(() => {
    const tierNow = readPersistedTier();
    if (tierNow) launch(host, port, tierNow);
  }, RESTART_DELAY_MS);
});

The window slides. Three deaths spread across an hour are tolerated — they're noise. Three deaths in 90 seconds is a crash loop. The supervisor stops. The gaveUp flag flips to true. The UI sees this via the IPC bridge.

The IPC bridge

Until this commit, the supervisor was opaque. You couldn't ask it "are you running?" from the renderer. Now it exposes two IPC channels:

electron/main.tsipcMain.handle("voice-core:state", () => {
  if (!voiceCoreService?.getState) return { available: false } as const;
  return { available: true, ...voiceCoreService.getState() };
});

ipcMain.handle("voice-core:restart", () => {
  if (!voiceCoreService?.restart) return { available: false } as const;
  return { available: true, ...voiceCoreService.restart() };
});

The preload script whitelists those channels:

electron/preload.tsconst ALLOWED_INVOKE_CHANNELS = new Set<string>([
  ...
  "voice-core:state",
  "voice-core:restart",
]);

And the settings drawer (or the onboarding "voice broken" branch) can now:

const { available, gaveUp, lastExit, running } =
  await window.electronAPI.invoke("voice-core:state");

if (gaveUp) {
  // Show a "voice broken — try again" button
  await window.electronAPI.invoke("voice-core:restart");
}

The restart() method clears the give-up state, resets the restart history, kills the existing child (if any), and re-launches. It is the operator-initiated reset. The user gets one button. They don't have to relaunch the app.

THE THREE-IN-FIVE RULE

Restart budgets are a mature pattern: systemd's StartLimitIntervalSec, kubelet's CrashLoopBackOff, supervisord's startretries. The number "3 in 5 minutes" is not magic — it is enough to swallow transient hiccups (a Hugging Face mirror flake, an OOM during model load that the next retry happens to fit) without burning CPU on a permanent crash loop.

One subtlety. The supervisor re-reads inference-bindings.json on every restart attempt:

const tierNow = readPersistedTier();
if (tierNow) launch(host, port, tierNow);

Why? Because onboarding might have just changed the tier between restarts. If the first crash happened on T2_CUDA (CUDA OOM on Parakeet) and onboarding then downgraded the user to T3_CPU, the next launch picks up the new tier from disk. No relaunch needed.

10 -- THE ARBITER

detect → tier → gate → probe → install → pull → supervisor → ARBITER

Every byte of VRAM on this machine is contended. Ollama wants 5 GB for the LLM. ComfyUI wants 8 GB for SDXL. Parakeet wants 1.5 GB for ASR. A 12 GB RTX 4070 cannot host all of them simultaneously — not even close. The arbiter is the thing that decides who gets the GPU, and who has to wait.

It is the most opinionated file in the codebase. Six hundred lines. One global mutex on globalThis. A lane policy table that reads like a hierarchy chart. A restore queue that brings your chat model back after you finish rendering a video.

Lanes, not models

The arbiter doesn't think about models. It thinks about lanes:

lib/resource/types.ts (referenced)type LaneId =
  | "chat"      // LLM via Ollama / llama-server
  | "vision"    // VLM — usually shares chat
  | "tts"       // Kokoro / Chatterbox
  | "stt"       // Whisper / Parakeet / Moonshine
  | "image"     // ComfyUI SDXL workflow
  | "audio"     // Stable Audio
  | "3d"        // Hunyuan 3D
  | "video"     // big video model
  | "omni";     // speech-to-speech replaces chat+vision+tts+stt

Every model is mapped to one lane. Acquiring a lane reserves an estimated VRAM amount with a UUID ticket. Releasing the ticket frees the reservation. The arbiter never knows the model. It knows the lane and the estimate.

The eviction policy table

This is the heart of the file. EVICTABLE_BY[req.lane] lists which lanes can be evicted to make room for req.lane:

arbiter.ts — EVICTABLE_BYconst EVICTABLE_BY: Record<LaneId, ReadonlySet<LaneId>> = {
  chat:   new Set(["chat"]),                              // chat doesn't evict others
  vision: new Set(["vision"]),
  tts:    new Set(["tts"]),
  stt:    new Set(["stt"]),
  image:  new Set(["image", "audio", "3d", "video"]),
  audio:  new Set(["image", "audio", "3d", "video"]),
  "3d":   new Set(["image", "audio", "3d", "chat", "vision"]),
  video:  new Set(["image", "audio", "3d", "video", "chat", "vision"]),
  omni:   new Set(["chat", "vision", "tts", "stt", "omni"]),
};

Read it as a hierarchy. Chat doesn't evict anything — it waits or fails. Image and audio evict each other and the heavy media lanes, but not voice. 3D and video are big enough that they kick chat out. Omni is the special case — it replaces the whole voice stack, so it evicts chat+vision+tts+stt as a unit.

The policy is asymmetric. A video render says "yes, kick everything." A chat request says "I'll wait." A speech-to-speech omni model says "I am the voice stack now."

Restore-on-idle

The trick that makes the whole thing user-friendly. When the arbiter evicts a chat model to make room for a video render, it pushes the chat reservation onto a restore queue:

arbiter.ts — evictif (victim.restoreOnIdle) {
  restoreQueue.unshift({
    lane: victim.lane,
    estimateMb: victim.estimateMb,
    reason: victim.reason,
    modelId: victim.modelId,
    evictedAt: Date.now(),
  });
  emit({ kind: "restore-scheduled", at: Date.now(), lane: victim.lane, modelId: victim.modelId });
}

When the video render finishes (release fires), maybeRestore() runs:

arbiter.ts — maybeRestoreasync function maybeRestore() {
  if (restoreQueue.length === 0) return;
  await refreshSnapshot();
  const snap = getSnapshot();
  // Skip restore if any heavy lane is still active.
  for (const r of reservations.values()) {
    if (r.lane === "3d" || r.lane === "video" ||
        r.lane === "image" || r.lane === "audio") return;
  }
  const next = restoreQueue[0];
  if (snap.freeMb < next.estimateMb + snap.reserveMb + RESTORE_HEADROOM_MB) return;
  restoreQueue.shift();
  // Best-effort silent re-acquire.
  await acquire({
    lane: next.lane, estimateMb: next.estimateMb,
    reason: `restore: ${next.reason}`,
    evicts: "none", restoreOnIdle: true, priority: "background",
  });
}

The user finishes their video. The arbiter notices the GPU is idle. The chat model lazy-loads back without anyone asking. The next time the user types a message, it's already warm.

Downgrade swap

The wildest pattern in the file. When a video render needs to evict a 9 GB chat model, the arbiter can perform a downgrade swap — unload the big model, load a 3 GB version of the same model on the same lane, and queue the original for restore:

arbiter.ts — evict (swap branch)if (victim.swapTo) {
  const unloaded = await doUnload(victim.lane, victim.modelId);
  if (unloaded.ok) {
    // Insert a fresh reservation for the swap target.
    reservations.set(swapTicket, {
      ticket: swapTicket, lane: victim.lane,
      estimateMb: victim.swapTo.estimateMb,
      reason: `downgrade for ${reason}`,
      modelId: victim.swapTo.modelId,
      restoreOnIdle: false,  // the *original* is what we want back
      ...
    });
    if (victim.restoreOnIdle) {
      restoreQueue.unshift({
        lane: victim.lane, estimateMb: victim.estimateMb,
        modelId: victim.modelId, replacesTicket: swapTicket,
      });
    }
    emit({ kind: "downgrade-swap", ... });
    return;
  }
}

The user gets a smaller, dumber chat model while their video renders. When the video finishes, the smaller model is unloaded and the original 9 GB model lazy-loads back. Chat keeps working through the eviction. That's the design goal: never go silent.

SMALLER WHILE BUSY

This is the pattern that makes co-located generation feel possible on a 12 GB card. You don't choose between "render a video" and "have a chat." The arbiter chooses for you — render gets the budget, chat gets a smaller shape, and the moment the GPU is free again, your preferred model is back. The user never knows the swap happened unless they're staring at the resource pane.

One more rule that keeps the arbiter sane. The state pins to globalThis:

arbiter.ts — getStateconst STATE_KEY = "__controlDeckArbiterState";
function getState(): ArbiterState {
  const g = globalThis as unknown as Record<string, ArbiterState | undefined>;
  if (!g[STATE_KEY]) { g[STATE_KEY] = { reservations: new Map(), ... }; }
  return g[STATE_KEY]!;
}

Why globalThis? Because Next.js dev HMR throws away module bindings every time a file changes. Without this hack, every code reload would wipe your reservations and the next acquire would think the GPU was empty — while ollama was still sitting on 5 GB. Pinning to globalThis survives HMR.

What "supervisor takes over" actually means

On first boot, the orchestrator's provisionVoiceCore() spawned voice-core detached. That sidecar lives until the user reboots — nothing in the deck owns it. On second boot, the picture changes.

The Electron supervisor reads inference-bindings.json at app.whenReady() and sees selectedTier: "T2_CUDA". It probes port 4245. Three possibilities:

  1. Port is listening — the detached sidecar from yesterday is still running. Supervisor logs "port 4245 already listening — assuming prior instance, not spawning" and stops there. The deck talks to the existing sidecar.
  2. Port is free — the user rebooted, or the sidecar crashed cleanly. Supervisor spawns a fresh child via the uv ladder.
  3. No tier persisted — first boot, before onboarding completed. Supervisor logs "no tier installed yet — idle" and waits.

The persisted-tier handoff

This is the contract between the orchestrator and the supervisor. The orchestrator never spawns voice-core through the supervisor — it writes the tier to disk and trusts that the next boot will pick it up. The supervisor never reads the consent file or runs an installer — it just spawns whatever tier the orchestrator left behind.

voice-core-supervisor.ts — readPersistedTierfunction readPersistedTier(): string | null {
  const base =
    process.env.CONTROL_DECK_USER_DATA ??
    (app.isPackaged ? app.getPath("userData") : path.join(repoRoot(), "data"));
  const file = path.join(base, "inference-bindings.json");
  try {
    if (!fs.existsSync(file)) return null;
    const parsed = JSON.parse(fs.readFileSync(file, "utf8")) as { selectedTier?: string };
    return typeof parsed.selectedTier === "string" ? parsed.selectedTier : null;
  } catch { return null; }
}

That's the entire handshake. One file. Three OSes. The orchestrator (Next.js process) and the supervisor (Electron main) never IPC about this — they communicate through the filesystem.

The Ollama health re-check

Every second boot, the gate fires readDoneState(), which probes Ollama:

const ollamaHealthy = await probeOllamaService();
return { done: true, ...stored, ollamaHealthy };

This is one HTTP request to 127.0.0.1:11434/api/tags with a 1.5-second timeout. If it succeeds, normal flow. If it fails — the Ollama service crashed, the port got hijacked, the user uninstalled and forgot — the gate routes back to onboarding. The probe re-detects missing pieces; the orchestrator runs only the steps that need running. The user sees a fresh checklist with ○ Ollama service running and a "Get me running" button that just restarts the service.

THE IDEMPOTENT GOLDEN PATH

Every step the orchestrator runs is idempotent. Pulling a model that's already pulled is a no-op (Ollama skips because the manifest matches). Starting a service that's already running succeeds. Installing Ollama when it's already on PATH is gated out by probe.missing.ollama. The same code path that does a fresh install also does a repair. The user clicks "Get me running" and the system does whatever is necessary — nothing more.

Most boots after the first one feel instant because most boots don't run anything except the gate's localStorage check and a single HTTP probe. The expensive thing — voice-core loading two 1.5 GB models from disk into VRAM — runs in the background while the user is reading their chat history.

12 -- WHAT BREAKS, AND WHY THE DECK NOTICES

A good measure of a system is the list of things it can fail at gracefully. Control Deck has a longer list than most desktop apps, because most desktop apps don't try to install neural networks on machines they've never seen. Here is the inventory: the failure modes the deck plans for, by name, with the line that catches each one.

The headless SSH user

A user opens the deck on a remote machine over SSH X-forwarding. There is no polkit agent. pkexec will hang on a prompt nobody can answer. The orchestrator catches this before it spawns:

orchestrator.tsif (recipe.platform === "linux" && requiresGraphicalAgent(recipe.ollama.install.command)) {
  if (!process.env.DISPLAY && !process.env.WAYLAND_DISPLAY) {
    yield stamp({
      id: "install-ollama",
      status: "failed",
      detail: `No graphical session detected — \`pkexec\` needs a polkit agent.
        Open a terminal and run: \`${recipe.ollama.install.consent.manual_fallback}\``,
    });
    return;
  }
}

NixOS and Alpine

NixOS users can't write to /usr/local/bin. Alpine ships musl libc, which the Ollama binary doesn't link against. Both make Ollama's install.sh succeed silently and produce a binary that segfaults on first run.

orchestrator.ts — detectUnsupportedDistrofunction detectUnsupportedDistro(): string | null {
  if (process.platform !== "linux") return null;
  if (existsSync("/etc/nixos") || existsSync("/etc/NIXOS")) return "NixOS";
  if (existsSync("/etc/alpine-release")) return "Alpine Linux";
  return null;
}

Two files. Two early exits. The user gets "NixOS isn't supported by Ollama's install script. Install via your distro's package manager and retry." — before the 250 MB download starts, not after.

The vanilla Mac without Homebrew

The macOS recipe assumes brew is on PATH. A fresh Mac doesn't have it. firstMissingDependency() catches this and the probe sets autoInstallable: false. The voice-core crash loop

Three deaths in five minutes and the supervisor stops. The UI sees gaveUp: true via the IPC bridge. Without the just-added restart() method, the only fix would be relaunching Electron. Now there's a button.

The settings drawer's Backend pills are the visible surface. The drawer probes /api/backend for ollama and llama_server status:

SettingsDrawer.tsx — useLocalBackendHealthconst one = async (provider) => {
  try {
    const res = await fetch("/api/backend", {
      method: "POST",
      body: JSON.stringify({ provider, setActive: false }),
    });
    return res.ok && !!(await res.json()).healthy;
  } catch { return false; }
};

Each pill gets a colored dot: cyan accent if reachable, dim red if offline, gray if probing. The probe runs on drawer open and on backend switch. No cloud probes — those burn API credits for no benefit on a health check.

The pull stream dies mid-download

Already covered in chapter 8. The orchestrator never trusts the stream alone — it re-probes /api/tags after the loop ends. If the tag isn't there, it tells the user the network dropped and that Ollama's partial cache will resume on retry.

The Windows installer changes PATH but our process can't see it

Already covered in chapter 7. refreshWindowsPath() re-reads HKCU\Environment\Path via powershell and merges it into process.env.PATH in memory. The verify step then sees ollama --version succeed.

The packaged Electron build can't find windows.yaml

Already covered in chapter 6. Next.js's standalone tracer doesn't follow dynamic readFileSync calls, so the YAMLs would be missing. The fix:

OOM under arbiter contention

The sidecar reports CUDA OOM to the arbiter. The arbiter drops every reservation on that lane and force-unloads:

arbiter.ts — reportOomexport async function reportOom(lane, error) {
  emit({ kind: "oom", at: Date.now(), lane, error });
  for (const [ticket, r] of reservations) {
    if (r.lane === lane) {
      reservations.delete(ticket);
      emit({ kind: "release", ... });
    }
  }
  await doUnload(lane).catch(() => null);
  await refreshSnapshot();
  pumpQueue();
}

Then it pumps the queue. Anyone waiting on that lane (a soft-evict caller) gets re-tried. If they fit now, they win. If they don't, they time out gracefully.

The Skip button trap

One quirk worth flagging. The Skip button calls markDoneManual(), which writes a done flag with skipped: true and no tier. The next time the user opens the deck, the gate sees done: true and looks at ollamaHealthy. If they skipped before installing Ollama, ollamaHealthy is false, and the gate routes them back to onboarding. They have to skip again. This is by design — the user said "I'll set this up later" and the system honors it — but it's the rough edge most likely to confuse a future maintainer.

FAIL LOUD, FAIL EARLY

Every one of these failure modes has the same structure: detect before the expensive operation, surface a sentence the user can act on, never silently succeed. The most expensive failure is the 5 GB pull that completes and then the smoke test discovers the wrong CPU instruction set. The cheapest failure is "you don't have curl." Push every check as far upstream as it'll go.

What does Control Deck actually do? It detects your hardware honestly. It picks a model stack you can actually run. It installs the pieces, with consent, and tells you exactly what command will execute. It pulls the weights, throttles the progress bar, and re-verifies after the stream closes. It supervises a Python sidecar with a sliding-window restart budget and a kill switch. It arbitrates every byte of VRAM with a lane policy that knows what's evictable for what.

And when it breaks — because it will — it tells you what broke, in a sentence, and gives you a button.

That's the whole deck. Five minutes on the first boot. Twelve hundred milliseconds every time after.
