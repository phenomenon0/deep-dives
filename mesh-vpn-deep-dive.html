MESH VPN

From raw UDP sockets to a self-healing encrypted mesh. Kotlin on Android, Rust at the core, and the NAT traversal tricks that make peer-to-peer actually work._

Your phone, your TV, and a file descriptor that pretends to be a network card.

Your phone and your TV are on the same Wi-Fi. They cannot talk to each other. Not because the hardware forbids it, but because no application on either device knows the other exists. Install a mesh VPN on both, and suddenly the phone can open a UDP socket to 10.0.0.2:7777 and stream controller inputs to the TV at 60 frames per second. The TV can stream video back. A friend can join from across town. All encrypted. All authenticated. All invisible to every other device on the network. The mechanism that makes this possible is almost offensively simple: a file descriptor that pretends to be a network card.

On Android, you do not open /dev/net/tun directly. The platform gives you a cleaner abstraction: VpnService. But the mechanism is identical. You build a virtual interface, the system routes traffic through it, and you get a ParcelFileDescriptor. Which is just a file descriptor in a trenchcoat.

Every Platform, Same Mechanism

On iOS, the equivalent is NEPacketTunnelProvider from NetworkExtension. On Linux and Raspberry Pi, you open /dev/net/tun directly (the Rust tab below shows this). On Windows, WireGuard uses WinTUN. On macOS, utun. The API differs by platform. The mechanism is identical everywhere: a file descriptor that captures IP packets.

What can you do with this? More than you might think. Your phone becomes a game controller : 20 bytes of stick input, 60 times per second, encrypted and tunnelled to a TV across the room or across the city. The TV streams a video feed back. A friend joins from their phone, and suddenly you have a three-player couch game where the couch spans two apartments. Someone opens a laptop, and the mesh gives them access to a shared folder on the TV’s hard drive. None of these applications know a VPN exists. They connect to an IP address and a port, and the mesh handles everything underneath : the encryption, the NAT traversal, the path selection. That is the point of a TUN device: it makes the network layer invisible to the application layer.

The TUN Device

A TUN device operates at Layer 3: it captures and injects IP packets. Its cousin the TAP device operates at Layer 2 and handles Ethernet frames. WireGuard and Tailscale both use TUN because they only care about IP routing, not Ethernet bridging. This is an important distinction: a TUN-based VPN can route packets between subnets, but it cannot bridge two LANs at the Ethernet level. For our mesh, that is exactly what we want.

On Linux, creating a TUN device is two syscalls: open("/dev/net/tun") and an ioctl(TUNSETIFF) to configure it. On Android, VpnService.Builder wraps both into a single establish() call and also handles the routing table changes that would otherwise require ip route commands.

TUN Packet Loop – Two Threads, Two File Descriptors

The critical insight is the symmetry. Both peers run the same code. There is no "client" and "server" in a mesh VPN. There are only peers, each with a TUN device and a UDP socket. The packet loop is identical on both sides: read from TUN, encrypt, send over UDP. Receive from UDP, decrypt, write to TUN. The only state that differs is the routing table: which peer owns which IP range.

use std::fs::OpenOptions;
use std::os::unix::io::AsRawFd;

fn create_tun() -> std::io::Result<i32> {
    let file = OpenOptions::new()
        .read(true).write(true)
        .open("/dev/net/tun")?;

    // struct ifreq with IFF_TUN | IFF_NO_PI
    let mut ifr = [0u8; 40];
    ifr[16] = 0x01;  // IFF_TUN
    ifr[17] = 0x10;  // IFF_NO_PI (no packet info header)

    unsafe {
        let ret = libc::ioctl(
            file.as_raw_fd(),
            0x400454CA,  // TUNSETIFF
            ifr.as_mut_ptr()
        );
        if ret < 0 { return Err(std::io::Error::last_os_error()); }
    }

    Ok(file.as_raw_fd())
}
Key Insight

The MTU is set to 1280, not the usual 1500. Why? Our packets will be wrapped inside UDP inside IP, and each layer adds headers. WireGuard adds 32 bytes of its own header plus a 16-byte authentication tag. If the inner packet is 1500 bytes and the outer headers push it past the path MTU, the packet gets fragmented or dropped. 1280 is the minimum MTU that IPv6 guarantees, making it a safe choice for any network path. Tailscale uses 1280 for the same reason.

The Packet Loop

The core of any userspace VPN is a tight loop that shuttles packets between the TUN device and a UDP socket. On Android, we run this loop in Rust (called via JNI) because per-packet crypto in a GC’d language invites latency spikes. The loop is two threads, one for each direction:

Rust
fn run_tunnel(tun_fd: i32, udp: &UdpSocket, peer: SocketAddr) {
    let mut buf = [0u8; 1500];

    // Outbound: TUN → encrypt → UDP
    loop {
        let n = unsafe { libc::read(tun_fd, buf.as_mut_ptr() as _, buf.len()) };
        if n <= 0 { break; }

        let packet = &buf[..n as usize];
        let encrypted = encrypt_packet(packet);  // → ch04
        udp.send_to(&encrypted, peer).ok();
    }
}

fn run_receive(tun_fd: i32, udp: &UdpSocket) {
    let mut buf = [0u8; 1500];

    // Inbound: UDP → decrypt → TUN
    loop {
        let (n, _src) = udp.recv_from(&mut buf).unwrap();
        let decrypted = decrypt_packet(&buf[..n]);  // → ch04

        if let Some(packet) = decrypted {
            unsafe { libc::write(tun_fd, packet.as_ptr() as _, packet.len()); }
        }
    }
}

Two threads, not one. The TUN read and UDP receive block independently. If you combined them into a single loop, receiving a packet from the network would stall TUN reads, and vice versa. The threads are the concurrency model.

Two file descriptors, two threads, and a tight loop. The tunnel is shaped — but right now it carries nothing. encrypt_packet and decrypt_packet are stubs that return their input. Flip them on and every app on the phone is exposed, talking plaintext across the internet with a fake-VPN badge on top. Before we can fill the stubs in, you need to know exactly what the TUN device hands us: not a vague blob of bytes, but a 20-byte IPv4 header followed by the payload it is wrapping. That is chapter 2.

Byte 0 encodes both the version (high nibble: 4 for IPv4) and the header length (low nibble: 5, meaning 5×4 = 20 bytes). Bytes 2–3 give the total packet length in big-endian. Byte 8 is the TTL (time-to-live), decremented by every router and used to prevent routing loops. Byte 9 is the protocol: 6 = TCP, 17 = UDP, 1 = ICMP. Bytes 12–15 are the source IP; bytes 16–19 are the destination IP. These fields exist because routers need to forward packets without trusting the sender. TTL prevents routing loops, the checksum catches corruption, and the destination tells the router where to send it. We care because our VPN reads the destination IP to decide which peer gets the encrypted packet.

Rust
struct Ipv4Header {
    version:     u8,       // always 4
    ihl:         u8,       // header length in 32-bit words (usually 5)
    total_len:   u16,      // entire packet length, including this header
    ttl:         u8,
    protocol:    u8,       // 6=TCP, 17=UDP, 1=ICMP
    src_addr:    [u8; 4],  // e.g. [10, 0, 0, 1]
    dst_addr:    [u8; 4],  // e.g. [10, 0, 0, 2]
}

impl Ipv4Header {
    fn parse(buf: &[u8]) -> Option<Self> {
        if buf.len() < 20 { return None; }
        let version = buf[0] >> 4;
        if version != 4 { return None; }  // not IPv4

        Some(Ipv4Header {
            version,
            ihl: buf[0] & 0x0F,
            total_len: u16::from_be_bytes([buf[2], buf[3]]),
            ttl: buf[8],
            protocol: buf[9],
            src_addr: [buf[12], buf[13], buf[14], buf[15]],
            dst_addr: [buf[16], buf[17], buf[18], buf[19]],
        })
    }

    fn dst_ip_str(&self) -> String {
        format!("{}.{}.{}.{}",
            self.dst_addr[0], self.dst_addr[1],
            self.dst_addr[2], self.dst_addr[3])
    }
}

And 60 bytes is only the price of wrapping. Encryption needs keys — and right now, both peers have none. Neither can encrypt anything without a shared secret that nobody else on the wire has seen. They have to build one from scratch, over a public channel, without ever sending the answer. Chapter 3 is how they do it.

Why UDP?

WireGuard runs over UDP, not TCP. If you encapsulate TCP inside TCP, you get the TCP-over-TCP problem: both layers independently detect loss and retransmit, fighting each other. The outer TCP retransmits an encrypted packet while the inner TCP has already retransmitted the plaintext inside a different encrypted packet. The result is bandwidth collapse under loss. UDP as the outer transport lets the inner TCP handle retransmission without interference.

// 03 – the key exchange

TUNNEL → PACKET → KEYS → CIPHER → NAT → PUNCH → RELAY → MESH → ROUTING → STATE → ANDROID → HARDENING → TAILSCALE

Two devices agree on a shared secret without ever sending it across the wire.

Two devices that have never communicated need to agree on a shared secret. If either one sends the secret in plaintext, an eavesdropper captures it and the entire session is compromised. If they negotiate it over multiple round-trips, the handshake is slow and vulnerable to interruption. WireGuard solves this in two messages and 240 bytes. The protocol is called Noise IK, and it is a bet: I already know who you are, so let us skip the introductions and start encrypting. Two messages, three Diffie-Hellman operations, and both sides share a session key that an eavesdropper cannot derive even if they record every byte of the exchange.

Normally, two strangers on the internet prove their identity over multiple round trips. Noise IK assumes you have already traded public keys, via a coordination server or a QR code. Alice can encrypt her identity under a key derived from Bob's public key. Only Bob can decrypt it. Bob confirms "that is Alice," and replies with his half. Mutual authentication in two messages instead of four.

The Primitives

Our mesh needs exactly four cryptographic building blocks. Everything in this article — the handshake, the packet encryption, the key rotation — is built from combinations of these four:

Primitive What It Does Concrete Choice
Key exchange Two peers derive a shared secret from their public keys X25519 (Curve25519 ECDH)
AEAD cipher Encrypt data + authenticate it in one operation ChaCha20-Poly1305
Hash Compress arbitrary data into a fixed-size fingerprint BLAKE2s (256-bit output)
KDF Derive multiple keys from a single shared secret HKDF-BLAKE2s

These are not arbitrary choices. WireGuard picked them because they are all constant-time (resistant to timing attacks), fast on ARM without hardware acceleration (important for phones and TVs), and each has a single canonical implementation with no configurable parameters. There is no cipher negotiation in WireGuard. You use these four, or you do not connect. This inflexibility is a feature: it eliminates an entire class of downgrade attacks.

Why Not AES?

AES-GCM is fast on CPUs with AES-NI instructions (x86 desktop, server). But many Android devices, especially Android TV boxes and budget phones, use ARM chips without hardware AES acceleration. On those chips, AES-GCM is 3–5× slower than ChaCha20-Poly1305, which is implemented entirely with additions, XORs, and rotations, operations that are fast on every CPU. This is why Google mandated ChaCha20-Poly1305 as a TLS cipher for Android in 2014.

X25519: Key Generation

Every peer in our mesh has a static key pair: a 32-byte private key and a 32-byte public key. The private key is just 32 random bytes with three bits clamped (the lowest three bits are cleared, and the highest bit is set). The public key is the private key multiplied by the curve’s base point. This multiplication is a one-way function; there is no known way to reverse it.

Rust
use x25519_dalek::{StaticSecret, PublicKey};
use rand::rngs::OsRng;

// Generate a static identity key pair for this peer
let private_key = StaticSecret::random_from_rng(OsRng);
let public_key = PublicKey::from(&private_key);

// 32 bytes each. The public key is safe to share.
println!("Public key: {:?}", public_key.as_bytes());
// → [142, 231, 17, 83, ...] (32 bytes)

// Diffie-Hellman: given our private key and their public key,
// both sides compute the same shared secret.
let shared_secret = private_key.diffie_hellman(&their_public_key);
// shared_secret.as_bytes() → 32-byte value known to both peers

This is the Diffie-Hellman magic: Alice computes a * B (her private key times Bob’s public key), Bob computes b * A (his private key times Alice’s public key), and both arrive at the same point on the curve : the shared secret. An eavesdropper who sees both public keys A and B cannot compute the shared secret without solving the elliptic curve discrete log problem, which is believed to require ~2128 operations on Curve25519.

The Noise IK Handshake

WireGuard does not use raw Diffie-Hellman. It uses the Noise protocol framework, specifically the IK pattern. "I" means the initiator transmits their static key in the first message. "K" means the responder’s static key is already known to the initiator.

Think of it as a conversation with three layers of proof happening simultaneously:

Layer 1: Alice generates a throwaway key pair (the ephemeral key) and mixes it with Bob's public key. This proves she is talking to the real Bob, because only someone who knows Bob's private key could decrypt what follows.

Layer 2: Alice encrypts her own static public key and a timestamp under a second shared secret derived from both static keys. This proves Alice is who she claims to be, and the timestamp prevents replay.

Layer 3: Bob replies with his own ephemeral key. Now both sides have mixed ephemeral and static keys together. Even if every long-term key is stolen tomorrow, the ephemeral keys are already gone from memory. Past sessions stay safe. This is forward secrecy.

All three proofs happen in two messages and 240 bytes. No certificate authority. No multi-round negotiation. No cipher suite selection. One protocol, one set of primitives, one bet: I already know who you are.

Three Diffie-Hellman operations happen across the two messages. Each one proves something different. Together they form a chain: the session key depends on all three secrets.

DH Operation Inputs What It Proves
DH(ealice, Sbob) Alice’s ephemeral × Bob’s static Alice is talking to the real Bob (not an impersonator)
DH(salice, Sbob) Alice’s static × Bob’s static Alice is who she claims to be (mutual authentication)
DH(ebob, Ealice) Bob’s ephemeral × Alice’s ephemeral Forward secrecy. If either static key is compromised later, past sessions are safe

Each DH result is mixed into a chaining key using HKDF-BLAKE2s. The chaining key accumulates entropy from every DH operation. By the time both messages are complete, the derived session keys depend on all three DH secrets. Compromise any one of them and you still cannot recover the session key without the other two.

Implementing the Initiator

Rust
use x25519_dalek::{EphemeralSecret, PublicKey, StaticSecret};
use blake2::Blake2s256;
use chacha20poly1305::{ChaCha20Poly1305, KeyInit, AeadInPlace};

fn initiate_handshake(
    my_static: &StaticSecret,
    my_public: &PublicKey,
    their_public: &PublicKey,
) -> (Vec<u8>, HandshakeState) {
    // 1. Generate ephemeral key pair (used once, then discarded)
    let eph_secret = EphemeralSecret::random_from_rng(OsRng);
    let eph_public = PublicKey::from(&eph_secret);

    // 2. Initialize chaining key and hash
    let mut ck = blake2s(b"Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s");
    let mut h  = blake2s(&[&ck[..], their_public.as_bytes()].concat());

    // 3. Mix in our ephemeral public key
    h = mix_hash(&h, eph_public.as_bytes());

    // 4. DH #1: ephemeral × their static
    let dh1 = eph_secret.diffie_hellman(their_public);
    let (ck_new, key1) = hkdf(&ck, dh1.as_bytes());
    ck = ck_new;

    // 5. Encrypt our static public key under key1
    let encrypted_static = aead_encrypt(&key1, &h, my_public.as_bytes());
    h = mix_hash(&h, &encrypted_static);

    // 6. DH #2: our static × their static
    let dh2 = my_static.diffie_hellman(their_public);
    let (ck_new, key2) = hkdf(&ck, dh2.as_bytes());
    ck = ck_new;

    // 7. Encrypt timestamp under key2 (proves freshness)
    let timestamp = tai64n_now();  // 12-byte monotonic timestamp
    let encrypted_ts = aead_encrypt(&key2, &h, &timestamp);
    h = mix_hash(&h, &encrypted_ts);

    // 8. Assemble Message 1
    let mut msg = Vec::with_capacity(148);
    msg.push(1);                          // type: handshake initiation
    msg.extend_from_slice(&[0u8; 3]);          // reserved (must be zero)
    msg.extend_from_slice(&random_u32().to_le_bytes()); // sender index
    msg.extend_from_slice(eph_public.as_bytes());
    msg.extend_from_slice(&encrypted_static);
    msg.extend_from_slice(&encrypted_ts);
    msg.extend_from_slice(&mac1(&msg, their_public)); // anti-DoS
    msg.extend_from_slice(&[0u8; 16]);                  // MAC2 (cookie, usually zero)

    (msg, HandshakeState { ck, h, eph_public })
}
Key Insight

The ephemeral key is generated fresh for every handshake and destroyed after use. This is what gives WireGuard forward secrecy: even if your static private key is stolen tomorrow, an attacker cannot decrypt today’s traffic because the ephemeral keys are gone. They existed only in RAM, for the duration of one handshake.

Failure Mode: Clock Skew

That 12-byte tai64n_now() call in step 7 hides a real operational hazard. The responder compares the received timestamp against the last timestamp it saw from this initiator — and rejects anything older or equal. It also rejects timestamps too far in the future. WireGuard’s accepted window is roughly ±3 minutes from the responder’s wall clock. If a phone boots up with its clock set to 1970 (common before NTP kicks in), every handshake it sends fails silently — the responder sees "too old, replay" and drops the message. If a device’s clock runs hours ahead, the responder sees "too new, rejected" and drops it just as silently. No error is returned on the wire. The initiator just keeps retrying and timing out.

This is the failure you cannot diagnose by looking at your own logs. You need the responder’s logs too. Production hardening (chapter 13) shows how to catch this with NTP health checks and a fallback to HTTPS-based time sync on first boot.

What the psk2 in the Protocol Name Buys You

Look at the first line of the handshake code: blake2s(b"Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s"). The psk2 means an optional 32-byte pre-shared key is mixed into the chaining key right before message 2 is built. WireGuard leaves this slot all-zeros by default, so it does nothing unless you set it. But you can set it — one command, one shared secret you distribute out of band — and from that moment the handshake is also authenticated by a symmetric key that no public-key crypto can break.

The point is not today's attacker. It is the attacker with a quantum computer in 2035. Curve25519 is not post-quantum safe; if a harvest-now-decrypt-later adversary archives your traffic today, they can decrypt it once Shor's algorithm runs on real hardware. The PSK slot closes that door: even a broken Curve25519 cannot recover the session key if the PSK is unknown. Three commands of friction for a decade-long guarantee.

The responder performs the same DH operations in reverse, derives the same chaining key, and replies with Message 2 containing its own ephemeral public key. After both messages are exchanged, both sides call hkdf(&ck, &[]) one final time to derive two symmetric keys: one for the initiator-to-responder direction, one for the reverse. Two messages, 240 bytes, and both peers share a secret that nobody else on the internet can derive. But a shared secret is not encryption. The next chapter turns that secret into a cipher that protects every packet on the wire.

Encrypting every packet with ChaCha20-Poly1305 and why nonce reuse is catastrophic.

A nonce is not a suggestion. Reuse it once and the entire keystream is recoverable. That is the single most important sentence in this chapter. ChaCha20-Poly1305 is an AEAD cipher: Authenticated Encryption with Associated Data. It does two things in one operation: encrypts your plaintext (so eavesdroppers cannot read it) and authenticates it (so tamperers cannot modify it without detection). The "associated data" is extra context, like the packet header, that is authenticated but not encrypted, so both sides can parse it before decryption.

How the Cipher Works

ChaCha20 is a stream cipher. It takes a 256-bit key and a 96-bit nonce and generates a keystream: an infinite river of pseudorandom bytes. You XOR your plaintext with the keystream to encrypt. XOR again with the same keystream to decrypt. The magic is that the keystream is indistinguishable from random noise to anyone who does not know the key.

The companion is Poly1305, which takes the ciphertext and produces a 16-byte authentication tag. If even one bit of the ciphertext was flipped in transit, the tags will not match and the receiver silently discards the packet. No error message, no feedback. An attacker learns nothing about what went wrong.

Together they form an AEAD cipher: encrypt AND authenticate in one operation. This is the entire data-plane crypto for our mesh. Every packet, every peer, every direction.

The core operation is four 32-bit additions, four XORs, and four bitwise rotations. These are the fastest operations on any CPU. No multiplication, no table lookups, no data-dependent branches:

a += b;  d ^= a;  d <<<= 16;
c += d;  b ^= c;  b <<<= 12;
a += b;  d ^= a;  d <<<= 8;
c += d;  b ^= c;  b <<<= 7;

Four variables, four operations, repeated 20 times. No S-boxes, no finite-field arithmetic. Twenty rounds produces one 64-byte block of keystream. Each block is independent (you can compute block n without blocks 0 through n−1), making ChaCha20 trivially parallelizable.

This simplicity is why ChaCha20 is ~3× faster than AES on ARM chips without hardware acceleration. And why it is easier to implement in constant time, closing a major side-channel attack surface.

Poly1305 takes the ciphertext and produces a 16-byte authentication tag (MAC). The sender computes the tag and appends it; the receiver recomputes and compares. If even one bit was flipped in transit, the tags diverge and the packet is silently dropped.

This silence is intentional. In a VPN, you do not want to give an attacker an oracle. If you sent back "authentication failed," you would confirm the packet structure and format. Silent drop denies the attacker information about what they are attacking.

Poly1305 uses a one-time key derived from the ChaCha20 keystream. This means each packet gets a fresh MAC key, so even if the MAC computation has a theoretical weakness, it cannot be exploited across packets.

Encrypt & Decrypt

Rust
use chacha20poly1305::{
    ChaCha20Poly1305, KeyInit, AeadInPlace,
    aead::Nonce, aead::Tag,
};

struct Transport {
    key:           [u8; 32],
    counter:       u64,
    sender_index:  u32,
}

impl Transport {
    fn encrypt_packet(&mut self, plaintext: &[u8]) -> Vec<u8> {
        // Build the nonce from the counter (little-endian, zero-padded to 12 bytes)
        let mut nonce_bytes = [0u8; 12];
        nonce_bytes[4..].copy_from_slice(&self.counter.to_le_bytes());
        let nonce = Nonce::from(nonce_bytes);

        // Encrypt in place
        let cipher = ChaCha20Poly1305::new(&self.key.into());
        let mut buffer = plaintext.to_vec();
        let tag = cipher.encrypt_in_place_detached(&nonce, &[], &mut buffer)
            .expect("encryption failed");

        // Assemble: header + encrypted payload + tag
        let mut packet = Vec::with_capacity(16 + buffer.len() + 16);
        packet.push(0x04);                              // type: transport data
        packet.extend_from_slice(&[0, 0, 0]);          // reserved
        packet.extend_from_slice(&self.sender_index.to_le_bytes());
        packet.extend_from_slice(&self.counter.to_le_bytes());
        packet.extend_from_slice(&buffer);              // ciphertext
        packet.extend_from_slice(tag.as_slice());        // 16-byte MAC

        self.counter += 1;  // CRITICAL: never reuse a nonce
        packet
    }

    fn decrypt_packet(&self, packet: &[u8]) -> Option<Vec<u8>> {
        if packet.len() < 32 { return None; }  // 16 header + 16 tag minimum

        // Parse header
        let counter = u64::from_le_bytes(packet[8..16].try_into().ok()?);

        // Build nonce from counter
        let mut nonce_bytes = [0u8; 12];
        nonce_bytes[4..].copy_from_slice(&counter.to_le_bytes());
        let nonce = Nonce::from(nonce_bytes);

        // Split ciphertext and tag
        let payload = &packet[16..packet.len() - 16];
        let tag = Tag::from_slice(&packet[packet.len() - 16..]);

        // Decrypt and verify
        let cipher = ChaCha20Poly1305::new(&self.key.into());
        let mut buffer = payload.to_vec();
        cipher.decrypt_in_place_detached(&nonce, &[], &mut buffer, tag)
            .ok()?;  // returns None if auth tag doesn't match

        Some(buffer)
    }
}
Nonce Reuse Is Catastrophic

If you encrypt two different plaintexts with the same key and nonce, an attacker can XOR the two ciphertexts together and get the XOR of the two plaintexts, from which the original messages can often be recovered. WireGuard prevents this with a monotonically increasing counter that is never reset for a given session key. If the counter reaches 264−1 (which would take billions of years at 10 Gbps), the session must rekey. In practice, WireGuard rekeys every 2 minutes regardless.

Plugging It In

With the handshake from chapter 3 and the cipher from this chapter, our packet loop from chapter 1 is now complete. The stubs collapse into real code by holding a Transport instance alongside the TUN and UDP file descriptors:

Rust
fn run_tunnel(tun_fd: i32, udp: &UdpSocket, peer: SocketAddr, transport: &mut Transport) {
    // TUN → UDP: read plaintext IP packet, encrypt, send
    let mut buf = [0u8; 1500];
    let n = read(tun_fd, &mut buf).unwrap();
    let encrypted = transport.encrypt_packet(&buf[..n]);  // stub → real
    udp.send_to(&encrypted, peer).unwrap();

    // UDP → TUN: receive ciphertext, decrypt, write
    let (n, _) = udp.recv_from(&mut buf).unwrap();
    if let Some(plaintext) = transport.decrypt_packet(&buf[..n]) {
        write(tun_fd, &plaintext).unwrap();
    }
}

Why your packets vanish when you leave the LAN, and who is dropping them.

The internet was designed for end-to-end communication. NAT broke that promise, and now we have to steal it back. Our tunnel from chapter 4 works beautifully when both peers can see each other: same Wi-Fi, same LAN, or both on public IPs. But in the real world, almost every device hides behind a NAT: your home router, your carrier’s CGNAT, your office firewall. The moment you try to connect your phone to your TV across different networks, the tunnel fails silently. The UDP packets leave one side and vanish into the void. This chapter explains why.

What NAT Actually Does

Your home router has one public IP address shared by every device on your LAN. When your phone sends a UDP packet to a peer, the router rewrites the source address from 192.168.1.42:51820 to 73.42.18.99:34921 (the router’s public IP and an ephemeral port it chose). It records this mapping in a table. When a reply comes back to 73.42.18.99:34921, the router looks up the mapping, rewrites the destination back to 192.168.1.42:51820, and forwards it. This is Network Address Translation, a hack from 1994 that was supposed to be temporary until IPv6 arrived. Thirty years later, it is everywhere.

The problem is the inbound direction. If a peer on the internet sends a UDP packet to 73.42.18.99:34921 before your phone has sent anything out, the router has no mapping. It does not know which internal device the packet is for. So it drops it. Your phone is invisible to the world unless it speaks first.

Think about that. Your friend's TV is trying to send you 20 bytes of controller input. The packet crosses three ISPs, arrives at your router, and bounces off. Not because the packet is malformed. Not because the address is wrong. Because you have not spoken first. The router has your phone's address right there in its table, and it still drops the packet. This is NAT.

The Double-NAT Nightmare: CGNAT

It gets worse. Mobile carriers frequently deploy Carrier-Grade NAT (CGNAT, RFC 6598). Your phone sits behind your home router’s NAT, which itself sits behind the carrier’s NAT. Two layers of address translation. The external port your phone sees via STUN is the carrier’s external port, not your router’s. And the carrier’s NAT is almost always symmetric.

Double NAT – CGNAT, Inaccessible by Design
Why This Matters for Our Mesh

In Tailscale’s measurements, ~92% of connections succeed with direct hole-punching. The remaining 8% hit symmetric NAT, double-NAT, or corporate firewalls that block UDP entirely. That 8% is why you need a relay (chapter 7). A mesh that only works for 92% of connections is a toy. The relay is not an optimization. It is a correctness requirement.

The Phone-to-TV Scenario

Let us ground this in our use case. You want your Android phone to connect to your Android TV. Three common scenarios:

Same Wi-Fi

Both devices on the same LAN. No NAT between them. Direct UDP works. The tunnel from chapter 4 works as-is. This is the easy case.

Same Home, Different VLANs

IoT VLAN isolation. Some routers put smart TVs on a separate VLAN. Devices cannot see each other at Layer 2. You need to route through the gateway, but no NAT is involved. Usually works with a route hint.

Phone on Cellular, TV on Home Wi-Fi

The common case. Phone is behind carrier CGNAT (often symmetric). TV is behind home router (usually port-restricted). Need STUN + hole punching + relay fallback.

Both on Cellular / Hotel Wi-Fi

Worst case. Both behind symmetric NATs or captive portals that block UDP. Hole punching almost never works. Relay is the only option.

The next chapter shows how to punch through the first three scenarios. The one after shows what to do when punching fails. But before we get to the hard dance, there are two shortcuts worth checking: the network may already be offering to open a door.

Shortcuts: IPv6 and Router-Assisted Mapping

Hole punching is what you do when the network refuses to help. But modern networks sometimes do help, in two distinct ways. Neither is reliable enough to be the primary plan, but both are cheap to try first — if either works, you skip STUN, you skip the simultaneous-send dance, and you get a direct path on the first try.

IPv6 end-to-end. Every Android phone on a modern carrier has an IPv6 address. Most home broadband gives every device on the LAN a real IPv6 address too. If both peers have IPv6, there is no NAT between them — just routing. The phone can send a UDP packet directly to the TV’s global IPv6 address and it will arrive, because IPv6 has enough addresses that nobody needs to translate. The catch: most residential IPv6 deployments still run a stateful firewall that drops unsolicited inbound traffic. So you still need the packet loop from chapter 4, but you skip NAT entirely. Tailscale’s measurements show ~30–40% of connections can use IPv6 directly when both sides support it. Always try IPv6 before IPv4.

UPnP IGD, NAT-PMP, and PCP — asking nicely. Many home routers expose a control protocol that lets a device on the LAN request "please forward external port X to me." If the router agrees, you get a stable public endpoint for free — no STUN needed, no hole to keep punching. Three competing protocols cover this:

STUN discovery, simultaneous sends, and the race condition you win on purpose.

The first packet you send to your friend’s TV is dropped. So is the first packet they send to you. Both NATs reject unsolicited inbound traffic from unknown sources. But those dropped packets are not wasted. Each one punches a hole: it creates a NAT mapping that says "I just sent to this address, so accept replies from it." When the second packet arrives, the hole is already open. Both sides created a mapping at the same time, and the third packet flows through in both directions. This is hole punching. It is a race condition you win on purpose.

But to send a packet to each other, both peers need to know the other’s public IP and port. That is the job of STUN, Session Traversal Utilities for NAT.

STUN: Discovering Your Public Address

STUN is a protocol so simple it barely deserves the name "protocol." You send a 20-byte Binding Request to a STUN server on the public internet. The server reads the source IP and port from the UDP packet (as rewritten by your NAT), wraps them in a Binding Response, and sends it back. That is it. One round trip, and you know your public-facing address.

The XOR-MAPPED-ADDRESS attribute XORs the IP and port with the transaction ID. This is not encryption; it is a workaround for broken NATs that inspect packet contents and rewrite IP addresses they find inside (a behaviour called ALG, Application Layer Gateway). XORing the address makes it unrecognizable to these overzealous NATs.

Rust
use std::net::UdpSocket;

const STUN_BINDING_REQUEST: u16 = 0x0001;
const STUN_MAGIC_COOKIE: u32 = 0x2112A442;
const XOR_MAPPED_ADDRESS: u16 = 0x0020;

fn stun_discover(sock: &UdpSocket) -> Option<(std::net::Ipv4Addr, u16)> {
    // Build a minimal STUN Binding Request
    let mut req = [0u8; 20];
    req[0..2].copy_from_slice(&STUN_BINDING_REQUEST.to_be_bytes());
    // length = 0 (no attributes in request)
    req[4..8].copy_from_slice(&STUN_MAGIC_COOKIE.to_be_bytes());
    // Transaction ID: 12 random bytes
    let txn_id: [u8; 12] = rand::random();
    req[8..20].copy_from_slice(&txn_id);

    sock.send_to(&req, "stun.l.google.com:19302").ok()?;

    // Read the response
    let mut buf = [0u8; 128];
    let (n, _) = sock.recv_from(&mut buf).ok()?;
    let resp = &buf[..n];

    // Parse attributes, find XOR-MAPPED-ADDRESS
    let mut pos = 20;  // skip 20-byte header
    while pos + 4 <= resp.len() {
        let attr_type = u16::from_be_bytes([resp[pos], resp[pos+1]]);
        let attr_len  = u16::from_be_bytes([resp[pos+2], resp[pos+3]]) as usize;

        if attr_type == XOR_MAPPED_ADDRESS && attr_len >= 8 {
            let data = &resp[pos+4..pos+4+attr_len];
            // XOR port with top 16 bits of magic cookie
            let port = u16::from_be_bytes([data[2], data[3]])
                ^ (STUN_MAGIC_COOKIE >> 16) as u16;
            // XOR IPv4 address with magic cookie
            let ip_bytes = [
                data[4] ^ req[4], data[5] ^ req[5],
                data[6] ^ req[6], data[7] ^ req[7],
            ];
            let ip = std::net::Ipv4Addr::new(
                ip_bytes[0], ip_bytes[1], ip_bytes[2], ip_bytes[3]
            );
            return Some((ip, port));
        }
        pos += 4 + attr_len;
        if pos % 4 != 0 { pos += 4 - (pos % 4); } // STUN padding
    }
    None
}

The Simultaneous Send

This is the critical moment. Both peers have each other’s public endpoint. They send UDP packets to each other simultaneously. Why the First Packets Die

The first packet from each side is sacrificed. Alice’s initial packet reaches Bob’s NAT before Bob has sent anything outbound, so Bob’s router has no mapping for Alice’s external address and drops it. Bob’s initial packet meets the same fate at Alice’s router. But both outbound packets create mappings on the way out. The second round of packets arrives at routers that now recognise the source as a legitimate reply, and they flow straight through. The “hole” is the NAT mapping created by the outbound packet.

The timing does not need to be perfect. NAT mappings persist for 30 to 120 seconds (UDP mapping timeout varies by router). As long as both sides send within that window, the holes will still be open when the return packets arrive. In practice, both peers send a burst of packets over 2 to 3 seconds, and at least one pair crosses successfully.

The Port Shotgun for Symmetric NAT

When both peers are behind symmetric NATs, the external port is unpredictable. But it is not random. Most NATs allocate ports sequentially or from a small range. If Alice’s NAT assigns ports in the 30000–40000 range, Bob can spray packets at hundreds of ports in that range; whichever one matches Alice’s actual external port creates a mapping the other can use. With both sides each spraying ~256 candidate ports, the collision probability becomes high enough to punch through — call it a targeted coupon-collector attack. Tailscale implements a variant of this as a last resort before falling back to relay. It adds ~500ms of latency and generates a burst of ~500 packets, but it works often enough to save the connection.

A relay is an admission of defeat, but a mesh that cannot relay is a mesh that cannot reach. When hole punching fails, we need a third party to forward packets between peers. This is what Tailscale calls DERP: Designated Encrypted Relay for Packets. The name is deliberately self-deprecating. Relaying is the slow path, the expensive path, the path you want to avoid. But it is also the path that makes the mesh always work, even behind the most hostile networks.

Think of It As a Rendezvous Hotel

Two travelers cannot find each other's homes — the streets are blocked, the addresses are rewritten, the doors do not open to strangers. So they agree on a hotel they both already know how to reach. They both check in, walk to the lobby, and the concierge passes sealed envelopes between them. The hotel never opens the envelopes. It does not know what they are planning. It just has mailboxes keyed by name and a policy of delivering whatever it is handed.

That is a relay. The peers can't reach each other directly, but they can both reach a third address on the public internet. They both open a connection there. The server reads only the destination public key on each packet, looks up the corresponding connection, and forwards the ciphertext. It never sees inside the envelope. It is a phonebook + a mailbox, not a router.

Why HTTPS, Not UDP

If your peer’s NAT blocks all inbound UDP, why would a UDP relay work any better? It would not. DERP runs over HTTPS with WebSocket upgrade, specifically, it uses the same TCP port 443 that every website uses. No firewall blocks port 443. No captive portal interferes with TLS connections. By tunnelling encrypted WireGuard packets inside a WebSocket frame inside a TLS connection inside a TCP stream, we can reach any device that can load a web page.

This is an absurd stack of protocols. The overhead is real: TCP headers, TLS records, WebSocket framing, all on top of the WireGuard envelope we already built. But it works when nothing else does, and the relay is a fallback, not the primary path. The moment hole punching succeeds, traffic migrates off the relay.

                val frame = bytes.toByteArray()
                when (frame[0]) {
                    0x05.toByte() -> {  // RecvPacket
                        val srcKey = frame.sliceArray(5..37)
                        val wgPacket = frame.sliceArray(37..frame.lastIndex)
                        onRelayedPacket(srcKey, wgPacket)
                    }
                    0x08.toByte() -> {  // PeerGone
                        val peerKey = frame.sliceArray(5..37)
                        onPeerDisconnected(peerKey)
                    }
                }
            }
        })
    }

    fun relayPacket(destKey: ByteArray, wgPacket: ByteArray) {
        // Frame: type(1) + length(4) + destKey(32) + wgPacket
        val frame = ByteArray(5 + 32 + wgPacket.size)
        frame[0] = 0x04  // SendPacket
        val len = (32 + wgPacket.size).toBigEndianBytes()
        len.copyInto(frame, 1)
        destKey.copyInto(frame, 5)
        wgPacket.copyInto(frame, 37)
        ws.send(ByteString.of(*frame))
    }
}

Home DERP Selection

In a production mesh, there are multiple DERP servers distributed globally. Each peer connects to the nearest DERP server based on latency and registers its public key. When peer A wants to relay a packet to peer B, it sends to its DERP server, which forwards to B’s DERP server (if different), which delivers to B. Tailscale runs about 20 DERP servers worldwide; Headscale (the open-source control plane) lets you deploy your own.

For our mesh, a single DERP server is enough to start. It can be any cloud VPS with a public IP, running a WebSocket server that maintains a map of connected public keys to WebSocket connections. The entire DERP server is roughly 200 lines of code. It does not need to understand WireGuard, parse packets, or manage crypto. It is a dumb pipe with an address book.

The Relay Hierarchy

Our mesh uses a three-tier connection strategy, tried in order:
1. Direct LAN: both peers on the same network. No NAT involved. Lowest latency (~1ms).
2. Hole-punched UDP: STUN + simultaneous send. Direct path through NATs (~5–30ms).
3. DERP relay: encrypted relay over HTTPS. Works everywhere (~30–80ms).
The mesh always starts at tier 3 (guaranteed connectivity), then promotes to tier 2 or 1 as STUN and hole-punching results come in. Traffic migration happens transparently. The application never knows which path its packets are taking.

The Latency Cost

To feel what these tiers mean in practice, picture three scenarios.

Scenario one: couch gaming. Your phone is a controller, the TV runs the game. Both on the same Wi-Fi. The direct LAN path adds about a millisecond of latency, faster than a USB cable. You flick the analog stick, and the character responds before your thumb has finished moving. At this tier, the mesh is invisible. You could stream 4K video from the TV to the phone simultaneously and barely notice the tunnel. The bottleneck is your Wi-Fi bandwidth, not the encryption.

Scenario two: your friend joins from home. Their phone punches through both NATs and establishes a direct UDP path. Round-trip time: maybe 20 milliseconds, depending on ISP hops. Button presses still feel instant. Analog sticks have the faintest hint of smoothing. A racing game plays great; a rhythm game starts to feel off at the margins. The friend can stream their camera feed to your TV at 720p without buffering. The hole-punched path carries 10–50 Mbps easily, and SRT or RTP over the mesh handles the occasional packet loss.

Scenario three: hotel Wi-Fi, corporate firewall, or carrier CGNAT stacked three deep. Nothing punches through. The mesh falls back to the DERP relay. Now every packet takes a detour through a server in some faraway city: 50, 60, maybe 80 milliseconds of round-trip time. Turn-based games are fine. A card game, a board game, a puzzle — you would never notice. But a fighting game becomes a slideshow of traded inputs. The TV can still stream video to the phone (buffered HLS or DASH absorbs the latency), and file transfers work at whatever bandwidth the relay server can push. The relay does not ruin the mesh. It just redefines what the mesh is good at until a better path opens up.

The mesh handles all three scenarios with the same code. The application opens a socket to bob-tv.mesh:7777 and sends packets. Whether those packets cross a living room, two ISPs, or a relay in another timezone is decided by the state machine, not the application. This is why the mesh aggressively promotes connections from relay to direct whenever it can, a topic we revisit in chapter 10.

Key Insight

The relay is not a VPN server. It does not terminate encryption, inspect traffic, or make routing decisions. It is a store-and-forward packet switch keyed by public key, wrapped in HTTPS for firewall traversal. This is a fundamentally different architecture from traditional VPNs (OpenVPN, IPSec), where the server is a trusted intermediary that sees all traffic in plaintext. In our mesh, the relay is optional: a convenience, not a dependency.

With hole punching and relay in place, our mesh can connect any two Android devices on any network. The next chapter adds the final piece: the coordination layer that turns two-peer tunnels into an N-peer mesh.

Peer Table Management

When a peer receives a new netmap, it diffs it against its current state. New peers get a session initialized (but ; that happens on first packet). Removed peers get their session torn down and their keys zeroed. Changed endpoints trigger a new round of hole punching.

Rust
use std::collections::HashMap;
use std::net::SocketAddr;

struct PeerEntry {
    public_key:    [u8; 32],
    mesh_ip:       std::net::Ipv4Addr,
    endpoints:     Vec<SocketAddr>,
    derp_url:      String,
    session:       Option<Session>,         // active Noise session
    conn_state:    ConnState,               // → chapter 10
    allowed_ips:   Vec<IpNet>,              // → chapter 9
    sender_index:  u32,                     // our sender index for this peer
}

struct PeerTable {
    // Lookup by public key (identity)
    by_key:   HashMap<[u8; 32], PeerEntry>,
    // Lookup by sender index (fast path for incoming packets)
    by_index: HashMap<u32, [u8; 32]>,
    // Lookup by mesh IP (routing: dst IP → which peer)
    by_ip:    HashMap<std::net::Ipv4Addr, [u8; 32]>,
}

impl PeerTable {
    fn apply_netmap(&mut self, netmap: &Netmap) {
        let new_keys: HashSet<_> = netmap.peers.iter()
            .map(|p| p.public_key).collect();

        // Remove peers no longer in netmap
        self.by_key.retain(|k, entry| {
            if !new_keys.contains(k) {
                // Tear down session, zero keys
                if let Some(ref mut s) = entry.session {
                    s.destroy();
                }
                self.by_index.remove(&entry.sender_index);
                self.by_ip.remove(&entry.mesh_ip);
                false
            } else { true }
        });

        // Add or update peers from netmap
        for peer in &netmap.peers {
            if let Some(entry) = self.by_key.get_mut(&peer.public_key) {
                // Existing peer — check if endpoints changed
                if entry.endpoints != peer.endpoints {
                    entry.endpoints = peer.endpoints.clone();
                    entry.conn_state = ConnState::NeedsRePunch;
                }
            } else {
                // New peer — allocate sender index, add to tables
                let idx = random_u32();
                let entry = PeerEntry {
                    public_key: peer.public_key,
                    mesh_ip: peer.addresses[0],
                    endpoints: peer.endpoints.clone(),
                    derp_url: peer.derp.clone(),
                    session: None,  // handshake on first packet
                    conn_state: ConnState::Disconnected,
                    allowed_ips: peer.allowed_ips.clone(),
                    sender_index: idx,
                };
                self.by_ip.insert(entry.mesh_ip, peer.public_key);
                self.by_index.insert(idx, peer.public_key);
                self.by_key.insert(peer.public_key, entry);
            }
        }
    }
}

Session Multiplexing

In a two-peer tunnel, there is one session and one key pair. In a mesh with five peers, each peer maintains four independent sessions, each with its own symmetric keys, counter, and sender index. When an encrypted packet arrives, we need to figure out which session it belongs to before we can decrypt it.

This is what the sender index is for. Each peer picks a random 32-bit value for each session and includes it in the handshake. When a data packet arrives, the first thing we read (after the type byte) is the 4-byte sender index. One hash table lookup gives us the session, and the session gives us the decryption key. This is O(1) per packet. No scanning, no trial decryption.

Lazy Session Establishment

A mesh with 20 peers would require 19 simultaneous WireGuard handshakes at startup if we eagerly established sessions. This is wasteful. Most peers do not talk to all other peers at once. Instead, we use lazy initialization: sessions are created on first packet.

When the TUN device emits a packet destined for 10.0.0.3, we look up the peer table by destination IP, find Carol’s entry, and check if a session exists. If not, we initiate a Noise IK handshake (via relay if no direct path exists yet), buffer the packet, and deliver it once the handshake completes. Subsequent packets to Carol use the established session directly.

Rust
fn route_outbound(
    table: &mut PeerTable,
    packet: &[u8],
    udp: &UdpSocket,
    derp: &DerpClient,
) {
    let hdr = match Ipv4Header::parse(packet) {
        Some(h) => h,
        None => return,  // not IPv4, skip
    };

    let dst_ip = Ipv4Addr::from(hdr.dst_addr);

    // Find which peer owns this destination IP
    let peer_key = match table.route_lookup(&dst_ip) {
        Some(k) => k,
        None => return,  // no route, drop
    };

    let peer = table.by_key.get_mut(&peer_key).unwrap();

    // Lazy session: initiate handshake if no active session
    if peer.session.is_none() {
        let (msg, state) = initiate_handshake(
            &my_static_key, &my_public_key,
            &PublicKey::from(peer.public_key),
        );
        // Send handshake via best available path
        send_to_peer(peer, &msg, udp, derp);
        peer.session = Some(Session::handshaking(state));
        peer.pending_packets.push(packet.to_vec());
        return;
    }

    // Encrypt and send
    if let Some(ref mut session) = peer.session {
        let encrypted = session.transport.encrypt_packet(packet);
        send_to_peer(peer, &encrypted, udp, derp);
    }
}

fn send_to_peer(
    peer: &PeerEntry,
    data: &[u8],
    udp: &UdpSocket,
    derp: &DerpClient,
) {
    match peer.conn_state {
        ConnState::Direct(addr) => {
            udp.send_to(data, addr).ok();
        }
        _ => {
            // Fall back to relay
            derp.relay_packet(&peer.public_key, data);
        }
    }
}
Separation of Concerns

The send_to_peer function does not know or care whether the packet is a handshake message or encrypted data. It only knows the current connection state, direct or relayed, and picks the right transport. The encryption layer (chapter 4) and the transport layer (chapters 6–7) are fully decoupled. This separation is what makes connection upgrades (relay → direct) invisible to the WireGuard session.

Key Rotation

WireGuard sessions are not permanent. Every session has a 3-minute rekey timer (REKEY_AFTER_TIME) and a safety threshold of 260 packets. The counter field is 64 bits wide, but the rekey fires at 260 to leave headroom before the nonce space exhausts. When either limit is reached, the initiator starts a new Noise IK handshake, derives fresh session keys, and seamlessly transitions. The old session stays alive briefly to handle in-flight packets, then is destroyed.

In our mesh, a rekey is cheap: 148 + 92 = 240 bytes, one round trip. If the peer is directly reachable, the rekey completes in under 10ms. The brief overlap between old and new sessions means zero packet loss during transition. The sender index in each packet tells the receiver which session to use for decryption.

AllowedIPs as a Routing Table

In a traditional VPN, the routing table and the encryption config are separate systems that must agree. In WireGuard, they are the same data structure. The AllowedIPs list for a peer does three things simultaneously:

Function Direction What It Does
Routing Outbound Packets matching an AllowedIP range are encrypted and sent to that peer
Access control Inbound Decrypted packets are accepted only if the source IP matches the peer’s AllowedIPs
Anti-spoofing Inbound Prevents a peer from impersonating another peer’s IP address

In a traditional VPN, you configure a route (route 10.0.0.0 255.255.255.0) and separately configure a firewall rule for who can send from that range. If they disagree, you get dropped packets or security holes. In WireGuard, there is one source of truth. AllowedIPs is the routing table AND the firewall AND the anti-spoofing filter, all bound to the same peer identity. One place to update. No inconsistency possible.

Outbound routing uses longest-prefix match, just like a kernel routing table. If Bob advertises 10.0.0.0/24 and Carol advertises 10.0.0.3/32, a packet to 10.0.0.3 goes to Carol (more specific match), while a packet to 10.0.0.7 goes to Bob (broader match). This is the same algorithm your operating system uses for routing decisions, reimplemented in userspace.

Rust
use std::net::Ipv4Addr;

struct RouteEntry {
    network:    u32,        // network address as u32
    mask:       u32,        // bitmask (e.g., /24 → 0xFFFFFF00)
    prefix_len: u8,         // for longest-prefix comparison
    peer_key:   [u8; 32],   // which peer to route to
}

struct RoutingTable {
    routes: Vec<RouteEntry>,  // sorted by prefix_len descending
}

impl RoutingTable {
    fn lookup(&self, dst: Ipv4Addr) -> Option<[u8; 32]> {
        let dst_u32 = u32::from(dst);
        // Routes are sorted longest-prefix-first.
        // First match wins (most specific route).
        for route in &self.routes {
            if (dst_u32 & route.mask) == route.network {
                return Some(route.peer_key);
            }
        }
        None
    }

    fn rebuild_from_netmap(&mut self, netmap: &Netmap) {
        self.routes.clear();
        for peer in &netmap.peers {
            for cidr in &peer.allowed_ips {
                self.routes.push(RouteEntry {
                    network:    cidr.network,
                    mask:       cidr.mask,
                    prefix_len: cidr.prefix_len,
                    peer_key:   peer.public_key,
                });
            }
        }
        // Sort: longest prefix first for correct matching
        self.routes.sort_by(|a, b| b.prefix_len.cmp(&a.prefix_len));
    }
}

The Routing Loop Trap

If you route 0.0.0.0/0 through the TUN device, your DERP relay traffic also enters the tunnel, and it tries to exit through the relay, creating an infinite loop.         ?.let { InetAddress.getByName(it.addresses[0]) }
}
The Phone-to-TV Payoff

With routing and DNS in place, the mesh stops being infrastructure and starts being a platform. Your phone can ping bob-tv.mesh and get a reply, whether that means a direct LAN hop, a hole-punched tunnel, or a DERP relay halfway around the world. But pinging is the boring part. Here is what this actually enables:

A game on your phone opens a UDP socket to bob-tv.mesh:7777. It sends 20-byte controller updates: stick position, button state, gyro orientation. The TV decodes them and renders the game. The return path streams H.264 video at 8 Mbps via RTP to alice-phone.mesh:5004. From the game engine’s perspective, the TV is a local server. From the video decoder’s perspective, the phone is receiving a local stream. Neither knows about the mesh.

A media app on your tablet resolves bob-tv.mesh and starts an HLS stream of a movie stored on the TV’s hard drive. The TV advertises its home LAN (192.168.1.0/24) as a subnet route, so the tablet can also reach the NAS at 192.168.1.50 and browse a shared photo library. A friend joins from their phone. The coordination server pushes an updated netmap. Within seconds, the friend’s phone has a direct hole-punched connection to the TV and a relayed connection to your tablet. // 10 – the state machine

TUNNEL → PACKET → KEYS → CIPHER → NAT → PUNCH → RELAY → MESH → ROUTING → STATE → ANDROID → HARDENING → TAILSCALE

Nine states, five timers, and the lifecycle that keeps every connection alive.

Roaming is free. An authenticated packet from a new address is proof enough. No renegotiation required. This is perhaps WireGuard’s most underappreciated feature. When your phone switches from Wi-Fi to cellular, its public IP changes instantly. In a traditional VPN, this kills the connection and forces a reconnect. In WireGuard, the next authenticated packet from the phone’s new IP is enough for the peer to update its endpoint. No handshake, no session tear-down, just a silent route change. The session keys are still valid because they are tied to the key pair, not the network address.

But roaming is just one state transition in a complex lifecycle. Each peer connection moves through nine distinct states, driven by timers, network events, and probe results. This state machine is the brain of the mesh. It decides when to punch, when to relay, when to rekey, and when to give up.

Connection States

Every peer connection is a negotiation between speed and reliability. The state machine captures the lifecycle of that negotiation:

Disconnected is the starting point. You know the peer exists (the netmap told you), but you have never talked to them.

Relay Only is the safe fallback. Traffic flows through DERP. It works everywhere, but adds 30 to 80ms of latency. The mesh immediately starts trying to do better.

Punching is the active attempt to do better. STUN has discovered endpoints, and we are sending probe packets directly. If one gets through, we promote. If none respond in 10 seconds, symmetric NAT or a firewall is blocking us, and we fall back to relay.

Direct is the goal. Packets flow peer-to-peer over UDP. Lowest latency. Every 25 seconds we send a keepalive to keep the NAT mapping alive.

Idle means the peer went quiet. No packets for 30 seconds. Maybe the app is backgrounded, maybe the phone is sleeping. We send keepalive probes. If they respond, we stay Direct. If 90 seconds pass with no response, the mapping is dead.

Expired means the mapping is certainly gone. Session torn down, keys zeroed, fall back to relay. If the peer comes back, we start fresh.

Roaming is the magic state. A packet arrived from a new IP address. The phone switched from Wi-Fi to cellular, or the NAT rebinding changed. We decrypt the packet. If it authenticates, the source address updates silently. No renegotiation.

Rekeying happens every 3 minutes. Fresh ephemeral keys, fresh session keys, forward secrecy renewed. The old session stays alive briefly for in-flight packets, then is destroyed.

Why 30 seconds for idle, 90 for expire? NAT mappings persist 30 to 120 seconds depending on the router. Sending keepalives every 25 seconds keeps the mapping alive. If no response arrives for 30 seconds, the peer may be sleeping or backgrounded, so we probe. After 90 seconds of total silence, the mapping is certainly dead on even the most generous routers, so we tear down and fall back to relay.

Implementing the State Machine

Rust
use std::time::{Duration, Instant};
use std::net::SocketAddr;

enum ConnState {
    Disconnected,
    RelayOnly,
    Punching   { started: Instant, attempts: u32 },
    Direct     { addr: SocketAddr, last_rx: Instant },
    Idle       { addr: SocketAddr, last_rx: Instant },
    Expired,
    Roaming    { old_addr: SocketAddr, new_addr: SocketAddr, since: Instant },
    Rekeying   { previous: Box<ConnState>, started: Instant },
    NeedsRePunch,
}

const KEEPALIVE: Duration = Duration::from_secs(25);
const IDLE_THRESHOLD: Duration = Duration::from_secs(30);
const EXPIRE_THRESHOLD: Duration = Duration::from_secs(90);
const PUNCH_TIMEOUT: Duration = Duration::from_secs(10);
const REKEY_INTERVAL: Duration = Duration::from_secs(180);  // REKEY_AFTER_TIME

fn tick(peer: &mut PeerEntry, now: Instant) -> Vec<Action> {
    let mut actions = Vec::new();

    match &peer.conn_state {
        ConnState::Direct { addr, last_rx } => {
            let silence = now.duration_since(*last_rx);

            // Send keepalive before NAT mapping expires
            if silence >= KEEPALIVE {
                actions.push(Action::SendKeepalive(*addr));
            }

            // Transition to Idle if peer has gone quiet
            if silence >= IDLE_THRESHOLD {
                peer.conn_state = ConnState::Idle {
                    addr: *addr, last_rx: *last_rx
                };
            }

            // Check if rekey is due
            if let Some(ref s) = peer.session {
                if s.age(now) >= REKEY_INTERVAL {
                    actions.push(Action::InitiateRekey);
                }
            }
        }

        ConnState::Idle { last_rx, .. } => {
            if now.duration_since(*last_rx) >= EXPIRE_THRESHOLD {
                peer.conn_state = ConnState::Expired;
                actions.push(Action::TeardownSession);
                actions.push(Action::FallBackToRelay);
            }
        }

        ConnState::Punching { started, attempts } => {
            if now.duration_since(*started) >= PUNCH_TIMEOUT {
                peer.conn_state = ConnState::RelayOnly;
                actions.push(Action::ScheduleRePunch(
                    Duration::from_secs(30)
                ));
            }
        }

        ConnState::RelayOnly => {
            // Periodically retry hole punch in background
            actions.push(Action::TryPunchInBackground);
        }

        _ => {}
    }

    actions
}

Roaming: The Authenticated Endpoint Update

When a packet arrives from a source address that does not match the expected endpoint, most systems would drop it as suspicious. WireGuard does something smarter: it decrypts the packet first. If decryption succeeds (the Poly1305 tag verifies), the packet is authentic. It came from a peer who knows the session key. The source address is simply updated. No new handshake, no interruption.

Rust
fn handle_incoming(
    table: &mut PeerTable,
    data: &[u8],
    src: SocketAddr,
) {
    if data.len() < 16 { return; }

    let msg_type = data[0];
    let sender_index = u32::from_le_bytes(
        data[4..8].try_into().unwrap()
    );

    // Look up the session by sender index
    let peer_key = match table.by_index.get(&sender_index) {
        Some(k) => *k,
        None => return,  // unknown session, drop
    };

    let peer = table.by_key.get_mut(&peer_key).unwrap();

    if msg_type == 0x04 {  // Transport data
        if let Some(ref session) = peer.session {
            if let Some(plaintext) = session.transport.decrypt_packet(data) {
                // Decryption succeeded → packet is authentic.
                // Check if source address changed (roaming).
                let expected = match &peer.conn_state {
                    ConnState::Direct { addr, .. } => Some(*addr),
                    _ => None,
                };

                if expected.map_or(false, |a| a != src) {
                    // ROAMING: peer moved to a new address.
                    // The successful decrypt proves authenticity.
                    peer.conn_state = ConnState::Direct {
                        addr: src,
                        last_rx: Instant::now(),
                    };
                } else {
                    // Normal packet, update last_rx
                    if let ConnState::Direct { ref mut last_rx, .. }
                        = peer.conn_state
                    {
                        *last_rx = Instant::now();
                    }
                }

                // Write decrypted packet to TUN
                write_to_tun(&plaintext);
            }
        }
    }
}
Key Insight

Roaming works because WireGuard’s security model ties sessions to cryptographic identity (the key pair), not to network identity (the IP address). As long as the session keys are valid and the packet authenticates, the source address is just a routing hint. This is what makes mobile . A phone can bounce between Wi-Fi, cellular, and back without the application layer noticing anything.

The Keepalive Contract

NAT mappings expire. If no packets flow for 30–120 seconds (depending on the router), the hole we punched closes and the next packet is dropped. WireGuard’s persistent keepalive prevents this: every 25 seconds, each side sends a minimal encrypted packet (just the header + empty payload + auth tag = 32 bytes). This does two things:

Keeps NAT Alive

The outbound keepalive refreshes the NAT mapping. The hole stays open. 25 seconds is safely below even the most aggressive NAT timeout (typically 30s minimum).

Detects Failure

If we send three keepalives (75 seconds) with no response, the peer is likely unreachable. The state machine transitions to Idle, then Expired, then falls back to relay. This is faster than waiting for TCP to time out.

The keepalive is also what triggers roaming detection. When a phone switches from Wi-Fi to cellular, its next keepalive arrives from a new source address. The peer decrypts it, sees the address changed, and updates the endpoint. The whole roaming process takes about 25 seconds, roughly one keepalive interval, with zero interruption to application-layer connections.

The Tick Loop

The state machine runs on a 100ms tick. Every 100ms, we iterate through all peers, check timers, and emit actions (send keepalive, initiate punch, rekey, etc.). This is cheap. For a mesh of 20 peers, each tick checks 20 entries, each of which is a single match statement and a timestamp comparison. The total CPU cost is negligible. The tick model is simpler and more predictable than per-peer timer threads, and it naturally batches work when multiple peers need attention at once.

With the state machine in place, our mesh is functionally complete. Each peer maintains independent connections to every other peer, automatically promoted from relay to direct when possible, with transparent roaming, keepalives, and rekey. Doze Mode & Battery

Android’s Doze mode restricts network access and defers jobs when the screen is off and the device is stationary. A VPN service gets an exemption from most Doze restrictions, but not all:

Constraint Effect on VPN Mitigation
Network restricted UDP keepalives may be delayed VpnService is exempt; works normally
Wake locks limited Cannot hold CPU awake indefinitely Use AlarmManager for periodic STUN refresh
JobScheduler deferred Background coordination delayed Use WebSocket push, not polling
App standby buckets Rare-use apps get throttled Foreground service keeps us in "active" bucket

Battery drain from a mesh VPN is dominated by two factors: keepalive frequency (25-second interval means 2,880 UDP packets per peer per day) and radio wake-ups (each packet wakes the cellular radio if it has idled). For a mesh with 5 active peers, expect ~3–5% battery drain per hour with active traffic, dropping to <1% when idle (keepalives only). Tailscale reports similar numbers.

Always-On VPN

Android supports always-on VPN at the system level: Settings → Network → VPN → gear icon → "Always-on VPN." When enabled, Android starts your VPN service at boot and blocks all network traffic if the VPN disconnects. This is ideal for a mesh. The device is always reachable. The only implementation requirement is handling onRevoke() gracefully (the user disabled the VPN) and onStartCommand() with a null intent (the system restarted your service).

Replay Protection

In chapter 4, we used a monotonically increasing counter as the nonce. The receiver must reject any counter value it has already seen, or an attacker can replay old packets. Replay what, exactly? Imagine the mesh controls a smart lock. Packet 47 says "unlock." Without replay protection, an attacker records packet 47, waits for you to leave, and plays it again. The lock opens. The replay window ensures packet 47 is accepted exactly once. Any subsequent attempt is rejected before decryption.

But strict monotonicity is too rigid. UDP packets can arrive out of order. WireGuard uses a sliding window bitmap: a 2048-bit field that tracks which of the last 2048 counter values have been received.

Rust
struct ReplayWindow {
    bitmap: [u64; 32],   // 32 × 64 = 2048 bits
    last:   u64,          // highest counter seen
}

impl ReplayWindow {
    fn check_and_update(&mut self, counter: u64) -> bool {
        if counter > self.last {
            // New highest: shift the window forward
            let shift = counter - self.last;
            if shift >= 2048 {
                // Massive jump: clear everything
                self.bitmap = [0; 32];
            } else {
                // Shift the bitmap by `shift` positions
                shift_bitmap(&mut self.bitmap, shift as usize);
            }
            self.last = counter;
            set_bit(&mut self.bitmap, 0);
            true
        } else if self.last - counter >= 2048 {
            // Too old: outside the window, reject
            false
        } else {
            // Within the window: check if already seen
            let idx = (self.last - counter) as usize;
            if get_bit(&self.bitmap, idx) {
                false  // replay: already received
            } else {
                set_bit(&mut self.bitmap, idx);
                true   // out-of-order but new: accept
            }
        }
    }
}

The window allows up to 2048 packets of reordering. In practice, UDP reordering on the internet rarely exceeds a few dozen packets, so this window is generous. The bitmap is 256 bytes, a negligible cost per session.

Cookie / DoS Protection

The Noise IK handshake in chapter 3 is computationally expensive: each initiation requires two Curve25519 DH operations. An attacker can flood the responder with forged handshake initiation packets, forcing it to waste CPU on DH computations for peers that do not exist. This is the handshake flood attack.

WireGuard’s defense is the cookie mechanism, adapted from DTLS. It works in two stages:

Cookie / DoS Protection Sequence 

  Initiator                              Responder (under load)
       │                                       │
       │  Handshake Initiation                │
       │  MAC1 = HMAC(msg, responder_pubkey)   │
       │  MAC2 = zeros (no cookie yet)         │
       │──────────────────────────────────────▶│
       │                                       │
       │                                       │  CPU load > threshold?
       │                                       │  Check MAC1 → valid
       │                                       │  MAC2 is zeros → no cookie
       │                                       │
       │  Cookie Reply                         │
       │  cookie = HMAC(initiator_IP, secret)  │
       │  encrypted with initiator's key       │
       │◀──────────────────────────────────────│
       │                                       │
       │  Handshake Initiation (retry)         │
       │  MAC1 = HMAC(msg, responder_pubkey)   │
       │  MAC2 = HMAC(msg, cookie)             │
       │──────────────────────────────────────▶│
       │                                       │
       │                                       │  Check MAC1 → valid
       │                                       │  Check MAC2 → valid
       │                                       │  Process handshake normally
       │                                       │
       │  Handshake Response                   │
       │◀──────────────────────────────────────│

MAC1 is always present and proves the initiator knows the responder’s public key (cheap to verify). MAC2 is only required when the responder is under load. The cookie binds the handshake to the initiator’s IP address, so an attacker who spoofs source IPs cannot reuse someone else’s cookie. The cookie changes every 2 minutes (the responder rotates its secret), so replay is bounded.

Why Not Just Rate-Limit?

IP-based rate limiting punishes everyone behind a shared NAT. If 100 devices share a carrier NAT IP, rate-limiting that IP blocks 99 innocent users. The cookie mechanism is per-handshake: legitimate initiators get a cookie on first try and succeed on retry. Attackers with spoofed IPs never receive the cookie reply (it goes to the real IP) and cannot proceed. This is targeted defense, not collateral damage.

Key Rotation Schedule

Event Timer What Happens
Session rekey Every 2 minutes Initiator starts a new Noise IK handshake. Fresh ephemeral keys. New session keys. Old session kept briefly for in-flight packets.
Counter exhaustion At 264−1 packets Session must rekey (theoretical limit, never reached in practice at ~10 Gbps it would take 50,000 years).
Handshake timeout 5 seconds If no response to handshake initiation, retry with exponential backoff (5s, 10s, 20s, then give up).
Cookie secret rotation Every 2 minutes Responder generates a new random secret for cookie computation. Old cookies remain valid for their lifetime.
Session destroy 3 minutes after rekey Old session keys are zeroed. Any in-flight packets using old keys are dropped.

What Happens When the Coordination Server Dies

The coordination server is a single point of failure for new connections, but not for existing ones. Here is the degradation hierarchy:

Server Down < 2 min

No impact. Existing sessions continue. Keepalives flow. Rekeys succeed (they use WireGuard, not the server). No one notices.

Server Down 2–60 min

Existing sessions work. New peers cannot join. Endpoint changes are not distributed. If a peer roams, the authenticated-endpoint-update (chapter 10) still works for direct connections, but the coordination server cannot help peers that need relay.

Server Down > 60 min

Peer sessions expire naturally (90s idle threshold). Peers still in the last-known netmap can reconnect via direct punch or relay. Peers that were never in the netmap are unreachable. The mesh degrades to the set of peers that have cached each other’s keys.

Server Compromised

The attacker can push a malicious netmap (add fake peers, remove real ones). But they cannot decrypt traffic. They do not have any peer’s static private key. They can disrupt connectivity (DoS) but not confidentiality. This is the same trust model as Tailscale’s control plane.

The Trust Boundary

Our coordination server is honest-but-curious infrastructure, same as Tailscale’s. It can see who is in the mesh and who is talking to whom (metadata), but it cannot read traffic (confidentiality is end-to-end). A fully compromised coordination server can disrupt connectivity but cannot break encryption. The only way to decrypt traffic is to steal a peer’s static private key, and even then, forward secrecy from ephemeral keys protects past sessions. This is the design goal: the infrastructure is a convenience, not a trust dependency.

Debugging the Mesh

When a mesh breaks, it breaks in three specific places: the tunnel never comes up (handshake failing), the tunnel is up but no packets flow (routing or NAT), or packets flow but something drops them (MTU, firewall, middlebox). Each has its own diagnostic surface. Memorise the commands once and they will serve you forever.

Layer-by-Layer Inspection 

  1. Is the TUN device up at all?
     $ ip -6 addr show tun0                     # Linux / Raspberry Pi
     $ ifconfig utun4                           # macOS
     → you should see the mesh IP (e.g. 10.0.0.7) bound to the interface

  2. Is the routing table sending traffic through TUN?
     $ ip route get 10.0.0.42                   # "via 10.0.0.7 dev tun0"
     $ netstat -rn | grep tun                   # macOS / BSD equivalent

  3. Is the app actually writing to TUN?
     $ sudo tcpdump -ni tun0 -XX -s 0           # watch plaintext IP packets
     → if you see packets here, the app is trying. If not, it isn't.

  4. Are those packets getting out over UDP?
     $ sudo tcpdump -ni eth0 udp port 51820     # watch WireGuard envelopes
     → outbound only: NAT is blocking. Outbound+inbound: tunnel is live.

  5. Is the handshake succeeding?
     $ wg show                                  # stock WireGuard
     $ meshctl peers                            # our implementation equivalent
     latest handshake: 37 seconds ago   → healthy
     latest handshake: (never)          → keys or endpoint wrong
     latest handshake: 4 minutes ago    → rekey stalled, check clock skew

  6. Is the coordination server reachable?
     $ curl -sv https://coord.example.com/health
     $ meshctl derp-check                       # probes every configured relay

Log at Three Levels, Not More

A VPN generates firehose-volume events: every packet, every rekey, every keepalive, every DERP frame. Resist the urge to log them all. Three levels is enough: ERROR for things that should page a human (handshake fails repeatedly, DERP unreachable, key rotation failed). INFO for state transitions (peer up, peer down, relayed → direct). DEBUG for packet-level detail, off by default, toggleable at runtime via a signal or control socket. Never log packet contents. Never log private keys. Never log full endpoints in production — just the peer fingerprint and "direct/relay" — because logs leak. Tailscale uses exactly this structure and the kernel WireGuard module logs almost nothing at all; it trusts the operator to tcpdump when they need the detail.

The HTTPS Trick

Tailscale can issue valid TLS certificates for mesh-internal hostnames because it controls the *.ts.net domain. When you enable HTTPS for a machine, Tailscale’s coordination server provisions a Let’s Encrypt certificate via DNS-01 challenge (it controls the DNS zone), pushes the cert to the machine, and updates MagicDNS to resolve the name. The result: https://nas.tail1234.ts.net works with a green padlock, even though the NAS is behind three layers of NAT. No port forwarding, no DDNS, no self-signed certificates.

Why Tailscale Chose Go

Tailscale’s data plane uses wireguard-go, the userspace WireGuard implementation in Go. We chose Rust for the crypto core; Tailscale chose Go for the entire stack. The tradeoffs are instructive:

Go (Tailscale’s Choice)

Pro: Single language for control plane + data plane. Fast compilation. Excellent networking stdlib. Easy cross-compilation to every platform.
Con: GC pauses on the hot packet path (~100μs occasionally). Higher memory footprint. No zero-cost abstractions for crypto.

Rust Core + Platform Shells (Our Choice)

Pro: No GC on the packet path. Rust’s type system prevents entire classes of memory safety bugs in crypto code. Smaller binary. Platform shells are thin (Kotlin, Swift, or nothing at all on Linux).
Con: Multiple shell languages per platform. JNI (Android) is painful to debug. Cross-compilation for 5+ targets. Smaller hiring pool for Rust.

Tailscale optimized for developer velocity across all platforms. Go compiles to every OS Tailscale supports (Linux, Windows, macOS, iOS, Android, FreeBSD) from a single codebase. The GC pauses are real but tolerable. Most users do not notice 100μs hiccups in a VPN tunnel. For a startup shipping to every platform simultaneously, the single-language advantage outweighs the performance cost.

For our Android-specific mesh, the Kotlin+Rust split makes more sense: Kotlin is the native Android language (no JNI needed for platform APIs), and Rust gives us predictable latency below 100µs, which matters for gaming, our primary use case.

Headscale: The Open-Source Control Plane

Tailscale’s data plane is open source (tailscale/tailscale on GitHub). The control plane is proprietary. It is the commercial product. But the protocol between client and control plane is documented well enough that Headscale (an open-source project by Juan Font) reimplements it. Headscale is a single Go binary that speaks the same coordination protocol as Tailscale’s servers, letting you run your own control plane.

This is architecturally significant: it proves that the control plane is a well-defined service boundary. The data plane does not depend on any proprietary magic. You can swap Tailscale’s control plane for Headscale (or for our WebSocket-based coordination server from chapter 6) and the data plane works identically. The WireGuard tunnel does not care who introduced the peers.

The Lesson

Tailscale did not build a faster tunnel. WireGuard already solved that. They built the operations layer: identity, policy, observability, zero-config deployment. The tunnel is table stakes. Every mesh VPN has one. The product is in the coordination plane, the ACL engine, the SSO integration, the audit log. Our deep dive built the data plane and a minimal coordination layer. Tailscale’s value is in everything above that line.

Where to Go from Here

We built a mesh VPN from scratch in 13 chapters. But the interesting question is not what we built. It is what becomes possible once the mesh exists.

The Living Room

Four friends, four phones, one TV. The TV runs a party game. Each phone is a controller, not through Bluetooth but through the mesh. The phones send stick and button data at 60 Hz over encrypted UDP. The TV sends back per-player HUD information. One friend is actually at home across town, connected via a hole-punched tunnel. The game does not know. The latency difference between the couch and the apartment is about 25 milliseconds, roughly one and a half frames at 60 fps.

The Presentation

Your phone is the remote. Swipe to advance slides on the TV. But the slides live on your laptop, which is also on the mesh. The TV pulls them directly from the laptop via the mesh subnet route. You annotate from your phone, and the annotations flow to both the TV and the laptop simultaneously. After the meeting, you meshdrop the annotated PDF to everyone who was connected. No cloud, no account, no intermediary that keeps a copy.

The Workshop

A Raspberry Pi runs a sensor array. An Android TV displays a real-time dashboard. Your phone receives alerts. Your laptop SSHes into the Pi for debugging. Four devices, three different networks, one mesh. The Pi’s data never touches a cloud server. The SSH session survives your laptop switching from the workshop Wi-Fi to your phone's hotspot. The mesh roams, the TCP connection stays alive, you do not even re-authenticate.

The Browser

A fifth person wants to spectate the party game but does not have the app. They open a URL. A WebRTC connection bootstraps through the mesh’s DERP server. They cannot join the TUN layer (the browser sandbox does not allow it) but the game exposes a WebSocket spectator stream, and the mesh’s coordination server tells the browser where to connect. The spectator sees the game state with 80 milliseconds of additional latency. Good enough to watch, not good enough to play. That boundary, between what TUN enables and what the browser constrains, is the boundary between a player and a spectator, a controller and a viewer.

None of this requires a server you pay rent on. The coordination server is a $5/month VPS. The DERP relay is the same box. The compute, the storage, the rendering: all of it lives on devices you already own. The mesh is just the connective tissue that lets them find each other.

What we did not build is just as important: SSO integration, policy-as-code ACLs, multi-platform support, centralized audit, automatic HTTPS certificates. Those are the features that separate a weekend project from a product. All coordination-plane concerns, not data-plane concerns. The tunnel is the foundation. The operations layer is the product. Tailscale understood this better than anyone.

But the foundation is what we came here to understand. How a file descriptor pretends to be a network card. How two strangers agree on a secret without ever transmitting it. How a NAT mapping becomes a door instead of a wall. How a mesh finds a path when every path is hostile.

That is what a mesh VPN is. Not a tunnel. A policy: every peer can reach every other peer, by whatever path works right now.
