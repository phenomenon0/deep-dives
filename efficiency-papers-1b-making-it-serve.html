01 // The Fleet Problem

You run a 100-room hotel. Every guest who walks in might stay for 30 nights—but most leave after two. Your policy: reserve 30 rooms for every guest, just in case. A weekend visitor checks in. Thirty rooms blocked. A one-night business traveler. Thirty rooms blocked. Three guests later, you have reserved 90 rooms but occupied four. The lobby is packed with people you are turning away because the booking system says you are at capacity.

That is GPU memory management before 2023. Every inference request gets max_seq_len worth of contiguous KV cache allocated upfront, because the serving system does not know how long the response will be. A request that generates 50 tokens still holds memory for 2,048. Or 4,096. Or 32,768. The waste is not a rounding error. It is the majority of your most expensive resource doing nothing.

Woosuk Kwon and his team at Berkeley measured it: only 20.4% to 38.2% of KV cache memory stores actual token states in a running system. The rest is dead weight—three kinds of dead weight, each worse than the last. Internal fragmentation: slots allocated inside a request's block that the sequence never reaches because it finishes early. External fragmentation: scattered gaps between completed requests too small to fit a new one, even though total free memory is sufficient. Reservation overhead: memory locked for tokens that will never exist, because the system cannot predict output length. On an 80GB A100, that is 48 to 64 GB of VRAM holding air.

The constraint

60-80% of KV cache memory is wasted. Not because the model is inefficient—Part I-A already optimized that. Because the serving system does not know how to share.

One request is a solved problem

Serving a single request is trivial. Load the model. Run prefill. Decode token by token. A 7B model on a single A100 handles one user comfortably. You can optimize the attention kernel (Part I-A covered that). You can quantize the weights. You can fuse operations. Single-request inference is a solved problem.

The entire field of "LLM serving" exists because one user is not the problem.

Scale to ten thousand concurrent users and everything changes. Not incrementally. Categorically. The problems you face at ten thousand users are not harder versions of the single-user problems. They are a different class entirely. They are policy problems—decisions about resource allocation, scheduling priority, eviction strategy, and failure handling. The same class of problem that operating systems have been solving since the 1960s. The same problems, it turns out, with the same solutions.

Crisis 1: Memory is finite, requests are greedy

Each request's KV cache grows with every generated token. For a 7B model with 32 layers, each token adds roughly 1 MB of KV state. Sounds small. But at 2K context across a thousand concurrent requests, that is 2 TB of KV cache—far more than any single GPU's 80 GB. Even with aggressive batching across multiple GPUs, the memory pressure is immense.

The questions become policy questions: Who gets memory? Who waits? Who gets evicted? When two requests compete for the last free block, which one survives? These are scheduling and replacement decisions. They have the same structure as the page replacement algorithms (LRU, LFU, clock algorithms) that OS designers debated in the 1970s. The answers, as we will see, are also the same.

Crisis 2: Variable lengths make batching messy

The naive approach: collect N requests, run them together, wait for ALL to finish before accepting new ones. This is called static batching. If one request generates 500 tokens and the rest generate 20, the GPU sits idle for 480 decode steps on 95% of the batch. Every completed request is padded to the length of the longest. Every waiting request is blocked until the entire batch drains. The GPU alternates between full utilization during forward passes and total waste during padding. Throughput collapses to a fraction of theoretical peak.

Crisis 3: Prefill-decode interference

The two phases of inference have opposite computational profiles. Prefill processes the entire input prompt in one parallel pass. It is compute-heavy. GPU-bound. It loves big matrices—this is what the hardware was designed for. Decode generates one token at a time. It is memory-bandwidth-bound. The GPU reads every parameter in the model to produce a single token. Compute units sit mostly idle, waiting for data to arrive from HBM.

When these two phases share a GPU, they sabotage each other. A long prefill—a 32K-token prompt, say—monopolizes the GPU for seconds. During that time, every decode request in the batch is blocked. No tokens generated. Latency spiking. Users staring at frozen cursors. This is head-of-line blocking, the same pathology that plagues single-threaded web servers.

The fix is the same as the web server fix: disaggregate. Run prefill on one pool of GPUs and decode on another, so they never interfere. DeepSeek does this. Together AI does this (their cache-aware variant reports 40% higher throughput for long-context workloads). Every major serving framework—vLLM, SGLang, TensorRT-LLM, NVIDIA Dynamo—now supports prefill-decode disaggregation.

The core tension

Optimizing for one request is a solved problem. Optimizing for a fleet of requests is where systems engineering begins. And the GPU is speed-running 50 years of OS evolution to get there.

LLM serving is, at its core, a scheduling problem. Closer to air traffic control than to machine learning. You have a finite runway (GPU memory). Variable-size aircraft (requests with different prompt and generation lengths). Unpredictable arrival times. The art is: who lands next? Who circles? Who gets diverted? The model itself is the easy part. The hard part is managing 10,000 overlapping lifecycles on hardware that was not designed for sharing.

Throughput vs latency: two different problems

Before we trace the solutions, we need to name the two targets precisely, because confusing them is the most common mistake in LLM optimization discussions.

Throughput is how many tokens per second the system produces across ALL users. Measured in tokens/second/GPU. It is the provider's metric—the number that determines cost per token, revenue per GPU, and how many users you can serve before buying more hardware.

Latency is how long ONE user waits. Split into TTFT (time-to-first-token, how long before the response starts streaming) and TPOT (time-per-output-token, how fast it streams once started). It is the user's metric—the number that determines whether the experience feels instant or sluggish.

These are different problems with different solutions that sometimes conflict. Batching improves throughput (amortize weight reads across many requests) but hurts latency (your request now shares the GPU with 63 others). Speculative decoding improves latency (collapse multiple sequential steps into one verification) but has limited throughput benefit at high batch sizes (the GPU is already utilized, nothing to reclaim).

02 // The Scheduling Revolution

In July 2022, Gyeong-In Yu at Seoul National University published a paper at OSDI called Orca. The venue was the 16th USENIX Symposium on Operating Systems Design and Implementation—an OS conference, not an ML one. The title was dry. The idea was not. Yu had been watching inference servers batch requests the way a long-haul bus runs its route: everyone boards at the depot, nobody gets off until the last passenger reaches their destination. If 31 of 32 passengers want the first stop, they ride the full route anyway. The bus cannot stop.

That is static batching. You gather a batch of requests, run them ALL through the model until EVERY request in the batch finishes generating, then return results. A request that finishes at iteration 20 sits padded and idle for 480 more iterations while the longest sequence in the batch completes at iteration 500. New requests arriving at iteration 21 must wait until the entire batch clears. GPU cycles wasted on padding. Memory wasted on completed-but-held sequences. Throughput collapses under variance.

The pathology is worst when it matters most: in real production workloads, output lengths vary wildly. One user asks "What is the capital of France?" (3 tokens). Another asks for a 2,000-word essay. Static batching pads the first to 2,000 tokens and blocks everything behind them.

Yu asked a simple question: what if the batch boundary was every single decode step instead of every request?

The subway, not the bus

Orca introduced iteration-level scheduling. After every single forward pass—one iteration, one token generated per active sequence—the scheduler can:

// After each decode iteration:
1. Eject finished sequences from the batch
2. Inject newly arrived sequences into the batch
3. Run next forward pass with updated batch composition

The batch composition changes at every step. Requests enter and exit like passengers on a subway: at every station, not just the terminus. A request that finishes at iteration 20 is immediately ejected, and a waiting request slides into its slot at iteration 21. No padding. No blocking. The GPU stays full.

The industry now calls this continuous batching. The name stuck because it captures the essential property: the batch never stops and restarts. It flows continuously, like a river, not a series of dams.

It turned a 36.9x throughput improvement over FasterTransformer from a paper number into the universal default. The 36.9x is the extreme case—maximum variance in output length on GPT-3 175B. Real production gains are 3-8x for conversational workloads. Still transformative. The difference between needing 100 GPUs and needing 15.

Orca's second trick: selective batching

Not all operations in a Transformer can be naively batched across sequences of different lengths. Feed-forward layers are position-independent—batch freely. Attention is position-dependent—each sequence has a different context length and must attend only to its own tokens. Orca introduced selective batching: apply batching only to operations that do not depend on sequence position, while handling attention per-sequence. This lets the engine mix prefill and decode sequences in the same forward pass—a prerequisite for continuous batching to work at all.

The implementation detail matters. Prefill processes many tokens at once (a matrix). Decode processes one token at a time (a vector). Mixing them in the same batch requires the engine to track which sequences are in which phase and handle each accordingly. Without selective batching, you would need separate batches for prefill and decode, destroying the scheduling flexibility that makes continuous batching valuable.

What Orca did not solve

Continuous batching solved the scheduling problem: when to admit and eject requests. But it exposed the memory management problem underneath. You could now pack more requests into the GPU at any given moment—but each request still grabbed a contiguous block of memory sized for the worst case. The scheduler was smart. The allocator was still stupid. A request that would generate 50 tokens still reserved memory for 2,048, blocking other requests from using that space.

The combination was frustrating: Orca told you when to let requests in and out, but could not fix the fact that each request was hogging 5-10x more memory than it needed. The scheduler was optimal. The memory allocator was the new bottleneck. That is the problem the next chapter attacks.

The pattern will repeat throughout this article. Each breakthrough exposes the next bottleneck. Continuous batching exposes memory waste. Fixing memory waste (PagedAttention) exposes prefix redundancy. Fixing prefix redundancy (RadixAttention) exposes decode latency. Fixing decode latency (speculative decoding) exposes draft model quality. Each layer of optimization reveals the constraint that was hidden behind it. The stack grows deeper. This is not a flaw in the research process. It is the research process. Systems engineering is the art of finding and eliminating the current bottleneck, knowing that a new one will emerge.

03 // The Page Table

In the summer of 2022, a team of PhD students in Berkeley's newly launched Sky Computing Lab had built a framework for distributing deep learning models across GPUs. When they set up a demo, performance was terrible. Not the kind of terrible that comes from a bad algorithm. The kind that comes from a hidden bottleneck nobody thought to look for. Zhuohan Li and Woosuk Kwon dug in for months, profiling every layer of the system. They expected to find compute as the constraint. They found memory.

The KV cache management was catastrophically wasteful. Every request pre-allocated a contiguous slab of GPU memory for its maximum possible sequence length. The actual utilization was 20-38%. The rest was the hotel reservation problem, happening on every request, on every GPU, at every serving provider in the world.

Kwon recalled something from undergrad. Every CS student takes an operating systems course. They learn about virtual memory and paging: break physical memory into small fixed-size pages, allocate on demand, map via a page table so each process thinks it has a big contiguous address space while the actual pages are scattered wherever there is room. No more reserving contiguous regions "just in case." They pass the exam. They forget it.

Kwon did not forget it. He asked: why aren't we doing this for KV cache?

The answer became PagedAttention, the core algorithm of vLLM. Published at SOSP 2023—the Symposium on Operating Systems Principles. Not ICML. Not NeurIPS. An OS venue. The reviewers recognized it as an OS paper that happened to run on GPUs. Because it was.

The explicit mapping

The correspondence is not an analogy. It is a one-to-one structural identity:

Instead of giving each request a contiguous block of GPU memory for its maximum possible KV cache, PagedAttention breaks the cache into small fixed-size blocks—like OS pages. Each block holds the keys and values for a fixed number of tokens (typically 16). Blocks are allocated on demand as the sequence grows. A single token generated? Allocate one block. Twenty tokens? Allocate two blocks. They can be stored anywhere in GPU memory, non-contiguously. A block table maps logical positions to physical locations. The model's attention kernel looks up physical block addresses through the table, gathers the keys and values, and computes attention as if the cache were contiguous.

The waste drops from 60-80% to under 4%. The only waste is in the last block of each active sequence—partially filled, waiting for more tokens. With 16 tokens per block, the worst case is 15 wasted tokens per sequence. For 100 concurrent sequences, that is 1,500 wasted token slots. Compare that to the pre-PagedAttention regime where the same 100 sequences might waste 200,000 token slots. Same GPU, 2-4x more concurrent requests.

The elegance of the design is that it requires no changes to the model itself. The attention computation is mathematically identical—the same keys, the same values, the same queries, the same output. The only difference is where the keys and values are stored in physical memory. The block table is a pure indirection layer that the model never sees. This separation of concerns—the model computes, the system manages memory—is exactly the virtual memory abstraction that OS designers achieved in the 1960s.

Copy-on-write completes the parallel

In beam search, multiple candidate sequences share a common prompt prefix. Before PagedAttention, each beam candidate got its own full copy of the prefix's KV cache. Five beams, same prefix: five copies of identical data. PagedAttention applies the same trick Unix uses when you fork() a process: copy-on-write. All candidates point to the same physical KV blocks for the shared prefix. Only when they diverge—when a beam generates a token that differs from the others—does the system copy the diverging block. This saved 55% memory on beam search workloads and 6-10% on parallel sampling.

The kernel tax

PagedAttention's paged layout is not free. The attention kernel must now gather KV values from scattered physical blocks using a block table lookup at every attention computation. Instead of a single contiguous memory read (which the GPU can stream efficiently), the kernel must follow pointers from the block table to potentially scattered physical locations, gathering keys and values block by block. This indirection—the cost of non-contiguous memory access—makes paged attention kernels 2.8x slower than native FlashAttention operating on contiguous memory.

The system trades kernel speed for memory efficiency. When memory is the bottleneck (it usually is at high concurrency), this is a profitable trade: you are 2.8x slower per kernel call but can fit 2-4x more requests, so total throughput still wins. But the kernel tax creates a second, subtler problem: ecosystem fragmentation.

Every new attention kernel innovation needs a paged variant. FlashAttention needs flash_attn_with_kv_cache. FlashInfer needs its own paged kernel. Custom MLA kernels need paged variants. Each variant requires 600+ lines of kernel changes and months of development before it reaches production. When FlashAttention-3 shipped in 2024, it initially lacked PagedAttention support—the fastest attention kernel in the world could not use dynamic memory allocation.

This kernel tax will matter in the next chapter, when a team at Microsoft Research asks the obvious question.

The 2-4x throughput unlock

The throughput gains from PagedAttention deserve decomposition. They come from a single mechanism: reduced memory waste enables larger batch sizes.

With static allocation, an 80GB A100 serving a 7B model might fit 10 concurrent requests (each reserving 4GB of KV cache at max_seq_len=4096). With PagedAttention, the same GPU fits 25-40 requests because each one only occupies memory for its actual token count. More requests in the batch means more work per forward pass. More work per forward pass means better GPU utilization. Better utilization means higher throughput. The 2-4x improvement over Orca (which already had continuous batching) is purely from better memory management enabling bigger batches.

vLLM internals: how the block pool actually works

The current vLLM v1 architecture (post-refactor) uses three key components. BlockPool manages physical KV cache blocks, maintaining all blocks as KVCacheBlock objects indexed by block_id, a free block queue in LRU order, and a cached block map for prefix caching. BlockTable implements the page table, mapping logical request positions to physical block IDs. KVCacheManager orchestrates allocation: on each request, check prefix cache hits, allocate new blocks, cache full blocks for reuse. Eviction is LRU-based—when free blocks are exhausted, evict blocks with zero reference count from the queue head. Blocks are freed in reverse order (tail first) to prioritize evicting less-reusable blocks.

04 // The Prefix Tree

PagedAttention reimplemented OS paging in userspace. Custom allocation logic. Custom block tables. Custom attention kernels. It worked brilliantly. But it created a new problem: every new attention innovation needed a paged variant. FlashAttention-2 needed a paged version. FlashInfer needed its own. When FlashAttention-3 shipped, it initially lacked PagedAttention support. The fastest attention kernel in the world could not use dynamic memory allocation. The ecosystem fragmented around a compatibility problem that vLLM's design had created.

In 2025, Prabhu et al. at Microsoft Research India asked what should have been asked from the start: if PagedAttention was inspired by OS paging, why not just use OS paging?

vAttention: just use the actual OS

CUDA already has virtual memory management APIs. The GPU hardware already does virtual-to-physical address translation, just like a CPU's MMU. Three API calls do all the work:

cuMemAddressReserve(ptr, size)  // Grab contiguous virtual range
                                    // No physical memory allocated yet

cuMemCreate(handle, pageSize)     // Create a physical page

cuMemMap(ptr, handle)              // Bind physical page to virtual address
                                    // GPU MMU handles translation from here

Reserve 12TB of virtual address space. 64-bit GPUs have 128TB available—this is a rounding error. Map physical pages only when tokens actually arrive. The GPU sees a contiguous tensor. The GPU's own memory management unit handles the scatter underneath. This is literally how malloc works on Linux: overcommit virtual, fault in physical.

The result: FlashAttention works unmodified. No custom paged kernels. No block table lookups in the attention hot path. No kernel tax. vAttention achieved 1.97x faster decode than vLLM's paged attention, 3.92x faster prefill on long contexts, and TTFT dropped from 266ms to 68ms on a 192K-token prompt.

The integration effort: 4 API calls. Versus rewriting every attention kernel to handle block table indirection.

Two additional engineering tricks make vAttention practical. Deferred reclamation: when request R1 finishes, do not immediately free its pages. When R2 arrives, give it R1's request ID and reuse its already-mapped physical memory. Only allocate new pages if R2's context exceeds R1's length. This avoids the allocation overhead entirely for the common case. Reclamation is batched when free memory drops below 10%.

Custom page sizes: NVIDIA's CUDA drivers support a minimum 2MB page size. The authors modified the open-source NVIDIA unified memory driver to expose smaller granularities—64KB, 128KB, 256KB. This cuts worst-case internal fragmentation from 128MB (2MB pages on Yi-6B) to 16MB (256KB pages). The allocation bandwidth at 64KB pages is 7.6 GB/s, while decode only needs about 600 MB/s. Allocation is never the bottleneck.

The irony

vLLM closed the vAttention integration proposal as "not planned." The ecosystem had already converged on paged layouts. Every framework, every kernel, every optimization assumed non-contiguous blocks with a block table. The kernel tax that vAttention eliminates is now load-bearing infrastructure. The incumbency problem that vAttention diagnosed is precisely what prevents its adoption.

RadixAttention: a filesystem for KV caches

PagedAttention solved allocation. vAttention solved the kernel tax. But both threw away the KV cache after every request finished. Each new request started cold—even if it shared 90% of its prompt with the previous one. System prompts. Few-shot examples. Conversation history. All recomputed from scratch, every time.

vLLM added "Automatic Prefix Caching" (APC) using hash-based block matching at 16-token granularity. If two prompts shared the first 32 tokens, the first two 16-token blocks would be cache hits. But the granularity was coarse. If two prompts diverge at token 17, the first 16-token block matches but the single shared token in the second block is wasted—15 tokens of reusable KV cache thrown away because of a block boundary. Across thousands of requests with slightly varying prompts, this granularity loss adds up. And APC only cached prompt tokens, not generated ones. In multi-turn chat, the assistant's response is part of the context for the next turn. Throwing away its KV cache means recomputing it on every follow-up message.

Lianmin Zheng at Berkeley—the same lab that built vLLM—reimagined KV cache management as a filesystem problem. The data structure: a radix tree, the same structure Linux uses for its page cache and routing tables. The system: SGLang, published at NeurIPS 2024. The algorithm: RadixAttention.

The insight is structural. LLM workloads are tree-shaped:

// Multi-turn chat
[system prompt] → [user Q1] → [asst A1] → [user Q2] → [asst A2] ...
                → [user Q1'] → [asst A1'] → ...   // different user, same system

// Few-shot learning
[examples 1-5] → [query A]
               → [query B]   // same examples, different queries
               → [query C]

// Agent workflows
[tool descriptions] → [tool call 1] → [result 1] → [tool call 2] ...
                    → [tool call 1'] → [result 1'] ...  // different task

// Code analysis
[file context] → [question about function A]
               → [question about function B]  // same file, different questions

Every one of these workloads is a tree. Shared prefixes branch into diverging suffixes. A radix tree is the natural data structure for all of them. It is the same data structure Linux uses for its page cache and IP routing tables—problems that also involve hierarchical prefix matching with branching at divergence points.

What RadixAttention changes

Token-level granularity. vLLM matches at 16-token block boundaries. RadixAttention matches at individual tokens. Two requests sharing 47 tokens reuse all 47. No wasted partial blocks. The tree splits nodes at exact divergence points.

Caches generated tokens too. This is the big one. When a model generates a response, those KV values stay in the tree. In multi-turn chat, the entire conversation history—system prompt, user turns, assistant responses—accumulates in the tree. The next user message just extends the existing path. vLLM's prefix caching only cached prompt tokens. RadixAttention caches everything.

Cache-aware scheduling. The scheduler does not process requests FIFO. It uses longest prefix match: requests sharing longer prefixes with cached data get priority. With the depth-first weight policy, the scheduler traverses the radix tree depth-first, weighting nodes by how many pending requests need them. Related requests run back-to-back, keeping their KV caches hot. Unrelated requests that would thrash the cache are deprioritized.

LRU eviction with reference counting. Active requests hold locks on their nodes via lock_ref counters. Only zero-reference leaf nodes are evictable. Eviction is recursive from leaves inward—you evict a leaf, then check if its parent is now a zero-reference leaf, and evict that too if so. This prevents evicting KV caches that running requests depend on—the same protection mechanism OS page caches use.

In-batch prefix sharing. When multiple requests in the same batch share a prefix, SGLang detects this via a simulated radix tree of the waiting queue. Requests with short existing cache matches but long in-batch prefix matches get deprioritized—they will benefit more from running after the prefix-establishing request completes. This avoids redundant computation even within a single batch.

The OS arc completes

PagedAttention reimplemented virtual memory paging in userspace. vAttention said: just use the actual CUDA VMM hardware. RadixAttention applied filesystem design patterns—radix trees, LRU eviction, reference counting—to a completely different domain. Three papers. Three decades of OS research, speed-run in three years. The best ML systems papers of 2022-2025 are OS papers in disguise. Every generation of hardware eventually needs an operating system. The GPU's OS is being written right now, one SOSP paper at a time.

Chapters 2 through 4 have traced one arc: the throughput story. Scheduling (Orca) eliminated batch-boundary waste. Memory management (PagedAttention) eliminated allocation waste. Caching (RadixAttention) eliminated recomputation waste. The serving system can now pack more requests, manage memory efficiently, and reuse computation across requests with shared structure. The GPU stays full. The cost per token plummets.

But throughput and latency are different problems. They can even be adversarial. A system serving 10,000 users at maximum throughput might have each individual user waiting 500ms per token because their request shares the GPU with 63 others. The provider is efficient—cost per token is minimal, GPU utilization is high. The user is impatient—the response streams slowly, the interface feels sluggish, the experience suffers.

Chapters 5 through 7 attack the other side: how do you make one user's experience fast? The answer involves exploiting a different kind of waste. Not memory waste (that is now solved). Not scheduling waste (solved too). Compute waste during the decode phase. The GPU is not full during decode. It is nearly empty—95% of compute units sitting dark while the memory bus feeds one token at a time. That emptiness is an opportunity. Speculative decoding and its descendants fill it.

05 // The Idle Assembly Line

Picture a factory floor with ten thousand machines. Drills. Lathes. Welders. Robotic arms. Each one capable of microsecond-precision work. But there is a rule: only one part can be on the line at a time, and it must visit every machine in order. Machine 1 installs a bolt. Then machines 2 through 10,000 wait idle while the part moves. Machine 2 installs a nut. 9,999 machines idle again. You have paid for a factory and you are using it as a workbench.

That is autoregressive decoding. The GPU reads every parameter in the model to produce one token. For a 70B model in FP16, that is roughly 140 GB of data transferred from HBM to compute cores. For one token. Then it does it again for the next token. And the next. Each token depends on the previous one—you cannot start generating token N+1 until token N exists, because it changes the attention context for everything that follows.

The arithmetic tells the whole story. During single-token decode, the operation is a matrix-vector multiply: one token's activations times the model's weight matrices. The arithmetic intensity is around 60-80 operations per byte transferred. But the GPU's compute-to-bandwidth ratio is much higher—156 ops/byte on A100, 295 ops/byte on H100. The GPU could do 2-4x more math per byte of data it reads from memory. But there is nothing to compute. The memory bus is saturated. The compute cores are dark.

The contrast is stark. Prefill is what GPUs were designed for: massive parallel matrix multiplication, thousands of tokens processed simultaneously, compute units fully engaged. Decode is the opposite: the GPU loads the entire model—every weight, every parameter, every layer—to generate a single token. Then it loads the entire model again for the next token. And again. The hardware is bottlenecked on memory bandwidth, with compute units sitting dark, waiting for data to arrive from HBM.

To put this in physical terms: an H100 can perform 990 trillion floating-point operations per second. During single-token decode of a 70B model, it performs roughly 140 billion operations (one matrix-vector multiply through the full network). That takes about 0.14 milliseconds of compute—but the data transfer takes 42 milliseconds because 140 GB must be read from HBM at 3.35 TB/s. The GPU spends 99.7% of decode time waiting for data and 0.3% computing. That is the scandal.

The asymmetry that changes everything

In late 2022, two teams at two different divisions of Google arrived at the same insight independently, within weeks of each other. Neither knew about the other's work.

Yaniv Leviathan, Matan Kalman, and Yossi Matias at Google Research submitted "Fast Inference from Transformers via Speculative Decoding" on November 30, 2022. They used T5-XXL (11B) with T5-small (60M) as draft. Result: 2-3x speedup, identical outputs. Published as an oral at ICML 2023.

Markus Chen, Jerry Tworek, Heewoo Jun, and John Jumper at DeepMind published "Accelerating Large Language Model Decoding with Speculative Sampling" on February 2, 2023. They used Chinchilla (70B) in a distributed setup. Result: 2-2.5x speedup, no quality loss.

Both teams arrived at the same core mechanism: a modified rejection sampling scheme that provably preserves the target model's output distribution. Both teams independently proved the same theorem. The dual discovery was not a coincidence—it was a consequence of the decode-phase scandal being obvious enough that multiple groups attacked it simultaneously.

Google Research later published a retrospective blog post calling speculative decoding "one of the more satisfying developments in machine learning inference." The two-team convergence was evidence that the idea was ready to be discovered—the underlying physics (memory-bound decode with idle compute) made the solution almost inevitable once teams started profiling their inference pipelines carefully.

The technique borrows its name directly from CPU architecture. Modern CPUs encounter branch instructions (if/else) and do not know which path to take until the condition is evaluated. Rather than stall the pipeline, they speculatively execute instructions down the predicted path. If the prediction was right (branch predictors are 95%+ accurate), the work is committed for free. If wrong, the speculative work is discarded and execution restarts from the correct branch. LLM speculative decoding is the same principle: speculate aggressively, verify cheaply, discard mistakes. The "branch predictor" is the draft model. The "pipeline" is the target model's forward pass. The key difference: even on "misprediction," you always get at least 1 correct token, so you never waste a step entirely.

The insight that makes it work: verifying K tokens costs approximately the same as generating 1.

Why? Three reasons, all physical:

First: the weights are already being read. Whether you process 1 token or 5, you read the same ~140 GB of parameters from HBM. The memory transfer—which is the bottleneck—is amortized across all tokens being verified.

Second: you are using idle compute cycles. Those 95% idle compute units now have something to do. The extra 4 tokens add rows to the batch, filling the compute that was previously dark.

Third: verification is parallel, generation is sequential. Generating token N+1 requires knowing token N (sequential dependency). But checking whether tokens N+1 through N+5 are correct can be done in one parallel forward pass. The target model processes the draft tokens as a batch, computing the probability distribution for each position simultaneously. If any draft token is wrong, the model knows immediately—because it can see the discrepancy between its own distribution and the draft's choice. This asymmetry between generation (sequential, slow) and verification (parallel, fast) is the entire trick.

Think of it as a proofreader versus a writer. A writer produces text one word at a time, each word depending on everything before it. A proofreader can scan a paragraph in seconds and identify errors in any position simultaneously. The proofreader is parallel. The writer is sequential. Speculative decoding turns the expensive target model into a proofreader and gives the cheap draft model the writing job.

The mechanism

Speculative decoding works in rounds. Each round:

// STEP 1: Draft
for i in 1..K:
    draft_token[i] = small_model.generate()  // fast, ~60M params

// STEP 2: Verify (one forward pass)
p_target = big_model.forward(draft_tokens)   // slow model, but parallel
p_draft  = small_model.probs(draft_tokens)

// STEP 3: Accept/Reject
for i in 1..K:
    if random() < min(1, p_target[i] / p_draft[i]):
        accept(draft_token[i])           // keep it
    else:
        resample(norm(max(0, p_target - p_draft)))  // fix it
        break

// GUARANTEE: output distribution = p_target exactly

The rejection sampling criterion is the mathematical heart. If the target model agrees with the draft at least as much as the draft predicted, always accept. If the target agrees less, accept proportionally and reject the rest. On rejection, resample from the residual distribution norm(max(0, p_target - p_draft))—this "fills in" exactly the probability mass the draft missed. The result, proved in both papers: the output distribution is exactly p_target. Not approximately. Exactly. Within hardware floating-point precision. Lossless.

This is not a quality-speed tradeoff. It is free speed. The same output you would get from running the target model alone, produced faster through better scheduling of the same computation. The "lossless" guarantee is what separates speculative decoding from approximation techniques like quantization, pruning, or distillation. Those trade quality for speed. Speculative decoding trades nothing—it finds speed that was always there, hidden in the idle compute cycles of the decode phase.

Prior art: Stern, Shazeer & Uszkoreit (2018)

Speculative decoding was not born in 2022. In 2018, Mitchell Stern, Noam Shazeer, and Jakob Uszkoreit at Google published "Blockwise Parallel Decoding for Deep Autoregressive Models." They added k-1 non-autoregressive heads to a Transformer decoder to predict k positions in parallel, then verified with the autoregressive head. This is structurally the same idea as Medusa (which would come five years later).

But Stern et al. lacked two things the 2022 papers had: (1) the rejection sampling proof that makes the output distribution lossless, and (2) the era of massive models where decode latency became the dominant bottleneck. In 2018, models were small enough that decode was fast. By 2022, models were large enough that decode latency was the primary user experience problem. The solution was the same. The problem had to catch up.

Batching and speculation: complementary, not competing

A subtle point that matters for production deployments: speculative decoding and continuous batching are complementary, not competing. But their benefits appear in different regimes.

At low batch sizes (1-8 requests), speculative decoding shines. The GPU is severely underutilized during decode—plenty of idle compute to exploit. Speedups reach 2-3x per user.

At high batch sizes (32+), speculative decoding's benefit shrinks to 1.3x or less. Why? Because batching has already filled the idle compute cycles. The GPU is well-utilized from serving 32+ requests. There is nothing left for speculative decoding to reclaim. The two techniques target the same resource (idle GPU cycles) but from different angles.

The exception: long context lengths. MagicDec (Together AI, 2024) showed that speculative decoding can help throughput even at high batch sizes when context lengths are long (32K+), because the KV cache bandwidth dominates and the draft model uses a much shorter context window.

The sweet spot is the increasingly common case of serving a moderate number of concurrent users where both throughput and latency matter—exactly the operating regime of most commercial LLM APIs.

Why trees beat chains

A chain of 5 tokens at alpha=0.9 survives with probability 0.59. One rejection kills everything downstream. But a tree with branching factor 2 and depth 5 has 32 leaf paths. The probability that at least one path survives all 5 levels is dramatically higher. You verify the entire tree in one forward pass using a tree attention mask—each token attends only to its ancestors. At least one path is likely to survive deeper than any single chain would.

06 // Killing the Draft

Classic speculative decoding requires a separate draft model. You need to find one, or train one, or hope someone published a compatible one. You deploy two models simultaneously—the 70B target and a 7B draft—managing distribution alignment, memory budgets, and scheduling between them. The draft model needs to be fast enough to be worth running and accurate enough to get tokens accepted. Finding that sweet spot for every target model is real engineering pain. In September 2023, Tianle Cai at Princeton asked the question that would eliminate the problem entirely: what if the target model could draft for itself?

Medusa: the model already knows its future

Cai's paper, Medusa, adds K extra prediction heads—typically five—on top of the model's final hidden states. Each head is a single-layer FFN with a residual connection. Tiny parameter overhead. Head k predicts the token at position t+k+1. The original language model head still predicts the next token normally at position t+1.

The candidate generation is combinatorial. Take the top-s predictions from each head. Form a Cartesian product. If head 1 gives 2 candidates and head 2 gives 3, that is 6 candidate two-token continuations. Build a tree of these candidates. Verify the entire tree in a single forward pass through the target model, using a modified attention mask where each token attends only to its ancestors in the tree structure. No cross-branch contamination.

Two training variants. Medusa-1 freezes the backbone and trains only the new heads. Cross-entropy loss. Can train on a single GPU with quantization. The output distribution is unchanged—lossless. Medusa-2 jointly trains backbone and heads with differential learning rates and a two-stage warmup to preserve model quality. Better predictions, higher speedup, but needs care to avoid degradation.

Speedups: Medusa-1 achieves 2.18-2.33x. Medusa-2 reaches 2.35-3.62x, peaking on extraction tasks. The cost eliminated: 275 NVIDIA A100 GPU hours that would have been spent pre-training a separate draft model.

EAGLE: predict features, not tokens

In January 2024, Yuhui Li at Peking University published EAGLE with a deceptively simple insight. Token sequences are discrete and high-entropy—the next token could be any of 32,000+ vocabulary entries. Feature sequences (the second-to-top-layer representations) are continuous vectors with much more regularity. Autoregression is dramatically easier in feature space than in token space.

But there is a catch. Features at position t+1 depend on which token was sampled at position t. If the model might sample "am" or "always," the feature sequences diverge completely. This creates ambiguity for any feature-level predictor.

EAGLE's fix is brilliant and simple: feed the already-sampled token embedding (one step ahead) alongside the previous feature. This resolves the sampling uncertainty. The draft model's architecture: a single FC layer for dimensionality reduction plus one Transformer decoder layer. Total trainable parameters: only 0.24B-0.99B depending on target model size. The embedding layer and LM head are frozen from the target model—zero extra training for those components.

Result: 2.7-5.6x speedup. 1.5-1.6x faster than Medusa across the board. The draft model's depth—a full Transformer decoder operating on features—gives it a richer representation of the model's internal reasoning than Medusa's shallow FFN heads.

Why features are easier than tokens: the information theory

Token sequences are discrete. At each position, the model picks from a vocabulary of 32,000+ options. The entropy of this choice can be very high—especially for content words, names, and creative text. Predicting the exact next token is hard because the probability mass is spread across many options.

Feature sequences (the model's internal representations) are continuous vectors in a high-dimensional space. These vectors change smoothly from one position to the next. The "path" through feature space is predictable in a way that the discrete token path is not. Think of it this way: predicting that a sentence will continue with a positive sentiment (a direction in feature space) is much easier than predicting the exact word "wonderful" versus "great" versus "excellent" (discrete choices with similar meanings).

EAGLE exploits this by predicting in feature space first, then mapping back to tokens. The feature prediction benefits from the smoothness of continuous representations. The token prediction then only needs to map a already-well-predicted feature vector to the nearest token—a much easier problem than predicting the token from scratch.

The evidence: EAGLE's feature-level prediction achieves 1.9x speedup in ablation, versus 1.5x for a matched token-level approach. The gap is entirely due to the predictability of the target.

EAGLE-2: dynamic trees from confidence

EAGLE-1 uses a static draft tree—same shape regardless of input context. But acceptance rates are not just position-dependent. They are highly context-dependent. A confident prediction at depth 3 might be more valuable than an uncertain prediction at depth 1. Static trees waste slots on low-probability branches and miss high-probability deep ones.

EAGLE-2 discovered something remarkable: the draft model's confidence score (softmax probability of its top prediction) is a near-perfect proxy for the target model's acceptance probability. Confidence below 0.05 maps to acceptance rate around 0.04. Confidence above 0.95 maps to acceptance rate around 0.98. Near-linear correlation across the full range.

This means you can build the optimal draft tree at inference time with zero extra training. The algorithm: expand the top-k most confident tokens at each depth. Compute each candidate's value as the product of all confidence scores along its path from root (estimating actual acceptance probability since rejecting any ancestor invalidates the branch). Rerank globally. Select the top-m candidates for the final tree. Prefer shallower nodes on ties.

Result: 3.05-4.26x speedup, 20-40% faster than EAGLE-1. No additional training required beyond the EAGLE-1 draft model. Pure inference-time optimization.

The discovery that confidence is acceptance changed how draft trees are conceptualized. Static trees are designed once at system start, based on average acceptance rates across a benchmark. Dynamic trees are designed per token, adapting to the model's uncertainty at that specific point in that specific context. On "easy" tokens (deterministic continuations like "the United States of"), the tree goes deep—the model is confident at every depth, so pushing deeper is almost certainly profitable. On "hard" tokens (creative choices, ambiguous grammar, domain-specific jargon), the tree goes wide and shallow—explore many possibilities at depth 1 rather than betting on any single deep chain. The tree shape becomes a real-time diagnostic of the model's confidence landscape.

The algorithm is elegant in its simplicity. For each candidate token at each depth, compute V_i = product of all confidence scores from root to that token. This product estimates the actual acceptance probability, because rejecting any ancestor invalidates the entire branch. Sort all candidates globally by V_i. Take the top-m. That is your draft tree. No neural network, no optimization, no training. Just multiplication and sorting. The dynamic tree is a pure inference-time optimization—any EAGLE-1 draft model can be upgraded to EAGLE-2 by changing only the tree construction code.

EAGLE-3: multi-layer fusion and the scaling law

In March 2025, the same team published EAGLE-3 with three architectural changes that unlocked a qualitative shift in draft model capability.

Multi-layer feature fusion. EAGLE-1 and EAGLE-2 used only the second-to-top layer features. EAGLE-3 fuses features from low, mid, and high layers. Concatenate k-dimensional vectors from three layers into a 3k-dimensional vector, then project back to k dimensions via an FC layer. The rationale: low layers encode syntax and structure. Mid layers encode semantics. High layers encode task-specific reasoning. All three are useful for predicting future tokens.

Training-time test. Previous EAGLEs trained on ground-truth target model features. At inference time, the draft model sees its own imperfect outputs as inputs—a distribution shift. EAGLE-3 fixes this by performing "test steps" during training: the draft model's outputs are fed back as inputs for further training iterations. The model learns to handle its own errors. Modified self-attention masks during training handle the tree-like contextual relationships.

Direct token prediction. EAGLE-1 and EAGLE-2 required a feature prediction loss alongside token prediction, constraining the draft model to produce vectors that match the target model's features. EAGLE-3 drops this constraint entirely. The draft model generates unconstrained vectors optimized purely for token prediction accuracy. Cleaner gradients. Better training dynamics.

These three changes unlocked something the EAGLE line never had before: a scaling law for draft models. With ~8x more training data, speedup improves roughly linearly. Previous EAGLEs hit diminishing returns quickly—more data did not help because the architecture was the bottleneck. EAGLE-3 removed the architectural constraints.

Peak speedup: 6.47x on HumanEval with Vicuna 13B. Roughly 400 tokens per second on LLaMA 3.1 8B with a single H100 via SGLang integration.

07 // Jacobi's Ghost

Carl Gustav Jacob Jacobi published his iterative method in 1845 in Astronomische Nachrichten. The application: solving normal equations for least-squares problems in astronomical calculations—predicting where planets would be. The method decomposes a matrix into its diagonal, lower triangular, and upper triangular components, then updates all variables simultaneously using values from the previous iteration. It was considered useless for decades because sequential methods like Gauss-Seidel converge faster. But Jacobi's method has one property they lack: every variable updates in parallel. It parallelizes perfectly.

179 years later, Yichao Fu at UC San Diego applied the same mathematical structure to predicting where tokens would be.

The reformulation

The insight that makes Lookahead Decoding work is a mathematical identity hiding in plain sight. Define a function for each token position that equals zero when the token is correct:

// Autoregressive decoding = solving nonlinear equations

f(y1, x) = 0                    // token 1 depends only on prompt
f(y2, y1, x) = 0               // token 2 depends on token 1
f(y3, y1, y2, x) = 0          // token 3 depends on tokens 1-2
...
f(ym, y{1:m-1}, x) = 0          // token m depends on all previous

// Standard decoding: solve top-to-bottom, sequentially
// Jacobi decoding: solve ALL simultaneously, iterate to convergence

// where f(y_i, ...) = y_i - argmax P(y_i | context)

Standard autoregressive decoding solves these equations one at a time, top to bottom. Solve equation 1. Use the answer to solve equation 2. Use both answers to solve equation 3. Sequential. Slow. This is Gauss-Seidel iteration—the method every numerical methods textbook prefers because it converges faster.

But Jacobi iteration solves them ALL simultaneously. Initialize all future token positions with random guesses. Run the model on all positions at once. Each position produces a new prediction based on the previous iteration's guesses for all preceding positions. Not the current iteration's partially-updated values (that would be Gauss-Seidel). The previous iteration's. This makes every update independent. Parallelizable. Exactly what a GPU wants.

Convergence is guaranteed. At worst, it takes exactly m steps—the same as autoregressive—because position 1 always gets the correct token on the first iteration (it depends only on the prompt). Position 2 gets the correct token once position 1 is correct. Correctness propagates left-to-right, one position per iteration at minimum.

At best, multiple positions can "crystallize" simultaneously—if a later position happens to guess correctly even before its preceding positions are correct, that token locks in and stays correct in all subsequent iterations. This is rare but possible, and when it happens, Jacobi decoding leaps ahead of the sequential baseline.

The mathematical guarantee is what makes this interesting from a theoretical perspective. Unlike speculative decoding, which requires a separate draft model and a rejection sampling proof, Jacobi decoding is self-contained. The model verifies itself through the structure of iteration. The convergence proof comes from the properties of the fixed-point equation, not from any external verification mechanism.

The problem: vanilla Jacobi decoding gives only 1.05x speedup. LLMs trained with teacher forcing are terrible at predicting token t+k when tokens t+1 through t+k-1 are wrong. The model almost never "guesses right" at distant positions with corrupted context. The parallel updates converge one position per step, which is the same as sequential decoding.

Lookahead: the trajectory is the treasure

Fu et al. discovered that the Jacobi iterations themselves produce something valuable even when they fail to converge. As the model iterates, tokens at the same position across consecutive iterations form n-grams. A token appears at position k in iteration t. That token's natural continuation appears at position k+1 in iteration t+1. These trajectory n-grams are often valid continuations of the confirmed sequence—even though the individual iterations have not converged and most guesses are wrong.

Lookahead Decoding runs two parallel branches in every forward pass:

The lookahead branch maintains a 2D window parameterized by W (window size into the future) and N (n-gram length). W positions ahead get Jacobi-updated simultaneously. As iterations proceed, n-grams are collected from the trajectory—sequences of tokens that appeared at the same position across N consecutive Jacobi steps. These n-grams are cached in a pool.

The verification branch searches the n-gram pool for candidates whose first token matches the last confirmed token. It appends these candidates to the current sequence and verifies them in a single forward pass using an attention mask—the same tree verification trick as speculative decoding. Accept the longest correct prefix.

The result: 1.8x on MT-Bench, 2.3x on code completion, up to 4x with multi-GPU parallelism. Exact output match with greedy decoding. No draft model to train or deploy. No auxiliary parameters. The model verifies itself through the structure of Jacobi iteration. The mathematical purist's answer to speculative decoding.

The weakness is real: 1.8x is less than the 3x that well-tuned speculative decoding achieves. The "free" approach pays for its freedom with lower speedup. But the elegance is also real: exact output, zero extra models, self-verification through a 179-year-old mathematical method.

Smaller models benefit more from Lookahead Decoding. Larger models are harder to parallelize because their decode phase is more compute-saturated. The sweet spot is models in the 7-13B range where decode is firmly memory-bound and the Jacobi iterations have room to explore.

A related line of work—CLLMs (Consistency Large Language Models)—takes the Jacobi insight further by training models to converge faster on Jacobi trajectories. If you can train a model that produces better guesses at distant positions, the n-gram pool fills with higher-quality candidates, and the verification branch accepts longer prefixes. CLLMs achieve 2.4-3.4x speedup, but require additional training. The purity of Lookahead Decoding (zero extra training) is both its selling point and its ceiling.

Fu et al. connected their work to an even deeper mathematical thread: the relationship between Jacobi decoding and diffusion models. Both involve iterative refinement of a noisy initial guess toward a coherent output. Both can be parallelized. The connection suggests that the boundary between "autoregressive" and "parallel" generation may be softer than the field assumes—a theme that continues to develop in 2025 research.

The punchline

Lookahead Decoding is n-gram mining from failed Jacobi iterations. The trajectory is the treasure, not the destination. A mathematical method invented in 1845 for finding planets spent 179 years waiting for the right problem. It found it in a GPU cluster predicting the next token.

MTP: same name, different souls

Multi-Token Prediction is one of those names that gets reused because it is obvious. Of course you want to predict multiple tokens. The question is how, and two teams answered it in fundamentally different ways, for fundamentally different reasons. The disambiguation is not academic—it determines whether the technique helps training, inference, or both.

Fabian Gloeckle and colleagues at Meta FAIR published "Better & Faster Large Language Models via Multi-token Prediction" at ICML 2024. In December 2024, DeepSeek included their own MTP architecture in the V3 technical report. Same name. Different architectures. Different goals. The disambiguation is critical for anyone deploying these techniques, because choosing the wrong one for your use case means optimizing the wrong end of the pipeline.

Meta FAIR (ICML 2024)

Parallel heads. D independent transformer-layer heads sit on top of a shared trunk. Each head predicts a different future offset: head k predicts token at position t+k. Crucially, head 3 does not see head 2's output. The heads are completely independent. Shared unembedding matrix across all heads.

Primary purpose: training. The D extra heads provide denser gradient signal per training token. Each position's loss includes not just next-token prediction but predictions 2, 3, 4 tokens ahead. This forces the model to build deeper representations—like training a chess player to evaluate 4 moves ahead, not just 1. Results: +12% on HumanEval, +17% on MBPP at 13B scale. Benefits increase with scale.

Inference bonus: The extra heads (normally discarded at inference) serve as a built-in draft model. Self-speculative decoding: 3.0x speedup on code, 2.7x on text. No separate draft model needed.

DeepSeek-V3 (Dec 2024)

Sequential chain. D modules, each feeding the next. Module k takes the previous module's hidden state plus the current token embedding, projects them together, runs a single transformer block, and outputs a prediction. Each module sees the previous module's output. The chain maintains causal coherence at every depth.

Primary purpose: inference. The MTP modules serve as a built-in draft model for speculative decoding. Because the output head is shared with the main model, memory overhead is minimal. Acceptance rates: 83% at k=1, 72% at k=2, 61% at k=3. Speedup: 1.8x in generation throughput.

Training bonus: The sequential modules provide denser supervision during training. Loss weight lambda=0.3 for first 10T tokens, reduced to 0.1 for remaining 4.8T tokens. D=1 in V3 (just one extra module).

The fundamental philosophical split: Meta asks "what if the model learned to predict further ahead during training?" DeepSeek asks "what if we built a draft model into the architecture?" Meta's heads are independent because training does not need sequential coherence—it needs diverse gradient signals. DeepSeek's modules are sequential because inference does need sequential coherence—each draft token should condition on the previous one. Same name. Different souls. Different ends of the pipeline.

Meta MTP: the training signal argument

Meta's theoretical argument for why multi-token prediction improves training quality goes deeper than "more loss terms = better." The information-theoretic claim: predicting t+2 forces the model to attend to tokens that matter for longer-range dependencies. Standard next-token prediction can be solved with shallow pattern matching—"the" is followed by a noun. But predicting t+4 requires understanding clause structure, argument relationships, and semantic coherence.

The analogy: training a chess player to evaluate 1 move ahead produces a player who responds to immediate threats. Training a player to evaluate 4 moves ahead produces a player who builds positional advantage. The extra heads are not useful at inference time for their predictions (Meta discards them). They are useful at training time for the gradient signal they propagate back through the shared trunk.

Results support this: MTP benefits increase with model scale (negligible at 300M-1.3B, significant at 7B+) and are strongest on tasks requiring reasoning and generation (HumanEval +12%, MBPP +17%) while actually hurting retrieval tasks (MMLU, TriviaQA). The model gets better at generating coherent text, not at recalling facts.

DeepSeek MTP: the inference architecture argument

DeepSeek's sequential MTP is designed for a different goal: making inference fast without post-hoc engineering. Each MTP module shares the main model's embedding layer and output head, minimizing memory overhead. The sequential structure ensures each draft token conditions on the previous one, matching how autoregressive generation actually works.

The acceptance rates tell the story: 83% at k=1 (first draft token), 72% at k=2, 61% at k=3. Even at k=3, more than half the draft tokens survive verification. And these modules were trained jointly with the base model during pre-training—no separate draft training phase, no distribution alignment problem, no deployment overhead.

DeepSeek used D=1 in V3 (a single additional MTP module) with training loss weight lambda=0.3 for the first 10T tokens, reduced to 0.1 for the final 4.8T tokens. The weight reduction schedule suggests the MTP objective is most valuable early in training, when the model is learning basic prediction patterns, and less valuable later when it is fine-tuning on specific capabilities.

The paper timeline

The full technique comparison: when to use what

Choosing between inference optimization techniques depends on your deployment constraints. Here is the decision tree that production teams actually use:

If throughput is your bottleneck (serving many users, cost per token matters): Start with continuous batching (free, universal). Add PagedAttention or RadixAttention for memory efficiency. Enable prefix caching if your workload has shared prefixes (chat, agents, few-shot). Consider prefill-decode disaggregation if you serve long prompts. You will get 5-20x improvement from these alone.

If latency is your bottleneck (real-time applications, interactive use): Speculative decoding or EAGLE for 2-5x per-user speedup. Best at low batch sizes. For maximum simplicity, use DeepSeek-V3's built-in MTP modules—no separate draft model required. For maximum speed, train an EAGLE-3 draft model for your specific target.

If you want both: Run continuous batching + PagedAttention for throughput, and enable speculative decoding when batch utilization is low. SGLang supports this hybrid configuration. vLLM has speculative decoding support. The systems are converging toward a unified stack where all techniques coexist.

If you cannot train a draft model: Lookahead Decoding gives 1.5-2x with zero training. Medusa heads can be trained in hours on a single GPU. EAGLE's draft model trains in 1-2 days. These are not large investments.

The convergence

Step back and see the full arc of this article. We began with a hotel that could not manage its rooms. We moved through scheduling (Orca), memory management (PagedAttention), caching (RadixAttention), and two forms of paging (vAttention). Then we crossed from throughput to latency: the idle assembly line, speculative decoding, draft-free methods (Medusa, EAGLE), Jacobi iteration, and multi-token prediction.

Every one of these innovations shares a property: they do not change the model. The weights are identical. The architecture is untouched. The training pipeline is unaffected (except for MTP, which deliberately entangles training and inference). All the gains come from better systems engineering around a fixed model.

The cumulative impact is staggering. A production inference stack in 2025 combines all of these techniques:

The production stack, end to end (early 2025)

A state-of-the-art production inference deployment in early 2025 looks roughly like this:

Frontend: Load balancer distributes requests across GPU pools. Cache-aware routing (SGLang v0.4) sends requests with similar prefixes to the same GPU to maximize cache hit rates.

Prefill pool: Dedicated GPUs handle prompt processing. Large batch sizes for matrix-matrix efficiency. Long prompts are chunked to avoid memory spikes. Output: computed KV cache, transferred to decode pool.

Decode pool: Dedicated GPUs handle token generation. Continuous batching keeps slots filled. PagedAttention or RadixAttention manages KV cache memory. Speculative decoding (EAGLE-2/3 or MTP) runs when batch utilization allows.

KV cache management: RadixAttention radix tree shared across the decode pool via cache-aware scheduling. Prefix caching eliminates recomputation for system prompts, few-shot examples, and conversation history. LRU eviction keeps the most-used prefixes hot.

Monitoring: TTFT, TPOT, throughput, cache hit rate, batch utilization, memory usage. Alert thresholds for each. The system self-tunes batch size and speculation depth based on current load.

This stack delivers 10-50x improvement over naive serving circa 2022. The gains come from every layer of the stack working together, not from any single technique.

That is both the triumph and the limitation. Systems optimization has delivered 10-50x total improvement across throughput and latency since 2022. But the model itself—its attention mechanism, its parameter count, its activation precision—remains the same hungry consumer of compute and memory it always was. The systems engineers have squeezed the lemon. The lemon is still the same size.

What comes next

We have optimized memory, scheduling, and latency—all without changing the model itself. Continuous batching packs the GPU. PagedAttention and RadixAttention manage its memory. Speculative decoding and its descendants reclaim its idle cycles. But the biggest gains are not optimizations. They are architectural decisions made before training begins. What if attention was not quadratic? What if 75% of the weights could be thrown away after training? What if experts could be routed instead of broadcast? Part II asks those questions.
